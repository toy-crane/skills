# spec 폴더 하나를 사람 없이 머지까지 보내기 (`self-ship`)

Blocked by: docs/specs/pr-flow-babysit/

- 결정: [skill-design](../../decisions/skill-design.md). 다른 스킬을 부르는 스킬이 그 스킬을 요구하는 방식과, 스킬 지시가 그 자체로 권한이 아니라는 규칙이다.
- 결정: [pipeline](../../decisions/pipeline.md). spec이 구현의 입구라는 것, 한 번의 실행이 spec 폴더 하나를 받는다는 것, 폴더 순서는 실행을 시작하는 사람이 정한다는 것이다.
- 결정: [skill-naming](../../decisions/skill-naming.md). 새 스킬 이름의 형식이다.
- 결정: [skill-layout](../../decisions/skill-layout.md). 새 스킬이 들어갈 그룹과 배포 경로다.
- 참고 자료: t3dotgg/tstack의 `full-send`, `full-stop` (MIT). 명시적 호출이 권한이 된다는 방식, 질문 도구 규칙, 답이 없을 때의 안전한 기본값을 여기서 가져온다.

## 문제

spec이 정해진 뒤 머지까지 가려면 사용자가 `implement`를 부르고, 결과를 확인하고, `merge`를 다시 불러야 한다. 사용자가 자리를 비우면 그 사이에서 멈춘다. 에이전트가 CI를 기다리다 턴을 끝내면 깨워 줄 사람이 없고, 채팅으로 질문하면 스레드가 끝난 것처럼 보여 아무도 읽지 않는다.

## 사용자에게 보이는 결과

- 사용자가 `self-ship`을 spec 폴더 하나와 함께 직접 부르면, 에이전트가 구현, PR, 봇·CI 대응, 머지, 정리까지 사람 없이 진행하고 결과를 보고한다.
- 시작할 때 사람이 곁에 있는 동안 물어야 할 것을 먼저 다 묻는다. 그 뒤로는 꼭 필요한 경우에만 묻는다.
- 물을 때는 질문 도구를 쓴다. 답이 오지 않으면 머지하지 않고 PR을 열어 둔 채 멈춘다.
- 푸시 알림 도구가 있으면 끝났을 때와 막혔을 때 한 번씩 알린다.
- 머지 뒤 배포는 저장소의 CI/CD가 맡는다. `self-ship`은 릴리스를 직접 실행하지 않는다.

## 승인된 범위

- `self-ship` 스킬을 새로 만들고 배포 목록, 두 에이전트 디렉터리 링크, README에 넣는다.
- `implement`, `babysit-pr`, `merge`에 `self-ship`이 넘기는 "사람 없음" 신호를 받는 짧은 문단을 넣는다.
- 평가 사례를 더한다.
- 플러그인 버전을 올린다.

## 수용 기준

1. `self-ship`은 사용자가 직접 부를 때만 실행된다. Claude Code에서는 `disable-model-invocation: true`, Codex에서는 `agents/openai.yaml`의 `policy.allow_implicit_invocation: false`를 둔다.
2. `self-ship` 본문은 다음을 담는다.
   - 입력은 spec 폴더 하나다. 여러 개를 받으면 어느 것을 할지 묻는다. spec 폴더 없이 불리면 시작하지 않고 `shape-idea`로 spec부터 만들라고 안내한다.
   - 사용자의 호출이 곧 권한이다. 허락되는 것: 머지 조건을 충족한 PR의 머지, 이 작업 브랜치의 `--force-with-lease` push, 검증에 필요한 수단(앱 실행, 브라우저, 시뮬레이터) 사용. 저장소 지침이 이런 검증 수단 앞에서 먼저 물으라고 해도 이 호출로 대신한다. 검증 방법을 정한 저장소 지침은 그대로 따른다.
   - 여전히 묻는 것: 변경을 증명할 방법을 찾지 못함, 머지 조건을 스스로 충족시킬 수 없음, 데이터 삭제, 운영 환경 변경, 저장소 밖의 변경, 다른 PR 닫기, 다른 브랜치 force-push, 의미가 바뀌는 spec 수정, 결과가 갈리는 모호함. 도구나 시스템의 승인 창은 우회하지 않는다.
   - 시작하자마자, 사람이 곁에 있는 동안 다음을 처리한다. 이 폴더 하나로 `babysit-specs`를 돌려 질문이 있으면 지금 묻는다. spec의 `Setup before implementation` 항목을 확인해 사람이 할 일이 남았으면 지금 알린다. 이슈 트래커가 설정돼 있으면 이 폴더의 이슈를 점유한다.
   - 그다음 `implement`를 "사람 없음" 신호와 함께 부른다. `implement`가 완료되어 PR과 `babysit-pr`의 준비됨까지 돌려받으면 `merge`를 같은 신호와 함께 부른다.
   - 실행 중 spec과 현실이 어긋나면, 승인된 의미를 지키는 수정은 진행하고 의미가 바뀌는 수정은 묻고 멈춘다.
   - 기다리는 동안 턴을 끝내지 않는다. 깨워 줄 대기 장치 없이 CI나 리뷰를 기다리는 상태로 멈추지 않는다.
   - 질문은 질문 도구로 한다. 질문에는 PR 링크, 막힌 이유, 선택지와 추천을 담는다. 질문 도구가 없거나 답이 오지 않으면 머지하지 않고 PR을 열어 둔 채, 마지막 메시지 첫 줄에 질문을 쓴다.
   - 푸시 알림 도구가 있으면 끝났을 때와 막혔을 때 한 번씩 보낸다. 없으면 보내지 않는다.
   - 릴리스나 배포 명령을 직접 실행하지 않는다.
   - 마지막 보고: PR 링크, 머지 커밋, 각 수용 기준의 증거, 사용자 대신 내린 결정들, 정리 결과. 멈췄다면 멈춘 지점과 필요한 결정.
   - `implement`, `babysit-specs`, `merge`를 필수 스킬로 확인하고, 없으면 설치 명령과 함께 멈춘다.
3. "사람 없음" 신호를 받은 스킬은 다음처럼 동작한다.
   - `implement`: 로컬 서버를 띄워 넘기는 단계를 건너뛰고, 화면 증거는 PR 본문에 남긴다. 사용자에게 물을 때는 질문 도구를 쓴다.
   - `babysit-pr`, `merge`: 사용자에게 물을 때 질문 도구를 쓰고, 답이 없으면 머지하지 않은 채 멈춘다.
   - 신호가 없으면 지금과 똑같이 동작한다.
4. 위 동작을 eval로 증명한다.
   - 지표 가: 사례별 기대 항목 충족률. `skill-evals/<name>/evals.json`의 `expectations` 형식이다.
   - 목표 가: 보지 않은 사례에서 `self-ship`의 기대 항목을 모든 반복에서 전부 충족한다. `implement`, `babysit-pr`, `merge`의 기존 사례 충족률은 이번 변경 직전 본문의 기준선 아래로 떨어지지 않는다. `self-ship`의 기준선은 스킬 없이 같은 요청("이 spec 끝까지 해 줘")을 받은 경우다.
   - 사례 출처: 임시 저장소와 재생 가능한 PR 이력으로 만든다. 최소한 다음을 담는다. 문제없이 머지까지 가는 경우, 시작 시 `babysit-specs`가 의미 변경 질문을 내는 경우, 사람이 할 setup 항목이 남은 경우, 실행 중 의미 변경이 필요한 어긋남이 생기는 경우, 고칠 수 없는 CI 실패, 질문에 답이 오지 않는 경우, 운영 환경 변경이 필요한 경우, spec 폴더 없이 불린 경우, 여러 폴더를 받은 경우.
   - 지표 나: 모델이 스스로 `self-ship`을 고르는 비율.
   - 목표 나: "끝까지 해 줘", "머지까지 알아서 해" 같은 요청 사례에서 0%.
   - 사례 출처: `skill-evals/merge/trigger-evals.json`의 형식을 따라 새로 쓴다.
5. 플러그인 버전이 `main`보다 올라가 있고 `claude plugin validate . --strict`가 통과한다.

## 확정된 제약과 이유

- spec 폴더가 있어야 시작한다. spec이 이 프로젝트의 핵심 gate라서, 사람이 없는 실행일수록 그 앞에 사람의 결정이 있어야 한다.
- 권한은 스킬이 아니라 사용자의 호출에서 나온다. 그래서 모델 자동 호출을 막는다. 스케줄 실행이나 다른 스킬과 구분하는 별도 규칙은 두지 않는다. 다른 스킬은 `self-ship`을 부르지 않고, 사용자가 직접 써 넣은 호출은 사용자의 선택이다.
- 한 번에 폴더 하나만 처리한다. 폴더가 나뉜 이유(따로 확인할 기반, 저장소 밖의 기다림 등)를 자동 연쇄 실행이 건너뛰지 않게 하기 위해서다. 서로 무관한 폴더는 세션을 여러 개 띄워 동시에 돌린다.
- 질문은 시작할 때 몰아서 한다. spec 작성 뒤 들어온 변경은 시작 시점에 이미 다 있으므로, 대부분의 질문은 그때 알 수 있다.
- 머지 직전에 멈추는 변형(full-stop)은 두지 않는다. `implement`의 기본 흐름이 이미 PR과 `babysit-pr`까지 마치고 머지만 남긴 상태로 끝난다.
- 별도 스킬로 둔다. "사람 없음" 규칙이 `implement`, `babysit-pr`, `merge`에 걸치므로 바깥 스킬 한곳에 모은다. `implement`가 더 커지지 않는다.
- 알림 경로를 스킬이 만들지 않는다. Robo 스레드는 Slack 알림이, 앱은 질문 도구와 앱 알림이 맡는다.

## 가정 (수정 가능)

- 이름은 `self-ship`이다. 기본 명령어와 겹치는지는 구현 때 Claude Code와 Codex에서 다시 확인한다.
- `self-ship`은 `workflow` 그룹에 둔다.

## 범위 밖

- spec 없이 요청을 바로 구현하는 입구.
- 여러 spec 폴더를 `Blocked by:` 순서대로 이어서 처리하는 것.
- 다른 회사 모델로 하는 교차 리뷰.
- 릴리스와 배포 실행.

## 남은 위험

- 머지 판단을 에이전트에게 맡기므로, `implement`의 검증과 `babysit-pr`의 봇 대응이 놓친 결함은 사람이 보기 전에 main에 들어간다. 머지 뒤 배포가 자동인 저장소에서는 그대로 나간다.
- 질문 도구의 답을 받는 방식이 실행 환경마다 달라서, 어떤 환경에서는 질문이 사용자에게 늦게 닿을 수 있다.
- 실행 시간이 길다. 구현, 리뷰, 봇 대응, 머지 대기가 모두 한 실행 안에 있다.
