# triage는 판단만 하고, 구현과 결정 대화는 다른 Skill에 넘기기

## 문제

지금 `triage-issues`는 대기열 고르기, 첫 판단, 결정 대화, 스펙 작성, 작은
수정 구현, "사람이 답했는지" 판단을 모두 한다. 사람이 답했는지는 질문 뒤 댓글의
작성자·시각과 본문 변경으로 가린다. 한 Skill에 역할이 너무 많다.

flyn에서는 사람과 에이전트의 대화를 메신저로 옮긴다. 이 Mac에 상주하는 실행기가
새 아이디어면 `triage-issues`를 이슈 하나로 실행하고, 답글이면 그 이슈의
`shape-idea` 대화를 사람의 답과 함께 이어 실행한다. 사람이 답했는지는 실행기가
안다. Skill은 이 실행기를 몰라야 하고, 채팅, 예약 작업, 실행기 어디서 실행해도
같게 동작해야 한다.

2026-10-02 flyn 저장소의 shape 세션에서 사용자가 아래 결정을 확정했다.

## 사용자에게 보이는 결과

- 새 이슈는 `triage-issues`가 한 번만 판단한다. 중복이나 이미 된 요청은 근거와
  함께 닫힌다. 분명하고 작은 요청은 같은 실행에서 `implement`로 이어져 구현 PR이
  된다. 정보나 결정이 필요한 요청은 같은 실행에서 `shape-idea` 대화로 이어지고,
  첫 질문은 `shape-idea`가 쓴다.
- 판단 결과는 이슈의 요약 구역과 트래커 규약의 라벨·상태로 남는다. 그래서 다음
  실행이 같은 이슈를 다시 판단하지 않는다.
- `shape-idea`가 다 정했는데 변경이 작으면 스펙 없이 정한 내용을 이슈 요약에
  남기고 바로 `implement`로 넘긴다. 나중 작업이 다시 읽을 계약이 생기는 큰
  변경은 지금처럼 스펙을 쓴다.
- `implement`는 스펙 폴더뿐 아니라 이슈와 정한 결정도 받는다. 이슈에서 시작한
  구현은 `Issue:` 줄과 닫는 문구가 든 PR로 끝난다.
- 트래커가 없거나 실행기가 없는 프로젝트에서도 세 Skill이 동작한다.

## 승인된 범위

1. `triage-issues`는 새로 생긴 이슈를 처음 한 번만, 판단만 한다.
   - 이슈 번호를 받으면 그 하나만 다룬다. 받지 않으면 아직 판단하지 않은 새
     이슈만 고른다. 기존 제외 조건(진행 중, 리뷰 신호, 열린 연결 PR, default
     branch 스펙 폴더의 `Issue:` 줄)과 원격 Git claim은 유지한다.
   - 중복이나 이미 됨 → 트래커 규약의 완료 처리로 직접 닫는다.
   - 결과가 분명하고 변경이 작음 → 같은 실행 안에서 `implement`를 이름으로
     부른다.
   - 정보나 결정이 필요함 → 같은 실행 안에서 `shape-idea`를 이름으로 부른다.
     첫 질문은 `shape-idea`가 쓴다.
   - 판단 결과는 트래커 규약의 라벨·상태로 남긴다.
2. `triage-issues`에서 뺀다: 직접 구현, 스펙 작성, 질문 작성, 대기 중인 이슈를
   다시 다루는 규칙, "사람이 답했는지" 판단(질문 뒤 사람 댓글 확인, 사람/AI 댓글
   구별, 본문 변경 지문). 댓글은 판단 근거로 읽을 뿐 실행 조건으로 쓰지 않는다.
   실행 여부는 실행하는 쪽이 정한다.
3. `implement`는 스펙 폴더 대신 이슈와 정한 결정도 입력으로 받는다. 검증, 런타임
   확인, 리뷰 규칙은 그대로다. PR 본문에는 `Issue: <tracker>:<id>` 줄과 트래커
   규약의 닫는 문구를 쓴다. 트래커가 없으면 이슈 대신 사람이 준 요청과 결정을
   입력으로 받는다.
4. `shape-idea`는 다 정했는데 변경이 작으면 스펙을 쓰지 않는다. 정한 내용을
   이슈의 요약 구역(트래커가 있을 때)에 남기고 `implement`를 이름으로 부른다.
   "작다"는 `triage-issues`가 쓰던 "결과가 분명하고 변경이 작다"와 같다. 대화
   방식(한 번에 결정 하나, 권장안)은 바꾸지 않는다. 사람의 답은 대화로 받는다.
5. 세 Skill 모두 메신저, 실행기, 특정 트래커 이름을 본문에 넣지 않는다. 트래커가
   없는 프로젝트, 실행기가 없는 프로젝트에서도 동작해야 한다.
6. 바깥 입력(앱 사용자 의견, 오류 이슈)은 Skill 변경 범위가 아니다.
   `setup-issue-tracker`에 출처 칸을 더하지 않는다.

## 수용 기준

1. 이슈 번호를 받은 `triage-issues`는 그 이슈 하나만 다룬다. 이미 판단한 이슈면
   지금 판단을 보고하고 멈춘다. 사람이 다시 판단하라고 분명히 말한 경우만 다시
   판단한다.
2. 번호 없이 실행한 `triage-issues`는 규약의 "아직 판단하지 않음" 조회가 돌려준
   이슈만 오래된 순서로 본다. 중복·이미 됨으로 닫은 이슈 뒤에는 다음 이슈로
   넘어가고, `implement`나 `shape-idea`로 처음 넘긴 이슈에서 멈춘다. 한 실행은
   이슈 하나만 넘긴다.
3. `triage-issues`는 넘기기 전에 요약 구역과 판단 신호를 먼저 쓴다. 넘긴 Skill이
   없거나 중간에 실패해도 그 이슈는 다음 실행에서 다시 판단되지 않는다.
4. `triage-issues`는 질문 뒤 댓글이나 본문 변경을 실행 조건으로 보지 않는다.
   대기 중인 이슈를 다시 고르지 않는다. 직접 구현하거나 스펙을 쓰거나 질문을
   쓰지 않는다.
5. 넘길 Skill이 설치돼 있지 않으면 `triage-issues`는 판단을 남기고, 사람이 할
   다음 단계를 보고한다.
6. `triage-issues`는 판단 표시를 쓴 뒤 Git claim을 풀고 넘긴다. 결정 대화가
   며칠 걸려도 claim이 남지 않는다.
7. 이슈를 받은 `implement`는 그 이슈를 규약대로 클레임하고, 이슈 본문·요약
   구역·댓글과 넘겨받은 결정을 구현 계약으로 읽는다. 커밋마다
   `Issue: <tracker>:<id>` 트레일러를 남긴다. 끝나면 `Issue:` 줄과 닫는 문구가
   든 ready-for-review PR을 연다. 요청 결과가 검증할 만큼 분명하지 않으면 추측하지
   않고 결정 대화로 돌린다.
8. 트래커가 없을 때 `implement`는 사람이 준 요청과 결정을 계약으로 삼는다.
   이슈를 만들거나 `Issue:` 줄을 쓰지 않는다.
9. `pr`과 `merge`는 커밋의 `Issue:` 트레일러도 모아 PR 본문에 같은 줄을 쓴다.
   닫는 문구는 diff와 검증이 구현 전달을 보일 때만 쓴다.
10. `shape-idea`는 이슈에서 시작하면 이슈 본문, 요약 구역, 댓글을 문제와 방향으로
    읽는다. 다 정했고 결과가 분명하고 변경이 작으면 `spec.md`를 쓰지 않는다.
    트래커가 있으면 정한 내용을 이슈 요약 구역에만 쓰고, `implement`를 이슈와
    결정으로 부른다. 트래커가 없으면 요청과 결정으로 부른다.
11. 큰 변경이면 `shape-idea`는 지금처럼 `spec.md`를 쓰고, 시작한 이슈의
    `Issue:` 줄을 적는다.
12. 세 Skill 본문에 메신저, 실행기, 특정 트래커 이름이 없다.
13. `setup-issue-tracker` 템플릿은 triage용 "사람의 답 감지, 본문 수정 감지,
    합치지 않고 닫힌 스펙 PR의 Backlog 복귀"를 더 기록하지 않는다. 대신 "아직
    판단하지 않음" 조회와 요약 구역 표식을 기록한다.

## 확정된 제약과 이유

- **판단과 실행을 한 실행에 묶는다.** triage가 라벨만 남기고 실행기가 라벨을 읽어
  다음 단계를 시작하는 구조는 고르지 않았다. 절차가 하나 더 생기고, 실행기가 없는
  프로젝트에서는 라벨에서 멈춘다.
- **사람이 답했는지는 실행하는 쪽이 안다.** 댓글 작성자와 시각, 본문 지문으로
  답을 추측하는 규칙은 Skill에서 뺀다. 실행기가 없는 프로젝트에서는 사람이 이슈를
  지정해 다시 실행해야 대기 중인 이슈가 진행된다. 사용자는 이 점을 받아들였다.
- **각 Skill은 스스로 선다.** 다른 Skill을 이름으로 부를 수는 있지만 그 본문을
  안다고 가정하지 않는다. 요약 구역 표식은 규약에 적어 두고, `shape-idea`는
  triage의 보조 스크립트 없이 그 구역을 직접 고친다.
- **기존 표식 문자열은 그대로 둔다.** `<!-- triage-issues:triage:start -->`와
  `<!-- triage-issues:spec:start -->` 계열은 이미 flyn 이슈에 들어 있다. 바꾸면
  두 번째 구역이 생긴다.

## 가정 (수정 가능)

- **"아직 판단하지 않음"의 기준**: 요약 구역이 없고, 규약의 판단 결과 신호
  (`needs-info`, `needs-decision`, 리뷰 신호, 진행 신호, 구현 대기 상태)도 없는
  열린 일반 이슈다. 요약 구역은 어느 트래커에서나 남는 표시라서 기준의 중심에
  둔다. 트래커별 조회 방법은 `setup-issue-tracker` 템플릿에만 둔다. 사람이 요약
  구역을 지우면 다시 판단 대상이 된다.
- **이슈에서 시작한 구현은 `implement`가 PR까지 연다.** 실행기 같은 무인 실행에는
  나중에 PR을 열 사람이 없고, 이슈는 PR이 합쳐질 때 닫히기 때문이다. `pr`이 있으면
  그것을 쓰고, 없으면 직접 연다. 스펙 폴더 입력은 지금처럼 PR을 열지 않는다.
- **결정 대기 라벨은 클레임이 지운다.** 작은 변경이면 `implement`의 클레임이,
  큰 변경이면 스펙이 합쳐진 뒤 구현의 클레임이 `needs-info`, `needs-decision`을
  지운다. 이 동작은 규약의 클레임 작업에 적는다.
- **합치지 않고 닫힌 스펙 PR의 이슈는 사람이 되돌린다.** 이전에는 triage가
  Backlog로 돌렸지만, 그것은 대기 중인 이슈를 다시 다루는 규칙이라 뺐다.
  `maintain-project-context`도 default branch에 없는 스펙은 보지 않는다.
- **이름 없이 실행한 triage도 한 번에 이슈 하나만 넘긴다.** 결정 대화는 이슈마다
  이어 붙는데, 한 실행에서 둘을 넘기면 대화가 섞인다.

## 범위 밖

- 실행기 자체(메신저 연동, 답글 감지, `--resume` 연결). 별도 저장소에서 한다.
- 바깥 입력(앱 사용자 의견, 오류 이슈)의 수집과 표시.
- 큰 변경에서 `shape-idea`가 쓴 스펙의 PR을 여는 일. 지금처럼 실행하는 쪽이나
  사람이 `pr`로 연다.
- 이미 `needs-info`나 `needs-decision`으로 기다리는 flyn 이슈의 이주. flyn에서
  사람이 이슈를 지정해 `shape-idea`를 실행한다.

## 남은 위험

- 실행기가 없는 프로젝트에서는 결정 대기 이슈가 사람이 다시 실행할 때까지 멈춘다.
- 요약 구역을 쓰는 도중 사람이 본문을 고치면 그 수정이 사라질 수 있다. 쓰기 직전에
  다시 읽고 쓴 뒤 확인하지만, 조건부 갱신이 없는 트래커에서는 경쟁이 남는다.
- `shape-idea`가 "작다"고 잘못 보면 스펙 없이 큰 변경이 구현으로 간다. 구현 중
  계약이 부족하면 `implement`가 결정 대화로 돌린다.

## 의존하는 결정

- [pipeline](../../decisions/pipeline.md): 이슈 트래커, 스펙 폴더, 구현의 넘김
  규칙. 이 스펙에 맞게 고친다.
- [shape-idea](../../decisions/shape-idea.md): 쓰기 경계와 스펙 작성 규칙. 작은
  변경의 넘김을 더한다.
- [skill-design](../../decisions/skill-design.md): 다른 Skill을 이름으로만 부르고
  스스로 서는 Skill.
