# `implement`가 리뷰 지적을 고칠 때 범위를 키우지 않기

- 결정: [pipeline](../../decisions/pipeline.md). 전체 diff 리뷰를 한 번 받고, 무엇을 고치고 무엇을 기록할지 나누는 기준이다.
- 결정: [skill-design](../../decisions/skill-design.md). 지침은 결과를 긍정형으로 적고 방법은 모델에게 맡긴다는 규칙이다.
- 결정: [testing](../../decisions/testing.md). 기준이나 이름 붙은 이유가 요구하지 않는 코드는 쓰지 않는다는 규칙이다.
- 참고 자료: t3dotgg/tstack의 `sol-loop`, `babysit-pr` (MIT). 수정 방식과 범위에 관한 지침을 여기서 가져온다.

## 문제

`implement`는 리뷰 지적 중 무엇을 고칠지는 정해 두었다. 수용 기준을 깨거나 평소 사용 경로에서 직접 재현한 결함만 고친다. 하지만 **어떻게** 고칠지는 정하지 않았다. 그래서 고쳐야 할 지적 하나에 lock, cache, helper, 옵션을 새로 더하거나, 실제로 일어난 경우를 넘어 생길 수 있는 경우까지 막는 코드가 붙을 수 있다. 리뷰 반영이 끝난 뒤 diff가 spec 의도에서 벗어났는지 다시 보는 단계도 없다.

## 사용자에게 보이는 결과

- `implement`가 리뷰 지적을 고칠 때, 같은 결함을 고치는 방법 중 코드를 지우거나 범위를 좁히는 쪽을 먼저 고른다.
- 실제로 일어난 경우만 고친다.
- 리뷰를 반영한 뒤 diff 전체를 spec 의도와 다시 대조하고, 의도에 없던 코드가 붙었으면 걷어낸다.
- 지적에 동의하지 않으면 근거를 대고 보고한다.

## 승인된 범위

- `implement` 본문의 리뷰 결과 처리 부분에 수정 방식 지침을 넣는다.
- `implement` 평가 사례를 더한다.
- 플러그인 버전을 올린다.

## 수용 기준

1. `implement` 본문은 다음을 담는다. 숫자 기준이 아니라 에이전트가 스스로 판단할 수 있는 지침으로 쓴다.
   - 고치기로 한 지적에 방법이 여럿이면, 코드를 지우거나 범위를 좁히는 수정을 먼저 고른다. 새 lock, cache, helper, 옵션은 그것으로만 고칠 수 있을 때 쓴다.
   - 재현한 경우를 고친다. 같은 지적이 가리키는 다른 경로, 드문 경우, 작은 성능 차이, 추가 호환성, 의도에 없는 테스트와 방어 코드는 고치지 않고, 기존 기준대로 기록하거나 handoff에 남긴다.
   - 리뷰 반영을 마친 뒤 전체 diff를 spec 의도와 다시 대조한다. 어떤 수용 기준이나 이름 붙은 이유도 요구하지 않는 코드가 붙었으면 걷어내고 영향받은 검증을 다시 돌린다.
   - 지적에 동의하지 않으면 근거(file:line, 테스트, 출력)를 붙여 handoff에 적는다. 리뷰를 끝내려고 동의하지 않는다.
   - 리뷰를 한 번만 받는다는 기존 규칙과 무엇을 고칠지의 기존 기준은 바꾸지 않는다.
2. 위 동작을 eval로 증명한다.
   - 지표: 사례별 기대 항목 충족률. `skill-evals/implement/evals.json`의 `expectations` 형식이다.
   - 목표: 새로 더한 사례의 기대 항목을 보지 않은 사례에서 모든 반복에 걸쳐 전부 충족하고, `implement`의 기존 사례 충족률이 이번 변경 직전 본문의 기준선 아래로 떨어지지 않는다.
   - 사례 출처: 기존 `skill-evals/implement/fixtures`의 리뷰 결과 처리 사례를 바탕으로 만든다. 최소한 다음을 담는다. 고쳐야 할 결함에 helper를 새로 만드는 수정과 조건 하나를 지우는 수정이 모두 가능한 경우, 재현한 경우 옆에 드문 경우까지 막으라는 지적이 함께 온 경우, 수정 뒤 의도에 없는 방어 코드가 diff에 남은 경우, 근거로 반대해야 하는 틀린 지적.
3. 플러그인 버전이 `main`보다 올라가 있고 `claude plugin validate . --strict`가 통과한다.

## 확정된 제약과 이유

- diff 줄 수 같은 숫자 기준을 쓰지 않는다. 숫자는 필요한 변경과 불필요한 변경을 구분하지 못한다. 사용자가 판단 지침 쪽을 골랐다.
- 리뷰 루프를 새로 만들지 않는다. 한 번 받는 리뷰 안에서의 수정 방식만 정한다.

## 가정 (수정 가능)

- 같은 지침이 흔들기(adjacent probe)에서 나온 수정에도 적용된다. 흔들기 결과는 이미 리뷰 결과와 같은 기준으로 다루기 때문이다.

## 범위 밖

- `babysit-pr`의 봇 지적 처리. 그 스킬 본문이 따로 정한다.
- 무엇을 고칠지의 기준 변경.

## 보류한 점

- 없음.

## 남은 위험

- "지우거나 좁히는 수정"이 가능한지는 에이전트 판단이라, 더 복잡한 수정이 정당한 경우를 지나치게 피할 수 있다.
