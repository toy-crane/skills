# merge와 triage-issues가 PR을 `pr`로 만들기

[skill-design](../../decisions/skill-design.md)은 Git 전달 스킬의 단독 동작과,
이 작업으로 정한 "`pr`을 부르고 없을 때는 무엇을 남기는가"의 기준이다.
[pr-descriptions](../../decisions/pr-descriptions.md)는 PR 본문 설명, 화면 증거,
이슈 연결 규칙의 기준이다. 이슈 연결의 세부 동작은
[spec-issue-link](../spec-issue-link/spec.md)가 정한 그대로 따르며, 이 스펙은
그 규칙을 어느 스킬이 들고 있는지만 바꾼다.

## 문제

2026-10-09 기준 dearly 저장소의 최근 2주 세션 중 `gh pr create`를 실행한
42개 가운데 `pr`을 로드한 세션은 11개뿐이었다. 나머지 31개 중 28개는
`merge` 안에서 PR을 만들었고, 3개는 `triage-issues` 세션이었다.

- `merge`는 `pr`의 이슈 연결 절과 본문 절을 거의 그대로 복사해 들고 있다.
  지금은 두 경로의 본문 품질이 같지만, 한쪽만 고치면 "PR 올려 줘"와
  "머지해 줘"의 본문이 달라진다.
- `triage-issues`는 "적절하면 PR 스킬을 쓴다"고만 적어서, 세 세션 모두
  `pr`을 부르지 않았다. 이 경로의 PR에는 본문 작성 지침이 아예 없었다.
- GitHub PR 템플릿으로는 막을 수 없다. `gh pr create` 2.100.0은
  `--body`나 `--body-file`을 받으면 템플릿을 읽지 않고, 에이전트는 항상
  본문을 직접 넘긴다.

## 사용자에게 보이는 결과

- "PR 올려 줘", "머지해 줘", triage가 올린 PR 모두 같은 `pr` 지침으로 쓴
  본문을 가진다. 본문 규칙을 고치면 세 경로에 한 번에 반영된다.
- "머지해 줘"는 PR URL을 보여 주고 멈추지 않는다. PR을 만든 뒤 검증하고
  병합하고 정리까지 마친다.
- `pr` 없이 `merge`나 `triage-issues`만 설치한 사용자도 PR을 받는다. 본문은
  문제, 변경 전후, 검증만 짧게 적히지만, 트래커가 설정된 저장소에서는 이슈
  연결(`Issue:` 줄, 닫는 참조 여부)이 `pr`을 쓸 때와 같다.

## 승인된 범위

1. **merge는 PR 생성·갱신을 `pr`에 맡긴다.** 새 PR을 만들 때와 열린 PR의
   본문을 고칠 때 설치된 `pr`을 명시적으로 부른다. `merge`가 먼저 하는
   `pull` 동기화, 기존 열린 PR의 head 맞추기, 병합 전에 커밋의
   `Spec-Folder` 트레일러를 읽어 두는 일은 그대로 `merge`가 한다. `pr`이
   브랜치를 publish하므로, `merge`는 동기화한 head를 검증한 뒤에 `pr`을
   부른다. 검증하지 않은 커밋이 원격에 올라가지 않게 하기 위해서다.
2. **merge는 `pr`의 마무리를 중간 단계로 다룬다.** `pr`은 "URL을 주고
   끝낸다"고 적혀 있지만, `merge` 안에서는 그 지점에서 멈추지 않고 검증,
   병합, 정리, 트래커 대조로 이어진다는 점을 `merge`에 적는다.
3. **merge의 본문 절을 지운다.** "Make the body understandable" 절(화면 증거,
   첨부, 민감 정보 검사 포함)은 `merge`에서 빠진다. `pr`이 없을 때 쓸 짧은
   대체 문장 하나만 남긴다. 문제, 변경 전후, 검증 근거를 적는다.
4. **이슈 연결 규칙은 merge에 남긴다.** 스펙 폴더 수집, 이슈 생성·재사용,
   spec.md와 PR 본문의 `Issue:` 줄, 닫는 참조 조건은 `pr`이 없을 때도
   `merge`가 직접 지킨다. 병합 뒤 대조와 이후 재시도가 합쳐진 PR 본문의
   `Issue:` 줄로 이슈를 찾기 때문이다. `pr`이 있으면 이 일은 `pr`이 하고
   `merge`는 결과를 확인한다. 남기는 사본은 지금의 긴 절을 그대로 두지 않고
   위 네 가지 결과만 적은 짧은 대체 문장으로 줄인다. `project-knowledge`의
   후속 항목 규칙처럼 "부르는 문장 + 압축한 인라인 대체" 모양이다.
5. **병합 뒤 일은 merge에 남긴다.** 이슈 닫기, 스펙만 담은 PR의 준비 상태
   전환, 트래커 실패 보고와 재시도는 지금처럼 `merge`가 한다.
6. **triage-issues는 두 곳에서 `pr`을 직접 부른다.** 구현 PR과 스펙 PR을
   올리는 자리에 "`pr`로 올린다"고 적는다. 지금의 일반 문장("적절하면 PR
   스킬을 쓴다")은 PR에 대해서는 이 명시 호출로 바뀐다. `pr`이 없을 때의
   대체 동작은 `merge`와 같은 모양이다. 짧은 본문을 쓰고 이슈 연결 규칙은
   지킨다.
7. **evals를 더한다.** `merge`와 `pr`, `triage-issues`의 evals에 아래 수용
   기준을 확인하는 사례를 넣는다.

## 수용 기준

1. 트래커가 없는 저장소에서 "머지해 줘"를 받고 `pr`이 설치되어 있으면,
   `merge`는 `pr`을 불러 PR을 만들고, URL에서 멈추지 않고 검증 뒤 원격이
   `MERGED`를 보고할 때까지 진행한 다음 정리 결과를 보고한다.
2. 열린 PR이 이미 있는 "머지해 줘"에서, PR 본문을 최종 변경에 맞춰야 하면
   `merge`는 `pr`을 불러 같은 PR을 갱신하고 새 PR을 만들지 않는다.
3. 화면 변경이 있는 "머지해 줘"에서 PR 본문의 전후 영상과 설명은 `pr`의
   지침으로 만들어진다. `merge` 본문에는 화면 증거 지침이 없다.
4. `pr`이 설치되지 않은 상태에서 트래커가 설정된 저장소의 "머지해 줘"는,
   스펙 폴더의 이슈를 만들거나 재사용하고 PR 본문에 `Issue: <tracker>:<id>`
   줄을 넣는다. 본문 설명은 문제, 변경 전후, 검증만 있어도 된다.
5. 같은 상태에서 구현을 전달한 PR은 닫는 참조를 넣고, 스펙만 담은 PR은
   닫는 참조를 넣지 않는다. `pr`이 있을 때와 결과가 같다.
6. "PR 올려 줘"만 받은 `pr`은 지금처럼 URL을 주고 멈추며 병합하지 않는다.
   "머지해 줘"는 `pr`이 아니라 `merge`로 가는 요청이다.
7. `triage-issues`가 작은 구현을 끝내고 PR을 올릴 때 `pr`을 부른다. PR 본문은
   `Issue:` 줄과 닫는 참조를 담는다.
8. `triage-issues`가 스펙 PR을 올릴 때 `pr`을 부른다. 이미 spec.md에 적힌
   `Issue:` 줄의 이슈를 재사용하고 새 이슈를 만들지 않으며, 본문에는 닫는
   참조가 없다.
9. `pr` 없이 `triage-issues`가 올린 PR도 7, 8번의 이슈 연결 결과가 같다.

## 확정된 제약과 이유

- **호출은 스킬 본문에 명시한다.** description만 보고 알아서 고르게 두지
  않는다. Git 스킬 라우팅 평가에서 암시적 활성화는 56개 중 25개였고,
  triage의 일반 문장은 세 세션 모두에서 `pr`로 이어지지 않았다.
- **대체 동작은 줄이되, 나중에 다시 읽는 데이터는 줄이지 않는다.** 본문
  설명과 화면 증거는 표현 품질이라 `pr`이 없으면 낮아져도 된다. `Issue:`
  줄과 닫는 참조는 `merge`의 병합 뒤 대조와 재시도가 읽으므로 빠지면
  동작이 깨진다. 이 구분이 이번에 [skill-design](../../decisions/skill-design.md)에
  더해졌다.
- **전체 사본 + CI 동일성 검사는 택하지 않았다.** 갈라짐은 막지만 긴
  사본이 그대로 남고 마크다운 절 비교 도구가 새로 필요하다.
- **이슈 연결 없는 짧은 대체 동작도 택하지 않았다.** 단독 설치된 `merge`가
  자기 대조 경로를 깨뜨린다.

## 가정 (에이전트 판단, 뒤집을 수 있음)

- triage의 PR 고유 규칙은 `pr` 규칙과 결과가 같다고 확인했다. 구현 PR의
  닫는 참조("검증된 PR이 직접 구현을 전달한다")는 `pr`의 "diff와 검증이
  구현 전달을 보여 줄 때만"과 같고, 스펙 PR의 "닫는 참조 없이 `Issue:` 줄"은
  `pr`의 스펙 전용 규칙과 같다. triage가 spec.md에 먼저 `Issue:` 줄을 쓰는
  순서도 `pr`의 "그 ID를 쓰고 아무것도 만들지 않는다"와 맞는다. 그래서
  triage의 PR 본문 문장은 `pr` 호출과 대체 동작으로 줄여도 결과가 같다.
  claim 확인, 라벨·리뷰 신호, `Triage 요약`처럼 triage만의 일은 그대로 둔다.
- `merge`가 이미 `pull`로 base를 맞춘 뒤 `pr`을 부르므로, `pr`의 base 맞추기는
  보통 할 일이 없다. 중복 실행은 무해하다고 본다.
- rebase 충돌 복구처럼 PR head만 바뀌고 변경 내용은 같은 경우에는 `pr`을
  다시 부르지 않는다. 본문이 최종 변경과 어긋날 때만 다시 부른다.
- `pr` evals에는 "머지해 줘"가 `pr`에서 병합까지 가지 않는지 보는 대조
  사례를, `merge` evals에는 1–5번 사례를, `triage-issues` evals에는 7–9번
  사례를 둔다.

## 손대지 않는 것

- `pr`의 본문 규칙과 이슈 연결 규칙 자체. 이번 작업은 규칙을 누가 들고
  있는지만 바꾼다.
- `merge`의 병합 방식 선택, auto-merge, 정리, 트래커 대조 절차.
- `triage-issues`의 선택, claim, 조사·분기, 이슈 본문 관리.
- GitHub PR 템플릿 도입. 위 문제 절의 이유로 대안이 아니다.

## 미룬 것

없음.

## 남은 위험

- 이슈 연결 규칙은 `pr`, `merge`, `triage-issues` 세 곳에 남는다. 갈라질 수
  있는 사본이 완전히 사라지지는 않으며, 이것은 단독 설치를 지키려고 감수한
  잔여 중복이다. 사본을 짧은 결과 문장으로 줄이고, 4·5·9번 수용 기준의
  eval이 세 경로의 결과가 같은지 확인한다.

- `merge` 안에서 `pr`을 부른 뒤, 모델이 `pr`의 "URL을 주고 끝낸다"에 끌려
  병합 전에 멈출 수 있다. 2번 범위와 1번 수용 기준의 eval이 이 위험을
  확인한다. 실패하면 문장 위치나 표현을 고쳐 새 대조 사례로 다시 본다.
- 단독 설치의 짧은 본문은 화면 변경에서 전후 영상이 없을 수 있다. 의도한
  품질 저하이지만, 단독 설치 사용자가 많으면 다시 볼 일이다.
- [spec-issue-link](../spec-issue-link/spec.md) 6번("merge는 스스로 PR을 만들 때
  1–5번을 똑같이 수행한다")은 결과로는 그대로 지켜진다. 그 폴더를 정리할
  때 문장이 "`pr`을 부르거나 직접"으로 읽히는지 확인해야 한다.
