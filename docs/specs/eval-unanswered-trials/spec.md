# 답하지 못한 시행을 결과로 세지 않는 eval

- 결정: [testing](../../decisions/testing.md). 답하지 못한 시행은 결과가 아니라는 규칙, 시행은 모델 접근 방식과 상관없이 동시에 돈다는 규칙, 한도는 eval이 다루지 않는다는 규칙을 정한다. 거기에 이미 있는 "점수를 매길 출력 전에 실패한 시도는 다시 돈다"와 "이미 채점된 결과는 다시 돌리지 않는다"는 규칙도 이 변경이 기대는 곳이다.
- 결정: [skill-design](../../decisions/skill-design.md). 스킬 변경은 이전 스킬 본문을 기준선으로 한 eval로 증명한다는 규칙이다.
- 용어: [GLOSSARY](../../../GLOSSARY.md). Eval, 셀(Cell), 셀 기록(Cell history), 회귀 묶음의 정의다.

## 문제

`llm-evals`로 eval을 돌리면 실행기는 사례×반복을 4개씩 동시에 돌린다. API 키로 돌리든 구독제로 돌리든 같다. 그런데 `llm-evals` 본문은 API 키를 추천하는 이유로 "사례를 병렬로 돌린다"를 들어서, 구독제는 병렬이 아닌 것처럼 읽힌다.

더 큰 문제는 결과가 오염된다는 점이다. Claude Code CLI(`claude -p --output-format stream-json`)는 API 오류로 끝난 턴도 `subtype: "success"`로 끝내고, `is_error: true`와 `api_error_status`만 덧붙인다. 사용량 한도나 rate limit에 걸린 경우가 여기에 해당한다. `skill-evals/` 아래 실행기 6개는 모두 `subtype`만 보고 오류를 거른다. 그래서 한도에 걸린 시행이 judge까지 가서 fail로 채점된다. pass rate는 실제보다 낮게 나오고, 셀 기록에는 행동이 만든 적 없는 실패가 남는다. 나중에 감사(audit)가 이 거짓 실패를 "뒤집힌 셀"이나 "무언가를 지키는 셀"로 읽게 된다.

이 내용은 Claude Code 2.1.323 바이너리의 출력 스키마에서 읽은 것이다. 실제로 한도에 걸려서 관찰한 것은 아니다.

## 사용자에게 보이는 결과

- eval은 API 키로 돌리든 구독제로 돌리든 시행을 동시에 돌린다. `llm-evals`는 API 키를 추천할 때 "병렬"을 이유로 들지 않는다. 추천 이유는 실제 경로로 돌고 정확히 과금된다는 점으로 남는다.
- 모델이 끝까지 답하지 못한 시행은 채점되지 않는다. 사용량 한도, rate limit, 네트워크 오류, 타임아웃이 모두 해당한다. 이런 시행은 pass rate에도, 셀 기록에도 들어가지 않고 오류로만 남는다.
- 실행이 끝나면 답하지 못한 시행이 몇 개인지 보인다. 같은 명령을 다시 돌리면 그 시행만 다시 돌고, 이미 채점된 시행은 다시 돌지 않는다.
- 한도에 걸려도 eval은 기다리거나 속도를 늦추지 않는다. 걸린 시행이 오류로 남을 뿐이고, 사용자는 한도가 풀린 뒤 다시 돌린다.
- `llm-evals`가 다른 프로젝트에 새 실행기를 만들 때도 같은 규칙을 따른다. 모델의 진입점이 오류로 끝났다고 보고한 시행은 채점하지 않는다.

## 승인된 범위

- `skill-evals/` 아래 실행기 6개(`audit-evals`, `babysit-pr`, `define-product`, `implement`, `llm-evals`, `merge`)가 답하지 못한 시행을 채점하지 않게 한다.
- `llm-evals` 본문을 고친다. API 키 추천 이유에서 병렬을 빼고, 시행을 동시에 돌린다는 점과 답하지 못한 시행은 결과가 아니라는 점을 실행기를 만들 때 지킬 원칙으로 적는다.
- `llm-evals`의 eval 사례를 더한다.
- 플러그인 사용자에게 업데이트가 보이도록 플러그인 버전을 올린다.

## 인수 기준

1. **이 저장소의 실행기.** `skill-evals/` 아래 실행기 6개 각각에서:
   - 모델 진입점이 오류로 끝났다고 보고한 시행(`result`의 `is_error: true`)은 judge를 부르지 않는다. `results.jsonl`에 행이 생기지 않고, `errors.jsonl`에 오류 종류와 함께 남는다.
   - 같은 명령을 다시 돌리면 그 시행만 다시 돌고, `results.jsonl`에 이미 있는 시행은 다시 돌지 않는다.
   - 정상으로 끝난 시행은 지금처럼 채점된다.
   - 셀 기록은 `results.jsonl`의 행에서만 갱신되므로, 답하지 못한 시행은 셀 기록에 들어가지 않는다.
   - 오류로 끝나는 `result`를 흉내 낸 입력으로 확인한다. 실제로 한도에 걸릴 필요는 없다.
2. **`llm-evals` 본문 행동.** `llm-evals` 본문을 따른 에이전트가 새 프로젝트의 실행기를 만들거나 기존 실행기를 쓸 때 위 규칙을 지킨다.
   - 지표: 사례마다 적힌 기대 항목 중 충족한 비율. 루브릭 채점으로 판정한다.
   - 목표: 새 사례 전체에서 90% 이상, 반복 2회. 기준선(바꾸기 전 본문)보다 노이즈 범위 밖으로 높다.
   - 사례 출처: 이 spec의 문제에 나온 실제 상황으로 만든 새 사례를 `skill-evals/llm-evals/evals.json`에 더한다. 최소한 다음을 담는다.
     - 모델 호출이 오류로 끝날 수 있는 프로젝트에 실행기를 만드는 경우. 만든 실행기가 오류로 끝난 시행을 채점하지 않고, 그 판단을 grader의 출력 해석이 아니라 진입점이 보고한 상태로 한다.
     - 실행 결과 일부가 한도 오류로 끝난 뒤 점수를 보고하는 경우. 오류 시행을 fail로 세지 않고, 몇 개가 남았는지와 다시 돌리면 그것만 채워진다는 점을 말한다.
     - 키가 있어서 접근 방식을 묻는 경우. API 키를 추천하되 이유로 병렬을 들지 않는다.
     - 구독제를 고른 사용자가 한도를 아끼려고 하나씩 돌리기를 원하는 경우. 같은 시행은 같은 사용량을 쓰니 순서를 바꿔도 아끼지 못한다고 답한다.
   - 사례가 적어 나누지 않고 전체를 채점하며, 결과는 방향성으로 읽는다.
3. **기존 행동 유지.** `llm-evals`의 기존 eval 사례와 회귀 묶음은 기준선보다 노이즈 범위 밖으로 떨어지지 않는다.
4. `testing.md`의 결정과 `llm-evals` 본문이 서로 어긋나지 않는다.
5. `claude plugin validate . --strict`가 통과한다.

## 확정된 제약과 이유

- **답하지 못한 시행은 결과가 아니다.** 오류로 끊긴 시행은 행동에 대해 아무것도 말해 주지 않는다. 채점하면 행동이 만든 적 없는 fail이 되어 점수와 셀 기록을 함께 틀리게 만든다.
- **판단은 진입점이 보고한 상태로 한다.** grader가 출력 문구를 읽고 "오류 같다"고 판단하게 하지 않는다. 문구는 버전마다 바뀌고, grader가 틀리면 같은 오염이 다시 생긴다.
- **시행은 모델 접근 방식과 상관없이 동시에 돈다.** 시행은 서로 영향을 주지 않고, 각각 같은 비용이나 사용량을 쓴다. 동시에 돌리는 건 걸리는 시간만 바꾼다.
- **한도는 eval이 다루지 않는다.** 기다리기, 속도 늦추기, 리셋 시각에 맞춰 멈추기는 넣지 않는다. 짧은 한도는 CLI가 스스로 재시도하고, 빠진 시행은 다시 돌리면 채워진다. 그래서 실행기마다 장치를 더할 이유가 없다.

## 가정

- 기본 동시 실행 수 4는 그대로 둔다. 한도에 걸리지 않을 만큼 빠른 값으로 충분하다고 본다. 바꿀 수 있는 가정이다.
- 인수 기준 2의 목표(90%, 반복 2회)는 바로 앞의 `eval-result-reuse` spec과 같은 기준을 가져왔다. 바꿀 수 있는 가정이다.
- 오류로 끝난 `result`의 모양은 Claude Code 2.1.323 바이너리의 스키마에서 읽었다. 실제 한도에서도 같은 모양으로 오는지는 관찰하지 않았다.
- 판정에 쓰는 CLI 호출(judge)이 오류로 끝나는 경우는 이미 `judge` 오류로 따로 남는다고 본다. 구현할 때 확인한다.

## 범위 밖

- 한도 대응 장치: 기다렸다 재시도하기, worker 전체를 멈추기, 리셋 시각을 알려 주고 멈추기. 위의 확정된 제약 때문이다.
- 동시 실행 수를 올리는 것. 한도에 더 자주 걸리는데, 그 대응은 이번 범위 밖이다.
- 이미 쌓인 셀 기록에서 과거의 거짓 실패를 찾아 지우는 일. 어느 실패가 한도 때문이었는지 지금 기록으로는 가릴 수 없다.

## 미뤄 둔 것

- 실행기 안의 한도 대응. 다시 여는 조건: 한도에 걸려 멈춘 실행이 남긴 빈 시행이 많아서, 손으로 다시 돌리는 비용이 실행기 안에서 기다리는 비용보다 커질 때. `testing.md`의 Reconsider when에 같은 조건이 적혀 있다.

## 남은 위험

- CLI가 오류 상태를 보고하는 방식이 버전마다 바뀌면 이 판정이 다시 조용히 새어 나갈 수 있다. 실행기가 기대하는 필드가 없을 때 정상으로 치지 않고 오류로 남기는지가 이 위험을 줄인다.
- 구독 한도에 걸렸을 때 CLI가 곧바로 끝나는지, 리셋까지 기다리는지는 확인하지 않았다. 기다린다면 시행이 타임아웃으로 끝날 텐데, 그 경우도 답하지 못한 시행으로 처리되니 결과는 오염되지 않는다.
