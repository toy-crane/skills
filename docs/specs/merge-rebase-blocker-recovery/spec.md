# Rebase 차단 후 PR 머지 완료

## 문제

`merge`가 GitHub의 rebase 실패에 막히면 PR이 열린 채로 남을 수 있다. 사용자는 같은 머지 요청 안에서 브랜치 갱신, 새 커밋의 CI 완료 확인, 실제 머지까지 이어지기를 기대한다.

## 사용자에게 보이는 결과

- GitHub가 자동 rebase에 실패해 머지를 거부해도, 해결 가능한 경우 `merge`가 PR을 갱신하고 CI가 완료된 뒤 머지를 끝낸다.
- 충돌의 의도를 판단할 근거가 없거나 새 커밋의 검증이 실패하면 PR과 작업을 보존하고, 막힌 이유와 필요한 다음 결정을 알린다.
- 완료 보고는 GitHub에서 확인한 `MERGED` 상태를 근거로 한다.

## 승인된 범위

- 기존 `merge` 요청의 연장으로, GitHub가 자동 rebase에 실패해 막힌 PR을 복구한다.
- PR 브랜치의 갱신 후 새 head에 대한 CI 완료 및 성공과 GitHub가 실제 요구하는 체크·리뷰를 확인한다.
- 이 저장소의 `codex-review-gate` 워크플로는 유지한다. `merge`가 모든 저장소 또는 모든 push에 사람의 `@codex review` 요청을 자체 요구하지 않는다.
- 차단 없이 머지 가능한 PR은 기존 머지 흐름을 따른다.

## 수용 기준

1. GitHub가 PR의 자동 rebase 실패를 보고하면, `merge`가 요청된 base의 최신 상태를 확인하고 기존 PR을 갱신한다. PR에 속하지 않은 로컬 작업과 다른 사람의 원격 변경은 보존된다.
2. 갱신으로 PR head가 바뀌면, 이전 head의 CI 결과로 머지하지 않는다. 새 head의 관련 CI가 끝나 성공하고 GitHub의 필수 체크·리뷰 조건도 충족된 뒤 머지를 시도한다.
3. CI 실패, 필수 체크·리뷰 미충족, 의도가 불분명한 충돌, 브랜치 갱신 권한 부족, 예상하지 못한 원격 변경이 있으면 우회하거나 덮어쓰지 않는다. PR을 유지하고 확인된 차단 원인을 보고한다.
4. 대기 중 head나 base가 다시 바뀌면 이전 판단을 재사용하지 않고 현재 PR 상태를 다시 확인한다.
5. 머지 명령의 출력만으로 완료를 선언하지 않는다. GitHub의 `MERGED` 상태를 확인한 뒤에만 기존 안전한 정리를 진행한다.

## 확정된 제약과 이유

- [Skill design](../../decisions/skill-design.md): Git 전달 스킬은 요청된 결과, 보존할 상태, 완료 증거를 명시하고 일반적인 Git 명령 선택은 실행 상황에 맡긴다. `merge`는 단독 설치에서도 복구 결과를 책임진다.
- 새 head의 검증을 기다린다. GitHub의 필수 체크는 이전 커밋의 성공으로 충족되지 않으며, rebase 후에는 head가 달라질 수 있다. [GitHub 필수 체크 안내](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)
- GitHub가 자동 rebase를 안전하게 끝내지 못하면 로컬에서 충돌을 해결하고 갱신된 브랜치를 게시할 수 있다. [GitHub PR 머지 안내](https://docs.github.com/en/pull-requests/reference/pull-request-merges)
- 사람의 `@codex review` 요청은 이 복구 흐름의 보편 조건이 아니다. 저장소가 실제로 요구하는 리뷰 게이트가 미충족이면 그 상태를 차단 원인으로 보고한다.

## 가정 (수정 가능)

- 차단되지 않은 PR까지 예방적으로 rebase하지 않는다.
- 관련 CI가 없는 저장소에서는 존재하지 않는 실행을 기다리지 않고 GitHub의 실제 머지 조건을 확인한다.

## 범위 밖

- `codex-review-gate`의 현재 head 검증 방식이나 저장소의 GitHub 규칙을 바꾸는 일. 이번 변경은 `merge`의 차단 복구 동작에 한정한다.
- 실패한 CI를 무시하거나 관리자 권한으로 머지 조건을 우회하는 일. 검증 실패를 해결하는 것은 별도의 변경이다.

## 보류한 점

- GitHub가 자동 rebase 실패를 보고하지 않고 최신 base만 요구하는 PR까지 이 복구 동작에 포함할지는 확정하지 않았다. 그 결정을 내리기 전에는 기존 `merge` 흐름으로 판단하고, 최신화가 필요해 끝내지 못하면 차단 이유를 보고한다.

## 남은 위험

- 저장소에 따라 rebase 후 리뷰 승인이나 외부 검증이 다시 필요할 수 있다. 사람이 수행해야 하는 조건이 남으면 자동 머지 완료까지 이어질 수 없다.
- 최신 base 요구만으로 막힌 PR은 이번 범위에서 자동 복구되지 않을 수 있다.
- GitHub 상태가 대기 중 계속 변하면 같은 PR을 재평가해야 하며, 안정된 head와 검증을 얻기 전에는 머지를 완료할 수 없다.
