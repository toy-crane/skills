# 구현 전에 필요한 셋팅을 먼저 알리기

[pipeline](../../decisions/pipeline.md)의 "Setup that lives outside the
repository" 항목이 이 작업의 결정 계약이다. 섹션 이름, 한 줄 형식, 멈추는
시점을 그 계약이 정한다.

## 문제

계정 생성, 키 발급, 콘솔이나 DNS 설정처럼 저장소 밖에서 해야 하는 셋팅을
다루는 단계가 없다.

- `shape-idea`의 spec에는 이런 셋팅을 적을 자리가 없다. 서비스를 고르면
  `add-stack-context`를 부르지만, 그 스킬은 에이전트 문서만 다룬다.
- `split-into-tasks`의 Blockers는 태스크끼리의 의존만 적는다.
- `implement`는 코드를 다 쓴 뒤 런타임 검증에서 처음 막히고, 그때 "실패한
  조건과 prerequisite"를 적은 채 미완료로 끝난다.

그래서 사람은 구현이 끝날 무렵에야 해야 할 셋팅을 알게 된다.

## 사용자에게 보이는 결과

- shaping이 끝날 때, 이 작업에 필요한 셋팅 목록을 함께 받는다. 구현 전에
  미리 처리할 수 있다.
- 구현을 시작하면 에이전트가 할 수 있는 셋팅은 먼저 해 둔다. 남은 것이
  있으면 코드를 건드리기 전에 그 목록을 한 번에 받는다.
- 셋팅을 마쳤다고 알리면, 에이전트가 완료 조건을 확인한 뒤 구현을 시작한다.
- 셋팅이 필요 없는 작업은 지금과 똑같이 진행된다.

## 승인된 범위

- `shape-idea`: spec에 `## Setup before implementation` 섹션을 항상 쓴다.
  필요한 셋팅이 있으면 한 줄씩, 없으면 `None.`을 적는다. 마무리 요약에도
  이 목록을 보여 준다.
- `implement`: 첫 소스 수정 전에 이 섹션을 읽고, 할 수 있는 항목은 직접
  처리한 뒤 모든 완료 조건을 확인한다. 남은 항목이 있으면 전부 보고하고
  소스를 건드리지 않은 채 멈춘다.
- `build-prototype`: 승인된 화면으로 spec을 직접 쓸 때도 같은 섹션을
  쓴다. 이 경로로 만든 spec도 `implement`의 사전 확인을 받아야 하기 때문이다.
- `implement`는 키 같은 비밀값을 묻거나 채팅으로 받거나 출력하지 않는다.
  사람이 제품이 읽는 자리에 넣고, 에이전트는 효과나 사람의 확인으로 판단한다.
- `babysit-specs`: spec을 다시 쓸 때 이 섹션을 다른 칸과 함께 남긴다.
  빠지면 `implement`가 확인 없이 구현을 시작하기 때문이다.
- 두 스킬의 평가(evals)에 위 동작을 확인하는 사례를 더한다.

## 섹션 형식

한 줄에 무엇이 필요한지, 어느 결과물에 필요한지, 끝났음을 보여 주는
조건을 적는다. 담당자나 단계별 할 일은 적지 않는다. 완료 조건은 이 spec이
만들 코드 없이도 확인할 수 있어야 한다. 콘솔 상태, 앱 밖에서 키로 직접
호출한 API 결과, DNS 조회 같은 것이다.

```markdown
## Setup before implementation

- Resend 발송 도메인 인증 (비밀번호 재설정 메일): 콘솔에서 도메인이 Verified
- Resend API 키 (같은 메일): 키로 API를 직접 호출하면 성공
```

## 인수 조건

1. 외부 서비스가 필요한 아이디어를 shaping하면, spec에 위 형식의 섹션이
   생기고 마무리 요약에 같은 항목이 나온다.
2. 외부 셋팅이 필요 없는 아이디어를 shaping하면, 섹션에 `None.`이 적힌다.
3. 섹션 어디에도 키, 비밀번호, 토큰 값이 없다.
4. 완료 조건을 만족하지 않는 항목이 있는 spec으로 `implement`를 실행하면,
   소스 변경 없이 남은 항목 전체를 한 번에 보고하고 멈춘다.
5. 에이전트가 직접 할 수 있는 항목은 보고 전에 처리되어 있고, 보고에는
   사람만 할 수 있는 부분만 남는다.
6. 사용자가 끝냈다고 하면 `implement`가 완료 조건을 다시 확인하고, 모두
   통과해야 구현을 시작한다.
7. 섹션이 없는 기존 spec은 지금과 똑같이 구현된다.

## 정해진 제약과 이유

- **목록은 shaping에서 적는다.** 셋팅이 필요하다는 사실은 서비스를 고르는
  때 이미 드러난다. 구현 시작 때 뽑아내면 사람이 너무 늦게 알게 된다.
- **남은 항목이 있으면 전체를 멈춘다.** 셋팅과 무관한 결과물을 먼저 만드는
  방식은 기다림과 구현이 섞여 흐름이 복잡해진다. 태스크가 없는 spec은
  결과물이 하나라 이득도 없다.
- **담당을 나누지 않는다.** 에이전트는 할 수 있는 데까지 하고, 나머지가
  사람 몫이다. 누가 할지는 실행 시점의 도구와 권한이 정하므로 spec에 미리
  적을 필요가 없다.
- **코드 쪽 이름은 적지 않는다.** 환경 변수 이름이나 설정 파일 위치는
  구현 세부라서 `implement`가 정한다. spec은 코드 구조를 예측하지 않는다.
- **섹션 제목은 영어로 고정한다.** `Blocked by:` 줄과 같은 이유로,
  `implement`가 찾아 읽는 표지다.
- **셋팅은 shaping 중에 하지 않는다.** shaping은 정렬만 하고 적용은
  구현의 몫이라는 `shape-idea`의 경계를 따른다.

## 가정 (바꿀 수 있음)

- 완료 확인은 완료 조건으로만 한다. spec에는 완료 표시를 하지 않는다.
- 에이전트가 완료 조건을 직접 볼 수 없으면(로그인 뒤 콘솔 화면 등),
  가능한 도구로 확인하고, 그래도 안 되면 사용자 확인을 받는다.
- `split-into-tasks`는 바꾸지 않는다. 태스크는 spec을 통해 섹션을 그대로
  따르고, 이미 끝난 항목은 완료 조건을 통과할 뿐이다.

## 건드리지 않는 것

- `add-stack-context`: 에이전트 문서만 다루는 지금 역할을 유지한다.
- 런타임 검증에서 막혔을 때 실패 조건과 prerequisite를 적는 `implement`의
  기존 동작: 미리 알 수 없었던 셋팅을 위한 마지막 안전망으로 남긴다.

## 남은 위험

- shaping 때 놓친 셋팅은 여전히 런타임 검증에서 늦게 드러난다. 그 경우는
  지금과 같다.
- 섹션이 없는 기존 spec은 이 이득을 받지 못한다.
