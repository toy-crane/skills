# 스펙 폴더와 트래커 이슈를 `Issue:` 줄로 잇기

## 문제

지금은 사람이 쓴 이슈 없이 시작한 스펙을 `merge`가 main에 합친 뒤
`spec:<slug> <제목>` 이슈(generated pointer)로 만든다. 그 시점에는 번호를
spec.md에 다시 적을 수 없어서 제목에 열쇠를 넣었다. 그래서 이슈를 찾으려면
전체 목록을 제목으로 대조하거나 검색해야 한다. Linear 검색은 뜻으로 찾기
때문에 정확한 제목이 나오지 않을 수 있다. flyn에서는 FLY-96부터 FLY-108까지
Done 상태인 스펙 이슈와 제목이 같은 중복 13개가 생겼다. 사용자는 이슈 제목의
`spec:` 접두사도 원하지 않는다.

2026-10-02 flyn 저장소의 shape 세션에서 사용자가 아래 결정을 확정했다.

## 사용자에게 보이는 결과

- 트래커를 쓰는 프로젝트에서 스펙 폴더를 담은 PR을 열면, 그 스펙의 이슈가
  PR보다 먼저 생기고 spec.md에 `Issue: <tracker>:<id>` 줄이 커밋된다. 이슈
  제목은 스펙 제목 그대로이며 접두사가 없다.
- 이슈는 언제나 그 줄의 번호로 바로 찾는다. 제목 검색이나 전체 목록 대조로
  찾지 않으므로, 검색 결과에 따라 같은 스펙의 이슈가 또 생기는 일이 없다.
- 사람이 쓴 이슈에서 출발한 스펙은 그 이슈 하나를 계속 쓴다. 에이전트가 만든
  이슈도 만든 뒤에는 사람이 쓴 이슈와 똑같이 다룬다.
- 트래커가 없는 프로젝트에서는 이슈도 `Issue:` 줄도 생기지 않고, 모든 Skill이
  트래커 단계를 건너뛴다.

## 승인된 범위

1. `spec:<slug>` 제목 열쇠와 "generated pointer" 개념을 없앤다. 이슈 제목에
   접두사를 붙이지 않고, 종류를 표시하는 `spec` 라벨도 만들지 않는다. 스펙
   이슈는 리뷰 중이거나 구현 대기 상태라서 지금 규칙만으로 일반 분류에서
   빠진다.
2. 스펙 폴더 하나는 트래커 이슈 하나와 이어진다. 연결은 spec.md의
   `Issue: <tracker>:<id>` 줄 하나다(예: `Issue: linear:FLY-145`,
   `Issue: github:#12`). 이 줄이 `Source-Issue:`를 대신한다. 출처가 아니라
   "이 스펙의 이슈"이기 때문에 이름을 바꾼다. PR 본문의 표식도
   `Issue: <tracker>:<id>`로 바꾸고, 스펙 없이 바로 고치는 PR에도 같은 줄을
   쓴다.
3. 이슈는 `pr`이 만든다. 스펙 폴더를 담은 PR을 열기 직전에 `Issue:` 줄이
   없는 spec.md가 있으면 스펙 제목으로 이슈를 만들고, 그 줄을 spec.md에 적어
   같은 브랜치에 커밋한 뒤 PR을 연다. `shape-idea`에서 만들지 않는 이유는
   둘이다. 버려지는 shape가 이슈를 남기지 않아야 하고, shape-idea,
   triage-issues, 스펙과 구현을 한 PR에 담는 경우까지 모든 경로가 PR을
   지나기 때문이다.
4. `shape-idea`처럼 이슈에서 출발한 흐름은 기존 이슈 번호를 알 때만 `Issue:`
   줄을 적는다. 번호는 사람이 주거나, 이슈를 넘긴 `triage-issues`가 준다. 사람이 번호를 말하지 않았을 때 제목 검색으로
   기존 이슈를 찾아 중복을 막지 않는다. 그 검색이 지금의 중복을 만들었다.
   그래도 생긴 중복은 사람이 트래커에서 정리한다.
5. 모든 조회는 `Issue:`에 적힌 번호로 직접 한다. 제목 대조로 목록을 만드는
   조회(`List managed issues` 등)는 없앤다.
6. 스펙 PR이 합쳐지지 않고 닫히면 그 이슈를 어떻게 할지는 사람이 정한다.
   (2026-10-02 [issue-skill-roles](../issue-skill-roles/spec.md)에서 바꿨다.
   이전에는 triage가 Backlog로 돌렸다.)
7. 옛 `Source-Issue` 이름은 호환하지 않는다. 이미 합친 PR 본문의 옛 표식도
   읽지 않는다. 각 프로젝트는 Skill을 갱신할 때 활성 스펙 폴더의 줄 이름을
   직접 바꾼다.
8. 트래커에 묶이지 않는 범용 구조여야 한다. Linear, GitHub Issues, 그 밖의
   트래커에서 똑같이 동작하고, 트래커가 없는 프로젝트에서도 동작한다. Skill
   본문의 필드 이름과 흐름에는 특정 트래커 이름을 넣지 않는다. 이슈 생성
   도구, 상태 이름, 닫는 문구 같은 트래커별 세부 사항은 `setup-issue-tracker`
   템플릿과 그것으로 만든 프로젝트의 `docs/issue-tracker.md`에만 둔다.

## 수용 기준

1. 트래커가 설정된 저장소에서 `pr`은 PR을 만들기 전에 PR이 추가하거나 바꾼
   스펙 폴더와 커밋의 `Spec-Folder` 트레일러가 가리키는 폴더 가운데 head에
   아직 있는 폴더를 모은다. 그중 spec.md에 `Issue:` 줄이 없는 폴더마다 이슈를
   하나씩 만든다. 삭제된 폴더는 건너뛴다.
2. 새 이슈의 제목은 spec.md의 첫 제목이고 접두사가 없다. 본문은 경계가 표시된
   스펙 구역 하나이며, 규약의 리뷰 신호를 단 채로 만든다. 그래서 PR이 이슈에
   연결되기 전에도 일반 분류가 그 이슈를 가져가지 않는다.
3. `pr`은 규약의 ID 형식으로 `Issue: <tracker>:<id>` 줄을 spec.md에 적어 같은
   브랜치에 커밋하고, PR 본문에도 같은 줄을 넣은 뒤 PR을 연다.
4. 이슈를 만들었는데 줄을 커밋하지 못하면 만든 이슈의 ID를 보고한다. 다시
   실행할 때 그 ID를 쓰고 이슈를 또 만들지 않는다.
5. 이미 `Issue:` 줄이 있는 폴더는 이슈를 만들지 않고 그 번호를 쓴다. 기존
   PR을 다시 쓸 때도 같다.
6. `merge`는 스스로 PR을 만들 때 1–5번을 똑같이 수행한다.
7. 합친 뒤 `merge`는 합친 범위에서 바뀐 스펙 폴더의 이슈를 `Issue:` 번호로
   찾아 스펙 구역과 선행 관계만 갱신한다. 이슈 제목과 사람이 쓴 본문은 두고,
   새 이슈를 만들지 않으며, 폴더 삭제만으로 이슈를 닫지 않는다.
8. 구현을 실제로 전달한 PR이 합쳐지면 그 이슈를 닫고, 스펙만 담은 PR이
   합쳐지면 이슈를 연 채 구현 대기 상태로 옮긴다.
9. `implement`는 `Issue:` 번호로 이슈를 찾아 클레임한다. 줄이 없는 폴더는
   클레임 없이 진행하고, 그 폴더를 담은 PR을 열 때 `pr`이 이슈를 만든다.
10. `maintain-project-context`는 default branch의 각 스펙 폴더를 `Issue:` 번호로
    찾아 스펙 구역과 선행 관계를 맞춘다. 줄이 없는 폴더는 이슈를 만들지 않고
    보고한다. 관리 이슈 목록, 고아 이슈 닫기, 중복 제목 감지는 하지 않는다.
11. `triage-issues`는 `spec:<slug>` 제목으로 이슈를 거르지 않는다. 진행 중이거나
    열린 PR이 연결된 이슈, default branch의 스펙 폴더가 `Issue:`로 가리키는
    이슈를 거른다. 이슈에서 출발한 스펙과 바로 고치는 PR 본문은 원래 이슈 번호로
    `Issue:` 줄을 적는다.
12. `shape-idea`는 트래커가 설정돼 있고 사용자가 기존 이슈 번호를 말했을 때만
    `Issue:` 줄을 적는다. 제목으로 기존 이슈를 찾지 않는다.
13. 트래커 섹션이 없는 저장소에서는 어떤 Skill도 이슈를 만들거나 `Issue:` 줄을
    쓰지 않으며, PR 본문과 흐름은 트래커 단계 없이 그대로다.
14. `setup-issue-tracker`가 고를 트래커를 나열하는 줄을 빼면, 바뀐 SKILL.md
    본문에 특정 트래커 이름이 없다. 트래커별 도구, 상태, 닫는 문구는 세
    템플릿에만 있다.
15. `setup-issue-tracker`를 다시 실행하면 옛 제목 열쇠와 `List managed issues`를
    `Issue:` 줄과 번호 조회로 바꾸고, 활성 스펙 폴더의 `Source-Issue:` 줄 이름은
    사용자가 직접 바꾸도록 알린다.

## 확정된 제약과 이유

- [pipeline](../../decisions/pipeline.md)의 트래커 결정과
  [pr-descriptions](../../decisions/pr-descriptions.md)의 PR 본문 결정을 이
  스펙에 맞게 고친다.
- `merge`도 `pr`을 부르지 않고 직접 PR을 만든다. Skill은 다른 Skill의 본문을
  가정하지 않으므로, PR 직전 이슈 생성 단계를 `merge`에도 그대로 적는다.
- 에이전트가 만든 이슈는 만든 뒤 사람이 쓴 이슈와 똑같이 다룬다. 스펙 제목이
  나중에 바뀌어도 이슈 제목은 따라 바꾸지 않고, 스펙 구역만 갱신한다. 이슈를
  처리하는 규칙이 하나만 남는다.
- `Spec-Folder:` 커밋 트레일러는 그대로 둔다. 이름을 바꾸는 범위는
  `Source-Issue`뿐이다.
- 스펙 구역을 고치는 방법은 각 Skill 본문에 글로 적는다. `triage-issues`의
  보조 스크립트에 기대지 않는다.

## 가정 (수정 가능)

- `merge`가 실패한 닫기나 구현 대기 전환을 다시 시도할 때 합친 PR 본문의
  `Issue:` 표식을 찾는 방법은 남긴다. 제목 대조가 아니라 번호가 적힌 표식이기
  때문이다.
- 합치지 않고 닫힌 스펙 PR의 이슈는 사람이 정리한다. 새로운 정리 단계를 더하지
  않는다. (2026-10-02에 triage가 새 이슈만 판단하게 되면서 바꿨다.)
- 이미 출하한 `issue-tracker-setup`, `triage-issues` 스펙은 이번 변경과 어긋나는
  줄만 고치고, 날짜가 적힌 승인 기록은 두고 폴더도 지우지 않는다.

## 범위 밖

- flyn의 이주 작업(기존 스펙 폴더의 줄 이름 변경, 중복 이슈 정리)은 flyn에서
  따로 한다.
- 옛 `spec:<slug>` 이슈를 새 방식으로 바꾸거나 닫는 자동 정리는 하지 않는다.

## 남은 위험

- `Issue:` 줄이 없는 채로 main에 있는 스펙 폴더는 구현 PR을 열기 전까지 이슈가
  없어서, 그동안은 병렬 구현 클레임으로 보호받지 못한다.
- 사람이 번호를 말하지 않으면 기존 이슈와 새 이슈가 중복될 수 있다. 사용자는
  이 중복을 트래커에서 직접 정리하기로 했다.
