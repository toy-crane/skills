# `merge`가 리베이스 결과를 검증하고 머지 순서를 지키기

- 결정: [skill-design](../../decisions/skill-design.md). Git 전달 스킬이 적어야 할 결과·권한·보존·증거와, `merge`가 `pull`과 `pr`을 조합하는 방식이다.
- 결정: [pipeline](../../decisions/pipeline.md). spec 폴더의 `Blocked by:` 줄이 무엇을 뜻하는지다.
- 관련 spec: [merge-auto-merge](../merge-auto-merge/spec.md). head나 base가 바뀌면 검증을 다시 하는 기존 규칙이다.
- 참고 자료: t3dotgg/tstack의 `modernize`, `babysit-pr` (MIT). `git range-diff` 비교와 "마지막 통과 뒤 들어온 base 커밋이 이 PR의 파일을 건드리면 다시 확인한다"는 규칙을 여기서 가져온다.

## 문제

PR 여러 개가 동시에 열려 있으면 하나가 먼저 머지되고 나머지는 리베이스해야 한다. `resolve-follow-ups`는 PR을 최대 셋까지 한꺼번에 만들고, 워크트리 여러 개에서 `implement`를 나란히 돌리기도 해서 자주 생기는 상황이다.

지금 `merge`는 줄 충돌만 다룬다. 리베이스 뒤 새 head로 CI를 다시 돌리지만, 두 가지는 확인하지 않는다.

- 충돌을 풀다가 이 PR의 변경 일부가 빠지거나, base에 이미 들어간 코드가 중복으로 들어간 경우. 최종 diff만 봐서는 티가 나지 않는다.
- 파일은 달라 충돌이 없는데, 먼저 들어간 변경이 바꾼 동작을 이 PR이 예전 동작으로 가정하는 경우. 테스트가 그 가정을 다루지 않으면 CI도 통과한다.

어느 PR을 먼저 머지할지에 대한 규칙도 없다.

## 사용자에게 보이는 결과

- `merge`가 PR을 리베이스한 뒤에는, 리베이스 전후 커밋을 하나씩 짝지어 이 PR의 변경이 온전히 넘어왔는지 확인한다.
- 이 PR이 갈라진 뒤 base에 들어온 커밋이 이 PR이 건드린 파일이나 동작과 겹치면, CI 통과만 믿지 않고 영향받은 동작을 다시 검증한다.
- 머지 순서는 spec 폴더의 `Blocked by:`를 먼저 따르고, 없으면 먼저 준비된 PR이 먼저 들어간다.

## 승인된 범위

- `merge` 본문에 리베이스 뒤 검증과 순서 규칙을 넣는다.
- `merge` 평가 사례를 더한다.
- 플러그인 버전을 올린다.

## 수용 기준

1. `merge` 본문은 다음을 담는다.
   - PR 브랜치를 리베이스한 뒤 publish하기 전에, 리베이스 전후 커밋 묶음을 `git range-diff`로 비교한다. 의도한 변경이 사라졌거나 base에 이미 있는 변경이 다시 들어왔으면 publish하지 않고 바로잡는다. 의도가 불분명하면 PR을 열어 둔 채 막힌 이유를 보고한다.
   - 이 PR이 갈라진 지점 이후 base에 들어온 커밋 중 이 PR이 건드린 파일이나 동작과 겹치는 것을 찾는다. 겹치면 이 PR의 spec 수용 기준이나 PR 본문이 말하는 동작 중 영향받는 것을 현재 head에서 다시 검증한다. 겹치지 않으면 기존 검증 규칙을 그대로 따른다.
   - 머지 직전에 base를 다시 받아, 마지막으로 검증이 통과한 뒤 base에 들어온 커밋이 이 PR의 파일을 건드렸으면 머지하지 않고 위 두 단계를 다시 거친다.
   - 이 PR의 spec 폴더에 `Blocked by:` 줄이 있고 그 폴더의 작업이 아직 base에 없으면 머지하지 않고 그 사실을 보고한다. `Blocked by:`가 없는 PR끼리는 먼저 머지 조건을 충족한 쪽이 먼저 들어가고, 나머지는 리베이스 뒤 위 검증을 거친다.
2. 위 동작을 eval로 증명한다.
   - 지표: 사례별 기대 항목 충족률. `skill-evals/merge/evals.json`의 `expectations` 형식이다.
   - 목표: 새로 더한 사례의 기대 항목을 보지 않은 사례에서 모든 반복에 걸쳐 전부 충족하고, `merge`의 기존 사례 충족률이 이번 변경 직전 본문의 기준선 아래로 떨어지지 않는다.
   - 사례 출처: 임시 Git 저장소로 만든 고정 상황이다. 최소한 다음을 담는다. 충돌 해결 중 이 PR의 변경 하나가 빠지는 리베이스, base에 이미 있는 변경이 다시 들어오는 리베이스, 파일은 다르지만 먼저 들어간 커밋이 이 PR이 기대는 기본값을 바꾼 경우, 겹치는 커밋이 없는 리베이스, 검증 뒤 base에 겹치는 커밋이 새로 들어온 경우, `Blocked by:` 대상이 아직 base에 없는 경우.
3. 플러그인 버전이 `main`보다 올라가 있고 `claude plugin validate . --strict`가 통과한다.

## 확정된 제약과 이유

- 순서 규칙은 `merge` 안에 둔다. 서로 의존하는 일은 shaping에서 이미 `Blocked by:`로 묶이므로, 남는 건 서로 무관한 PR끼리의 순서뿐이다. 무관한 PR은 먼저 준비된 쪽이 먼저 들어가도 된다.
- 다시 검증하는 범위는 겹치는 동작으로 한정한다. 리베이스할 때마다 전체 검증을 반복하지 않는다.

## 가정 (수정 가능)

- "겹친다"는 같은 파일을 건드렸거나, base 쪽 커밋이 이 PR이 호출하거나 기대는 동작을 바꾼 경우다. 에이전트가 diff를 읽고 판단한다.

## 범위 밖

- 열린 PR 전체를 보고 머지 순서를 정해 차례로 리베이스하고 머지하는 조율 스킬. 나중에 다시 다룬다.
- 오래된 PR이 아직 필요한지 판단하는 처분 규칙(MODERNIZE, REWORK, CLOSE).
- `pull` 본문 수정.

## 보류한 점

- PR 조율 스킬. 여러 PR이 쌓여 머지 순서나 리베이스가 반복해서 문제가 될 때 다시 연다.

## 남은 위험

- "겹치는 동작" 판단이 약하면 의미 충돌을 놓친다. 같은 파일을 건드린 경우는 기계적으로 잡히지만, 다른 파일을 통한 동작 변화는 에이전트의 diff 읽기에 달려 있다.
- 겹치는 커밋이 많은 저장소에서는 머지 전 재검증이 길어진다.
