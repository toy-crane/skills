# `merge`의 worktree 정리를 프로젝트 선언으로

## 문제

`merge`의 정리 단계는 동봉 스크립트로 Portless 경로에 등록된 프로세스만 멈춘다. `portless`가 없는 프로젝트에서는 아무것도 하지 않는다. 범용 Skill 안에 특정 프로젝트의 도구 가정이 섞인 것이다. 서버를 띄우는 `implement`는 "프로젝트가 지원하는 개발 방식"이라고만 적는다.

그 결과 flyn에서는 PR이 병합된 뒤에도 worktree가 API·Metro 프로세스, Android 에뮬레이터, worktree 전용 Supabase 스택을 계속 잡고 있었다. 반대로 작업 폴더만 보고 프로세스를 멈추면 에이전트가 자기 세션이나 다른 세션을 끊는다. Claude 데스크톱 세션의 프로세스는 작업 폴더가 그 worktree 안에 있기 때문이다.

## 사용자에게 보이는 결과

- 프로젝트가 `AGENTS.md`나 `CLAUDE.md`의 `## Worktree cleanup` 섹션에 정리 명령을 적어 두면, `merge`는 병합된 worktree를 정리할 때 그 폴더 안에서 명령을 실행해 개발 자원을 푼다.
- 섹션이 없는 프로젝트에서는 `merge`가 어떤 프로세스도 멈추지 않는다.
- `merge`를 실행한 세션이 그 worktree 안에 있으면, 정리 명령을 실행한 뒤 폴더를 남기고 HEAD를 병합된 base에 분리하고 브랜치만 지운다. 세션은 끊기지 않는다.
- 다른 세션이나 터미널이 쓰고 있는 worktree, 또는 지우기 직전에도 프로세스가 남은 폴더는 지우지 않고 무엇이 남았는지 알린다.
- Codex 앱이 관리하는 worktree는 Codex에 맡기고, 남겨 둔 이유를 알린다.
- Portless 전용 스크립트와 그 평가 사례는 사라진다.

## 승인된 범위

- `merge`의 병합 후 정리 단계를 [worktree-cleanup](../../decisions/worktree-cleanup.md) 결정 문서의 절차로 바꾼다. 그 문서가 정리 섹션의 이름과 형식, 현재 세션 판별, 붙은 프로세스와 남은 프로세스의 구분, Codex worktree 처리, 브랜치 삭제 조건을 정한다. 이 spec은 그 규칙을 다시 적지 않는다.
- 같은 절차를 뒤따르는 `clean-worktrees`도 쓴다. 두 Skill이 "안전하게 지우기"를 따로 정의하지 않고, 각 Skill은 혼자 설치돼도 이 절차를 갖는다.
- `merge`의 나머지 흐름(PR 준비, 병합 방식 선택, auto merge, 원격 `MERGED` 확인, 이슈 트래커 동기화, base checkout 갱신)은 바꾸지 않는다.

## 수용 기준

1. 정리 섹션이 있고 현재 세션이 worktree 밖에 있으며 붙은 프로세스가 없으면, 명령이 적힌 순서대로 그 폴더 안에서 실행된다. 이어서 worktree가 제거되고 브랜치가 지워진다.
2. 명령 하나가 실패하면 뒤의 명령은 실행되지 않는다. 폴더와 브랜치는 남고, 보고에 실패한 명령이 나온다.
3. 정리 섹션이 없으면 어떤 프로세스도 멈추지 않는다. 부모가 PID 1인 남은 프로세스가 폴더 안에서 돌고 있으면 폴더를 남기고 그 PID와 명령을 보고한다.
4. 남은 프로세스만 있고 정리 섹션이 있으면 명령을 실행한다. 지우기 직전 확인에서 프로세스가 사라졌으면 worktree를 지우고, 남아 있으면 폴더를 남기고 보고한다.
5. 현재 세션이 worktree 안에서 실행 중이면 정리 명령을 실행하고, 폴더를 남긴 채 HEAD를 병합된 원격 base에 분리하고 브랜치만 지운다.
6. 띄운 쪽이 살아 있는 프로세스(다른 에이전트 세션, 사용자의 터미널, 그 프로세스들이 띄운 서버)가 폴더 안에 있으면, 정리 명령도 실행하지 않고 worktree를 그대로 두고 보고한다.
7. worktree가 Codex worktree 루트 아래에 있고 현재 세션이 그 안에 없으면, 명령 실행과 제거 없이 Codex가 관리한다고 보고한다.
8. 로컬 브랜치의 끝이 병합된 PR의 head와 다르고 base에도 포함되지 않으면 브랜치를 지우지 않고 보고한다.
9. 커밋하지 않은 변경이나 잠금이 있는 worktree는 강제로 지우지 않고 남겨 보고한다.
10. 정리 결과는 이미 확인한 병합 결과와 따로 보고한다. 정리가 막혀도 병합 완료 보고는 바뀌지 않는다.
11. 저장소에 Portless 전용 스크립트, 그 테스트, Portless 평가 사례가 남지 않는다. 범용 Skill의 지침이 특정 프로세스 관리 도구를 기본값으로 언급하지 않는다.
12. 구현 검증은 이 저장소의 평가와 스크래치 Git 저장소로 1–9번을 재현한다. 현재 세션이 안에 있는 경우는 확인 명령의 조상 프로세스가 그 폴더 안에서 실행 중인 상황으로 재현한다.

## 확정된 제약과 이유

- [worktree-cleanup](../../decisions/worktree-cleanup.md): 정리 섹션, 현재 세션 판별, 붙음과 남음의 구분, Codex worktree, 브랜치 삭제, 공통 절차의 사본 관리가 모두 여기서 정해진다. 사용자가 이 세션에서 고른 세 가지(띄운 쪽이 살아 있으면 붙은 것으로 본다, 폴더를 남길 때도 정리 명령을 실행한다, Codex worktree는 Codex에 맡긴다)도 그 문서에 있다.
- [Skill design](../../decisions/skill-design.md): Git 전달 Skill은 혼자 설치돼도 약속한 결과를 책임진다. 고정 절차는 소유권을 추측하기 위험한 곳에만 쓴다. 이번 삭제 절차가 그런 곳이다.
- 확인과 승인 단계를 더하지 않는다. 지울 대상을 좁게 정의하는 기본값으로 안전을 지킨다.

## 가정 (수정 가능)

- 정리 섹션은 현재 checkout의 `AGENTS.md`를 먼저, 없으면 `CLAUDE.md`를 읽는다. `## Issue tracker`를 찾는 방식과 같다.
- flyn은 섹션에 `bun run dev:remove`와 `bun run db:remove`를 이 순서로 선언할 예정이다. 섹션 예시는 그 모양을 따른다.
- 원격 브랜치 삭제 방식은 지금과 같다. 이번 변경은 로컬 worktree와 로컬 브랜치만 다룬다.

## 범위 밖

- flyn 저장소의 수정과 실행. flyn의 `AGENTS.md` 선언은 flyn의 FLY-118 작업에서 한다.
- 프로세스를 직접 멈추는 기능. 프로젝트가 선언한 명령만 자원을 푼다.
- Codex 앱의 내부 상태 DB를 읽는 일. 문서화되지 않은 스키마라 업데이트로 조용히 깨질 수 있다.

## 남은 위험

- Codex worktree 루트는 Codex 설정에서 바꿀 수 있지만 Skill은 그 설정을 읽지 못한다. 기본 위치가 아닌 Codex worktree는 일반 worktree로 다뤄지고, 거기서 진행 중인 Codex 채팅은 보이지 않는다.
- Linux 등에서 고아 프로세스가 PID 1이 아닌 subreaper로 넘어가면 남은 프로세스도 붙은 것으로 보여 정리되지 않는다. 지우지 않는 쪽으로 틀리므로 작업은 잃지 않는다.
- 정리 명령이 생기기 전에 만든 오래된 worktree에서는 선언된 명령이 실패할 수 있다. 그런 worktree는 남겨 보고하므로 사람이 정리해야 한다.
