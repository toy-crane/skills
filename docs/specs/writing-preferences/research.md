## 결론

저장 위치는 이미 있다. 빠진 부분은 수정 요청이 들어온 때의 기록,
사용자가 고른 문장과 그 이유의 보존, 다음 초안에서 그 기준을 실제로
대조하는 과정이다. 이 세 부분을 기존 글쓰기 스킬에 연결하는 것을
추천한다. 블로그의 취향 자체를 배포하는 스킬 본문에 넣지는 않는다.

## 관찰한 패턴

### 1. 추상적인 말투 설정으로는 원하는 문장을 예측하기 어려웠다

P:121에서 사용자는 "가르치려는 태도는 최소화"하고 "차분하고 점잖은
스타일"을 원한다고 했다. P:126은 이를 되풀이하고 다음 질문으로 넘어갔다.
실제 문장을 보여주지 않았다.

이후 C1:287의 예고 문장을 고친 결과에는 "저는 아니라고 봅니다"가
남았고, 사용자는 C1:305에서 건방져 보인다고 다시 지적했다.
형용사에 대한 합의가 구체적인 문장에 대한 합의를 대신하지 못한 사례다.

제안: 매체 정의에서 추천 문단을 먼저 보여주고 채택한 예문을 남긴다.
이 방향은 현재 대화에서 이미 확정했다.

### 2. 쉬운 표현을 요구했는데 주장 자체가 달라졌다

C1:352에서 사용자는 문장을 직관적으로 이해하기 어렵다고 했다.
AI는 설명을 늘리면서 "결과가 좋아 보일수록 사람이 앱에 맞춘다"는
이야기를 넣었다. C1:556에서 사용자는 원래 하고 싶었던 말이 "더
그럴듯한 결과도 내 취향을 반영하지는 않는다"라는 것이라고 바로잡았다.
C1:560에서 AI도 두 주장이 달랐다고 인정했다.

제안: "쉽게", "자연스럽게"라는 피드백을 문장 표현만의 문제로
처리하지 않는다. 고치기 전에 유지해야 하는 주장과 주체를 확인하고,
새로 보탠 인과관계가 있는지 점검한다. 이 글의 구체적인 주장은 다른
글에 적용할 취향 규칙으로 승격하지 않는다.

### 3. 문장이 어색한 이유가 주체와 역할의 불일치인 경우가 있었다

C2:947에서 "시켜서 받은 앱"을 지적했는데, AI는 "말하고 받은 앱"으로
바꿨다. 사용자는 C2:960에서 "클로드가 구현한거지 받은건 아닌데"라고
다시 설명했다. C2:974에서는 원하는 문장 모양을 직접 제시했다.

Codex에서도 X:707의 "제 것이 되지는 않습니다"가 지적됐고,
X:798에서는 "아무리 그럴듯해도 제가 고른 답은 아닙니다"로 바뀌었다.
X:1137과 X:1164에서는 사람의 확인과 AI의 자체 확인이 뒤섞인 문제가
제목, 본문, 그림, 결론 전반의 역할 정리로 이어졌다.

제안: 지적된 낱말만 바꾸지 않고 누가 무엇을 하는지 확인한다.
같은 문제를 가진 본문과 제목, 그림도 살피되 관련 없는 부분을 전면
재작성하지 않는다. 적용하는 것은 역할을 명확히 쓰는 원칙이며, 특정
단어의 일괄 금지가 아니다.

### 4. 짧게 쓰라는 요청에는 유지해야 할 장점도 있었다

X:1475에서 사용자는 소제목을 줄여 달라고 했다. AI는 "사람의 선택",
"사람과 AI의 역할"처럼 분류명으로 만들었다. X:1678의 매력이 없다는
지적과 X:1738의 대상 교정 뒤, X:1775에서 새 소제목 두 세트를 제안했다.
사용자는 X:1782에서 첫 세트를 골랐다. "무엇을 버릴지는 사람이 정한다"
같이 짧으면서 주장을 담는 문장이 채택됐다.

제안: "소제목은 짧게"만 남기면 같은 실패가 반복될 수 있다.
줄일 것과 유지할 것을 함께 기록하고, 분류명과 채택한 제목을 비교할 수
있는 예문을 둔다. 첫 수정안이 적용됐다는 사실만으로 선호를 확정하지
않는다.

### 5. 읽기 쉬운 문장도 글의 흐름에 필요하지 않을 수 있었다

C1:594에서는 이전 글 연결을 빼라고 했고, C1:650에서는 블로그 내부
문서 예시를 독자가 이해할 예시로 바꿔 달라고 했다. C1:768, C1:980,
C1:1039에서는 글쓴이가 쓰는 도구와 만든 스킬, 개인 계획이 반복해서
제외됐다. C1:1064에서는 결론 두 문단의 중복이 지적됐다.

X:1027의 출처 문단은 내용 자체보다 앞뒤 흐름을 끊는 것이 문제였고,
X:1933에서는 여러 번 고쳤던 이미지 설명을 중복으로 판단해 삭제했다.
마지막에 삭제된 문장을 영구적인 좋은 예문으로 남기면 잘못 배운다.

제안: 수정 이유에 "누가 읽는가"와 "이 문단이 무엇을 더하는가"를
남긴다. 채택 상태는 뒤이은 수정에 따라 갱신한다. "항상 1인칭 금지",
"항상 링크 금지"처럼 적용 조건을 지우지 않는다.

### 6. 두 작업 모두 기록을 별도로 요청해야 했다

제안: 재사용 가치가 분명한 명시적 지시나 기존 원칙의 구체화는 해당

생긴 것으로 보지 않는다. 새로운 일반화나 적용 범위가 불명확한 경우만
확인할 후보로 남긴다.

### 7. 기록을 읽는 것과 실제로 지키는 것은 달랐다

X:33에서 Codex는 이미 존재하던 `writing.md`를 읽었다. 그 뒤에도
주체, 논리 연결, 중복에 대한 사용자 지적이 이어졌다. 단순히 읽는
경로를 하나 더 추가하는 것으로 해결된다고 말할 수 없다.

C1:578의 완료 보고는 독자 질문을 통과했다고 했지만, 이후에도 사용자가
여러 표현과 구조를 고쳤다. X:1671에서도 소제목의 이해 가능성을 확인한

검증이 문체나 취향 일치의 증거는 아니다.

제안: 기존 독자 질문 검증은 유지하고, 확정된 문체 규칙과 예문을 초안에
대조한다. 아직 합의되지 않은 취향을 AI가 새로 만들거나, 만족할 때까지
무한히 교정하는 검토를 추가하지 않는다.

## 기록 방법 제안

본문의 변경 이력은 Git에 두고, 다음 글에 필요한 현재 기준은 기존
매체 문서와 글쓰기 결정에 둔다. 세션 전문이나 시간순 수정 일지를 매번
읽게 하는 새 저장소는 만들지 않는 쪽을 추천한다.

| 보존할 내용 | 적용 범위와 위치 |
| --- | --- |
| 용어와 뜻 | 이미 합의된 프로젝트 용어면 `GLOSSARY.md` |
| 한 글의 주장, 범위, 제외 이유 | 그 글의 브리프. 다른 글의 취향으로 확대하지 않음 |
| 그 매체의 기본 말투와 채택 예문 | 매체 전제의 `Voice`. 공통 문체가 있으면 해당 결정 참조 |
| 반복 적용할 문체·구조 원칙과 예문 | 해당 범위를 명시한 기존 글쓰기 결정. 동일 원칙을 보강 |
| 한 번의 문장 교체나 사실 교정 | 본문과 Git 이력. 재사용할 이유가 없으면 규칙을 늘리지 않음 |
| AI가 추론했지만 사용자가 확인하지 않은 선호 | 확정 규칙과 구분한 후보. 빈도만으로 자동 승격하지 않음 |

한 규칙은 다음 정도의 정보면 충분하다. 필드를 채우기 위한 새 형식을
강제하기보다 기존 결정의 이유와 예문을 보강한다.

> **원칙:** 소제목은 짧게 쓰되 절의 주장을 드러낸다.
>
> **이유:** 길이를 줄이는 과정에서 분류명만 남기자 읽고 싶은 이유가
> 사라졌다는 피드백을 받았다.
>
> **비교 예문:** "사람의 선택" → "무엇을 버릴지는 사람이 정한다".
>
> **범위:** 이 블로그의 주장형 글. 모든 문서를 이 문체로 쓰라는 뜻은 아니다.
>
> **근거:** 짧게 해 달라는 요청 뒤 두 후보 세트 중 해당 세트를 선택했다.

위 예시의 제한된 범위는 제안이다. 실제 블로그의 현재 결정은 사용자가
이미 승인한 상태이므로 이번 연구만으로 좁히거나 덮어쓰지 않는다.
특히 현재 기록된 "프론티어 모델 회사 중심" 같은 기준을 다른 글쓴이나
매체의 보편적인 글쓰기 원칙으로 복사하지 않는다.

명시적 지시는 의미와 범위가 분명하면 추가 허락 없이 기록하는 방향을
추천한다. 선택지 중 하나를 골랐다는 사실, 단순 교정, 침묵은 자동으로
저자 전체의 영구적 취향을 승인한 것과 같지 않다. 기존 기준과 다른
요청이 오면 일회성 예외인지 기준 변경인지 구분하고 현재 기록을 고친다.

| `define-publication` | 실제 예문으로 추천하고 채택 예문을 보존 | 말투까지 열린 질문과 추상적인 답으로 처리할 수 있음. 추천은 별도 요청 후에만 하도록 되어 있어 확정한 새 방향과 조정 필요 |
| `define-piece` | 관련 기준·예문을 기획과 소제목에 적용하고, 글 단위 수정과 재사용할 선호를 구분 | 65–70행은 말투 비교 예문을 모두 버리고 한 줄만 남김. 채택한 기준점까지 잃을 수 있음 |
| `draft-piece` | 사용자 수정 요청에서 기존 규칙을 보강하고, 같은 원인의 다른 문장도 확인. 다음 초안에서는 확정 기준과 대조 | 78–79행의 일반적인 기록 안내는 수정 시점에 행동을 유도하지 못했음. 기록 스킬이 없으면 대화로만 넘김 |
| `draft-piece`의 수정 범위 | 확정한 문체 위반과 미확정 취향 제안을 구분해 기존의 제한된 수정 단계 안에서 처리 | 70–76행은 독자 질문 실패와 사실 오류만 수리하고 다른 문체 의견은 기록하므로, 이미 합의한 문체 위반까지 단순 의견으로 취급할 여지가 있음 |
| `project-knowledge` 또는 독립 설치 시의 동등한 처리 | 원칙, 이유, 적용 범위, 대표 예문을 현재 문서에 기록하고 중복을 합침 | 기준 자체는 이미 존재함. 새 보편 정책보다 글쓰기 스킬에서 적시에 호출하고 같은 결과를 보장하는 것이 우선 |

위 원인은 지침과 실제 실행을 대조한 해석이다. 스킬의 특정 문장을
원인으로 확정하려면 변경 전후 실행을 비교해야 한다.

발행 뒤 브리프가 없는 글의 교정도 실제 사용 경로다. 현재 `draft-piece`는
브리프 폴더로 시작하는 설명을 갖는다. 기존 글 경로로 교정할 때도
피드백 보존이 적용되도록 입력 범위를 검토할 필요가 있다. 이 경우
존재하지 않는 브리프를 지어내지 않고, 기존 글과 사용자의 수정 요청을
기준으로 삼는 범위를 별도로 정해야 한다.

사용자가 글의 주장을 직접 고쳐 준 경우에는 그 글의 계약도 맞춰야 한다.
C1:602와 C2:943에서 AI는 본문과 브리프가 어긋났다고 보고했지만 동기화는
미뤘다. `define-piece`가 계약을 소유하는 경계는 유지하면서, 이미 분명히
승인한 수정은 같은 세션에서 계약까지 반영하는 연결을 검토할 수 있다.
AI가 새로운 주장을 임의로 승인하는 것은 허용하지 않는다.

## 효과를 확인할 방법

스킬 문구가 생겼다는 것과 다음 글이 나아졌다는 것을 구분해야 한다.
변경 전후에 같은 모델, 같은 자료, 같은 기존 문체 기록을 제공하고,
과거 문장을 그대로 외우는 시험과 새로운 문장으로 전이하는 시험을 나눈다.

1. **기록 시점:** 명시적이고 범위가 분명한 문체 수정을 했을 때 별도의
   기억 요청 없이 기존 기록을 보강하는가. 기존 규칙이면 중복이 생기지
   않는가.
2. **재시작:** 수정 대화가 없는 새 세션이 저장소의 기록만 읽고 다른 주제로
   초안을 쓸 때 같은 문제를 피하는가. Claude가 기록하고 Codex가 읽는
   방향과 그 반대 방향을 확인한다.
3. **의미 보존:** 쉽게 풀어 달라는 요청을 처리하면서 원래 없던 인과관계나
   주장, 주체 변경을 만들지 않는가.
4. **범위 제한:** 한 글에서 회사 예시를 바꾸거나 한 문장을 볼드 처리한
   요청을 모든 글의 회사 목록·강조 규칙으로 확대하지 않는가.
5. **변경 수용:** 특정 회고에서 1인칭을 써 달라는 명시적 요청을 기존
   원칙 때문에 거부하지 않고 예외 범위를 보존하는가.
6. **검토의 역할:** 독자 질문을 통과해도 이미 확정한 문체 위반은 찾아
   고치는가. 새 취향을 만들어내거나 끝없는 교정으로 이어지지 않는가.

관찰할 결과는 같은 유형의 재지적, 주장 변형, 불필요한 영구 규칙 추가,
필요한 사용자 개입이다. 이번 연구만으로 수치 목표나 개선율을 제시하지
않는다. 최초 시험에 쓴 문장은 수정 뒤 재시험의 유일한 근거로 쓰지 않는다.
