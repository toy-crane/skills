# LLM 출력 품질을 eval로 증명하는 `llm-evals` 스킬

- 결정: [testing](../../decisions/testing.md). LLM 출력 품질 기준은 mock 테스트가 아니라 eval로 증명한다는 규칙과, eval의 red, green, held-out, "약하게 고치지 않기" 규율을 정한다.
- 결정: [pipeline](../../decisions/pipeline.md). `implement`가 기준마다 자동 테스트, eval, 런타임 증거 중 무엇으로 증명할지 고르는 규칙과, eval 승인을 spec과 첫 유료 실행 전 두 단계로 나누는 규칙을 정한다.
- 결정: [skill-design](../../decisions/skill-design.md). 다른 스킬의 글을 전제하지 않는다는 규칙, 이 묶음이 부르는 스킬은 필수로 두고 묶음 밖 스킬(`claude-api`)은 선택으로 둔다는 규칙이다.
- 결정: [skill-naming](../../decisions/skill-naming.md). `llm-evals`라는 이름과 버린 후보를 정한다.
- 용어: [Eval](../../../GLOSSARY.md). 이 spec에서 말하는 eval의 정의다.
- 참고 자료: claude-api 스킬의 `shared/evals/build-eval.md`, `shared/evals/eval-hillclimb.md`, `shared/evals/eval-audit.md`([anthropics/skills](https://github.com/anthropics/skills), Apache-2.0). 새 스킬의 규율은 여기서 핵심만 가져온다.

## 문제

`tdd`는 Claude 같은 모델 호출을 외부 API로 보고 mock하라고 한다. 그래서 "고객 문의가 환불 요청인지 맞게 분류한다" 같은 기준을 만나면, 모델 주변 코드만 테스트되고 동작을 실제로 정하는 프롬프트는 검증되지 않는다. 이런 기준은 "자동 테스트로 증명할 수 없음"으로 `implement`에 돌아가고, `implement`는 런타임에서 몇 번 눌러 보는 것으로 넘어가거나 미완료로 보고한다.

claude-api 스킬의 `build-eval`과 `hillclimb`은 이 문제를 푸는 방법을 갖고 있다. 승인된 사례 세트, 실제 진입점을 부르는 실행기, 채점기로 기준선 점수를 재고, train/test를 나눠 프롬프트를 한 번에 하나씩 고치면서 held-out 점수를 올린다. 하지만 이 묶음 밖에 있는 스킬이고, Claude 말고 다른 공급자를 쓰는 프로젝트에서는 스스로 빠지며, TDD의 red/green 계약이나 `implement`로 돌려줄 내용은 갖고 있지 않다.

## 사용자에게 보이는 결과

- LLM 출력 품질에 대한 기준이 있는 spec을 `implement`로 진행하면, 그 기준은 `llm-evals`로 넘어가 eval로 증명된다. "증명할 수 없음"으로 돌아오지 않는다.
- `llm-evals`는 첫 유료 실행 전에 한 번 멈춘다. 사례 목록, 채점 결과 샘플, 실행 규모(사례 수 × 반복 횟수), 실제 시험 실행에서 계산한 예상 비용과 비용 상한을 보여 주고 승인을 기다린다. 승인한 뒤에는 green에 닿을 때까지 묻지 않고 진행한다.
- 최종 보고에서 eval로 증명한 기준마다 기준선 점수, 최종 held-out 점수와 노이즈 범위, 라운드별 변경 내용이 나온다. 목표에 못 닿으면 최고 점수와 남은 실패의 원인 분류가 나오고, 그 기준은 미완료로 남는다.
- eval의 실행기, 사례, 채점기는 사용자 프로젝트에 남는다. 다음에 모델이나 프롬프트를 바꿀 때 같은 eval을 다시 돌릴 수 있다.
- `/llm-evals`로 직접 불러도 같은 방식으로 동작한다.
- eval을 만들기 전에 모델을 API 키로 부를지 구독제(Claude Code나 Codex 로그인)로 부를지 묻는다. API 키를 추천하지만, 키가 없어도 구독제로 진행할 수 있다.
- 이 워크플로우로 스킬을 만들거나 고칠 때도 eval이 돈다. 스킬을 설치한 일회용 작업 폴더에서 에이전트를 실행하고 끝난 상태를 채점하며, 이전 스킬 본문이나 스킬이 없는 상태를 기준선으로 삼는다.
- Claude가 아닌 모델을 쓰는 프로젝트에서도, claude-api가 설치되지 않은 환경에서도 같은 결과가 나온다. Claude Code와 Codex 모두에서 동작한다.
- shape-idea가 쓰는 spec에서 LLM 출력 품질 기준은 지표, held-out 사례 기준의 목표치, 사례 출처를 갖춘 형태로 적힌다.

## 승인된 범위

- 새 스킬 `llm-evals`를 `workflow` 그룹에 추가하고 두 배포 경로(플러그인, skills.sh)에 싣는다.
- `implement`가 기준을 eval로 증명하도록 고르고, `llm-evals`에 넘기고, 결과를 받아 보고하게 한다. `llm-evals`를 필수 스킬로 둔다.
- `tdd`가 LLM 출력 품질 기준을 mock 테스트로 증명한 것으로 치지 않고 이유와 함께 돌려주게 한다.
- `shape-idea`가 LLM 출력 품질 기준을 지표, 목표치, 사례 출처로 쓰게 한다.
- 위 스킬들의 평가 사례를 더한다.
- 플러그인 사용자에게 업데이트가 보이도록 플러그인 버전을 올린다.

## 수용 기준

1. `llm-evals` 본문은 다음을 담는다.
   - 트리거: 실행할 때마다 달라질 수 있고 결정적인 단정문으로 판정할 수 없는 LLM 출력 품질 기준을 증명할 때. `implement`가 넘길 때와 사용자가 직접 부를 때 모두 해당한다.
   - 입력: `implement`가 넘기면 해당 기준(지표, 목표치, 사례 출처), 진행 중인 결과물, spec. 직접 부르면 요청에서 기준을 끌어낸다.
   - 목표치가 없을 때: `implement`가 넘긴 기준이면 목표치를 지어내지 않고 shaping으로 돌려보낸다. 직접 불렀으면 사용자에게 목표치를 묻는다.
   - 사례 세트: 운영 로그, 버그 리포트, 사용자가 준 예시 순서로 출처를 찾는다. 합성은 실제 예시를 바탕으로만 한다. 사례 수와 반복 횟수는 노이즈 범위가 목표 개선폭보다 작아지도록 정한다. train/test는 무작위로, 주요 분류별로 고르게 나눈다.
   - 모델 접근 방식: eval을 만들기 전에 한 번 묻는다. API 키가 있으면 API 키(추천)와 구독제 중에서 고르게 하고, 앱 기능 eval이면 구독제의 정확도 차이를 함께 알린다. API 키가 없으면 멈추지 않고 구독제로 진행할지, 키를 준비한 뒤 진행할지 묻는다. 둘 다 없을 때만 멈추고 두 가지 준비 방법을 모두 알려 준다.
   - 실행기: 앱의 실제 진입점을 호출하고 모델 호출을 따로 다시 만들지 않는다. 구독제로 앱 기능을 eval할 때만 모델 호출 부분을 Claude Code나 Codex CLI 호출로 바꿔 끼우고, 앱과 같은 시스템 프롬프트와 모델을 쓰며 도구는 끈다. 사례마다 대화 전체, 응답에 찍힌 모델, 토큰 사용량, 점수를 남긴다. 인프라 오류는 점수와 따로 기록한다. 중단된 뒤 다시 돌리면 끝난 사례는 건너뛴다.
   - 스킬이나 에이전트 eval: 진입점은 대상 스킬을 설치한 일회용 작업 폴더에서 돌리는 에이전트 실행이고, 채점은 대화 내용이 아니라 끝난 뒤 남은 상태로 한다. 기준선은 스킬을 고칠 때 이전 본문, 새로 만들 때 스킬이 없는 상태다.
   - 채점기: 제대로 재는 방법 중 가장 싼 것을 고른다(코드 검사, 두 출력 비교 판정, 루브릭 판정, 사람 채점 순). 승인 전에 정답을 넣으면 거의 100점, 빈 출력이나 상수 출력을 넣으면 거의 0점이 나오는지 확인한다.
   - 승인: 첫 유료 실행 전에 한 번 멈춰 사례 목록, 채점 결과 샘플, 실행 규모, 시험 실행에서 계산한 예상 비용, 비용 상한, 이 규모에서의 노이즈 범위를 목표 개선폭과 나란히 보여 주고 명확한 승인을 기다린다. 구독제이면 비용 대신 사용 한도 소모 예상을 보여 주고, 달러 금액은 API 환산값으로만 표시한다.
   - red: 동작을 바꾸기 전에 전체 사례로 기준선 점수를 재고 기록한다.
   - 개선 루프: 라운드마다 변경 하나를 train 사례만 보고 제안하고, 점수는 test 사례에서 낸다. train만 오르고 test가 그대로면 되돌린다. green, 3라운드 연속 노이즈 안의 움직임, 승인받은 비용 상한 중 하나에 닿으면 멈춘다.
   - green: held-out 점수가 목표치 이상이고 기준선보다 노이즈 범위 밖으로 오른 상태다.
   - 사례, 채점기, train/test 분할은 통과시키려고 약하게 고치거나 빼거나 다시 나누지 않는다. 승인 뒤 이것들을 바꾸려면 다시 승인을 받는다. 정답은 테스트 대상 모델이 읽을 수 없는 곳에 둔다.
   - hand-back: 기준선에서 최종까지의 held-out 점수와 노이즈 범위, 라운드별 변경과 점수, 적용된 변경, eval 위치를 돌려준다. 목표에 못 닿았으면 최고 점수와 남은 실패의 원인 분류(내용 부족, 채점기, 하네스, 노이즈)를 돌려준다.
   - 보관: 실행기, 사례, 채점기는 사용자 프로젝트에 커밋할 수 있는 형태로 남긴다. 대화 기록과 리포트는 커밋 대상에서 뺀다.
   - claude-api가 설치되어 있고 테스트 대상이 Claude이면 그 실행기 scaffold와 리포트 도구를 쓸 수 있다. 없으면 같은 실행기 계약을 프로젝트 언어로 직접 만든다. claude-api를 요구하거나 그 글을 전제하지 않는다.
2. `implement` 본문은 다음을 담는다.
   - 각 인수 조건을 자동 테스트, eval, 런타임 증거 중 하나 이상에 대응시킨다. LLM 출력 품질 기준은 eval에 대응시킨다.
   - eval 기준을 `llm-evals`에 넘기고, 넘기는 내용과 돌려받는 내용을 적는다.
   - 다른 필수 스킬과 같은 방식으로, 시작 전에 `llm-evals`가 설치되어 있는지 확인하고 없으면 설치 명령과 함께 멈춘다.
   - 최종 보고에서 eval로 증명한 기준마다 기준선 점수와 최종 held-out 점수를 증거로 보고한다. 목표에 못 닿은 기준은 미완료로 보고한다.
3. `tdd` 본문은 LLM 출력 품질 기준을 mock한 모델 호출로 증명한 것으로 치지 않고 이유와 함께 돌려준다고 적는다. 모델 주변 코드는 지금처럼 테스트한다.
4. `shape-idea` 본문은 LLM 출력 품질에 대한 인수 조건을 지표, held-out 사례 기준의 목표치, 사례 출처로 쓰라고 적는다.
5. 평가에 다음 사례가 있고 통과한다.
   - `llm-evals`: `implement`가 목표치가 있는 기준을 넘긴 경우. 첫 유료 실행 전에 승인을 위해 멈추고, 프롬프트를 바꾸기 전에 기준선을 잰다.
   - `llm-evals`: `implement`가 목표치 없는 기준을 넘긴 경우. 목표치를 지어내지 않고 shaping으로 돌려보낸다.
   - `llm-evals`: 몇 라운드 뒤에도 목표에 못 닿는 경우. 사례나 채점기를 약하게 고치지 않고, 최고 점수와 원인 분류를 돌려준다.
   - `llm-evals`: Claude가 아닌 모델을 쓰고 claude-api가 없는 프로젝트. 같은 계약으로 실행기를 직접 만든다.
   - `llm-evals`: API 키가 없고 구독 로그인만 있는 경우. 멈추지 않고 구독제로 진행할지 키를 준비할지 묻는다.
   - `llm-evals`: API 키도 구독 로그인도 없는 경우. 멈추고 두 가지 준비 방법을 알려 준다.
   - `llm-evals`: 스킬 본문을 고치는 기준을 받은 경우. 이전 본문을 기준선으로, 일회용 작업 폴더의 에이전트 실행을 진입점으로 삼고 끝난 상태로 채점한다.
   - `tdd`: LLM 출력 품질 기준을 받은 경우. 주변 코드는 테스트하고 그 기준은 이유와 함께 돌려준다.
   - `llm-evals` 트리거 평가: LLM 출력 품질을 증명하려는 요청에는 트리거되고, 결정적인 동작을 테스트하려는 요청에는 트리거되지 않는다.
6. 배포
   - `llm-evals`가 플러그인 `skills` 목록, `.agents/skills/`와 `.claude/skills/` 심볼릭 링크, README에 있다.
   - 플러그인 버전이 `main`보다 올라가 있고, `claude plugin validate . --strict`가 통과한다.

## 확정된 제약과 이유

- eval은 `tdd` 안의 분기가 아니라 별도 스킬이다. `tdd`의 red는 몇 초 만에 도는 결정적 단정문의 실패이고, eval의 red는 유료로 반복 실행해 잰 기준선이다. 승인, 비용, 노이즈, train/test를 다루는 규율이 달라서 한 스킬에 넣으면 `tdd`가 두 배쯤 커지고 어떤 red가 기준인지 흐려진다.
- 라우팅은 `implement`가 맡는다. 설명으로만 트리거되는 스킬이면 `implement` 흐름 안에서는 아무도 부르지 않아서, LLM 기준은 계속 "증명 불가"로 돌아온다. 어떤 검사로 각 기준을 증명할지는 이미 `implement`의 몫이다.
- 승인은 두 단계다. 목표치는 제품 결정이라 spec에 있어야 구현 중에 낮출 수 없다. 구체적인 사례와 채점기는 코드와 데이터를 봐야 만들 수 있어서, 구현 단계에서 첫 유료 실행 전에 한 번 승인을 받는다. 승인 없이 진행하면 사례가 틀렸다는 것을 비용을 다 쓴 뒤에야 알게 되고, 아무도 그 점수를 믿지 않는다.
- 규율은 `llm-evals` 본문에 직접 담고 claude-api는 선택으로 둔다. claude-api를 필수로 하면 묶음 밖 스킬은 선택이라는 규칙과 부딪히고, 다른 공급자를 쓰는 프로젝트에서는 빠지며, 약 800줄짜리 대화형 가이드에는 red/green 계약도 `implement` hand-back도 없다. 통째로 가져오는 방법은 분량과 원본 업데이트 추적 비용 때문에 버렸다.

- 모델 접근은 API 키를 추천하되 구독제도 고를 수 있게 한다. API 키가 실제 경로를 그대로 재고 비용도 정확하지만, 모두가 비용 제약을 안고 있어서 키가 없다는 이유로 eval을 건너뛰게 하면 안 된다. 스킬이나 에이전트 eval에서는 CLI 실행이 곧 실제 진입점이라 구독제도 정확도 차이가 없다.
- 스킬 변경도 예외가 아니다. `implement`는 어느 프로젝트에서나 같은 규칙으로 동작하고 스킬 본문은 사실상 프롬프트라서, 이 저장소에서 스킬을 만들거나 고칠 때도 그 동작 기준은 eval로 증명한다.

## 가정 (수정 가능)

- 멈추는 조건의 "3라운드 연속"은 hillclimb 가이드가 정체로 보는 최소 횟수를 따른다.
- 반복 횟수, 판정 모델 선택, 비용 상한은 승인 단계에서 사용자에게 추천값과 함께 보여 주고 정한다.
- `llm-evals`는 `workflow` 그룹에 두고 스택 조건 없이 설치한다. `implement`가 필수로 요구하기 때문이다.
- `build-prototype`이 쓰는 spec에는 이번에 같은 문장을 넣지 않는다. 화면 중심 작업이라 LLM 출력 품질 기준이 드물다.
- 모델 API 키를 받거나 구독에 로그인하는 일은 각 프로젝트 spec의 "Setup before implementation"에 들어간다. `llm-evals`는 키를 받거나 만들지 않는다.
- 모델 접근 방식 질문은 첫 유료 실행 전 승인과 별개인 짧은 선택이다. 실행기 모양과 시험 실행이 이 선택에 따라 달라지므로 eval을 만들기 전에 묻는다.

## 범위 밖

- 이 저장소의 기존 비교 하네스(`scripts/run-tdd-comparison.sh`)를 `llm-evals` 방식으로 고쳐 쓰는 일. 앞으로 스킬 변경은 `llm-evals`로 eval하지만, 기존 하네스를 옮기거나 지우는 일은 따로 다룬다.
- 비용이나 지연을 줄이는 개선 루프(claude-api의 `cost-hillclimb`). 이번에는 품질 기준을 목표치까지 올리는 일만 다룬다.
- claude-api의 eval 가이드를 통째로 가져오는 일.
- `build-prototype` 본문 수정.

## 남은 위험

- 사용자 프로젝트에서 eval 실행 비용이 생긴다. 승인 단계에서 상한을 정하지만, 노이즈를 목표 개선폭보다 작게 만들려면 사례와 반복이 많이 필요할 수 있다.
- 승인 단계에서 멈추기 때문에, 사람이 없는 상태로 돌린 `implement`는 그 지점에서 기다린다.
- 핵심만 가져온 규율이 claude-api 원본이 바뀌는 것을 따라가지 못할 수 있다.
- 판정 모델로 채점하는 eval은 판정 모델이 겉모양에 속을 수 있다. 채점 샘플 승인과 정답·빈 출력 점검으로 줄일 뿐 막지는 못한다.
- 구독제로 앱 기능을 eval하면 앱의 파라미터와 도구 연결이 빠져서, 점수가 실제 동작과 다를 수 있다. 사용 한도에 걸리면 실행이 길어진다.
- 스킬 eval은 사례 하나가 여러 턴짜리 에이전트 실행이라, 감당할 수 있는 규모에서는 노이즈 범위가 클 수 있다(예: 사례 6개 × 3회면 약 ±24점). 승인 단계에서 드러낼 뿐 줄이지는 못한다.
- 아직 실제 프로젝트에서 돌려 본 근거가 없다. 평가 사례 외에 첫 실제 사용에서 확인해야 한다.

## Setup before implementation

- `llm-evals` 평가 사례에서 실제 모델을 호출할 Anthropic API 키 또는 Claude Code 구독 로그인. 승인, 기준선, 개선 루프를 실제 호출로 확인하는 평가 사례에 쓴다. 이 저장소 밖에서 Messages API를 직접 호출해 응답이 오거나, `claude -p`가 응답하면 준비된 것이다.
