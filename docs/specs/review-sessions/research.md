# 세션 기록에서 결정론으로 옮길 일 찾기 — 조사 결과

> 이 폴더의 조사 기록이다. [spec.md](./spec.md)가 근거와 수용 기준의 재현
> 대상으로 연결하며, 폴더가 퇴역할 때 함께 지워진다. 조사에 쓴 측정 틀은
> 스킬의 `scripts/review_sessions.py`로 옮겨졌다
> ([document-lifecycles](../../decisions/document-lifecycles.md)는 spec,
> prototype, tasks만 두므로 이 파일은 이 작업 단위에 한정된 임시 파일이다).

출발점은 [Poteto 인터뷰 정리](https://notes.toycrane.xyz/poteto-spacex-shipping-2500-prs/)의 주장이다.
지난 대화를 주기적으로 읽어서 반복 개입과 반복 실패를 찾고, 그중 고정된 절차는
CLI, 스크립트, 린트 규칙으로 옮기라는 것이다. 이 문서는 그 작업을 실제 세션
기록에 한 번 적용해 보고, 나온 후보가 정말 의미 있는지 판정한다.

## 1. 무엇을 봤나

| 항목 | 값 |
| --- | --- |
| 기간 | 2026-09-10 ～ 2026-10-10 (30일) |
| Claude Code 세션 | 965개 (eval·임시 디렉터리 세션 306개 제외) |
| Claude Code 도구 호출 / 오류 / 사용자 발화 | 138,706 / 2,989 / 9,216 |
| Codex 세션 | 560개. 그중 사람이 쓴 데스크톱 대화는 125개 |
| 소스 | `~/.claude/projects/*/*.jsonl`, `~/.codex/sessions/**/*.jsonl` |

추출은 조사용 스크립트가 한 번에 훑어서 세션당 한 줄(도구 호출, 정규화한
명령, 오류, 사용자 발화와 직전 AI 발화)로 만들었다. 17초 걸린다. 세션은 기간
안에 파일이 바뀐 것을 골랐고 그 세션의 사건은 전부 셌다. 오래 이어진 데스크톱
세션의 기간 밖 사건까지 들어가므로 이 표의 수치는 기간 안의 사건만 세는
방식보다 크다. 같은 집계는 이제 스킬의 `scripts/review_sessions.py scan
--select-by mtime`이 낸다.

보려 한 신호는 다섯 가지다.

- 같은 명령이 한 세션 안에서 실패를 끼고 반복되는 곳
- 여러 세션에 걸쳐 같은 오류 문구가 나오는 곳
- 사용자가 중간에 바로잡거나 끊은 곳
- 세션마다 같은 준비 작업을 다시 하는 곳
- 스킬이 있는데도 손으로 한 곳

### 범위의 한계

- Codex 기록은 얇다. 560개 중 334개는 Claude 세션이 `codex exec`/`codex review`로
  띄운 리뷰 실행이고, 252개는 서브에이전트다. 사람이 쓴 125개 대화에서 오류는
  내 기준으로 0건이었다. 실질 범위는 "Claude Code 세션과 거기서 부른 Codex
  리뷰"다.
- "같은 명령 반복" 탐지기의 상위 결과는 재시도가 아니라 파일 재읽기(`sed -n`,
  `cat`)였다. 이 신호는 쓰지 않았다.
- 실험용 저장소(todo-tutorial, feedme-clone*, experiments/)는 실제 작업에 섞여
  있다. 숫자를 조금 부풀린다.

## 2. 후보와 판정

판정 기준은 네 가지를 모두 만족하는가다. 여러 세션에서 반복되는가, 반복마다
턴·토큰·사람의 교정이 들었는가, 판단을 빼앗지 않고 결정론적 주인이 가져갈 수
있는가, 하네스가 이미 가진 일이 아닌가.

### A. 하네스가 이미 막고 있다 — 스킬 대상 아님

| 신호 | 세션 | 건수 | 남는 비용 |
| --- | ---: | ---: | --- |
| `sleep N; tail` 폴링을 하네스가 차단 (Monitor 쓰라고 안내) | 127 | 152 | 차단 뒤 128건은 다시 Bash로 시도, 23건만 Monitor로 전환 |
| Read 없이 Edit/Write | 44 | 78 | 1턴 |
| 읽은 뒤 바뀐 파일 Edit | 18 | 22 | 1턴 |
| zsh 글롭 `no matches found` (`--include=*.ts` 따옴표 누락) | 56 | 68 | 1턴 |
| 셸 cwd가 유지되는데 상대 경로로 `cd apps/...` 다시 실행 | 46 | 81 | 1턴. 이후 8이벤트 안 추가 오류 평균 0.5건 |
| `gh pr view --json merged` 같은 필드 추측 | 10 | 10 | 1턴 |

이 묶음은 이미 결정론적이다. 하네스가 막고, 에이전트가 한 턴 뒤 고친다. 남는
주인은 전역 지침 한 줄("절대 경로를 쓴다", "폴링은 Monitor로")뿐이고, 그 한 줄이
행동을 바꾼다는 증거는 없다. 하네스 버전이 바뀌면 사라지는 비용이기도 하다.

### B. 이 저장소의 스킬이 고칠 수 있다 — 의미 있음, 지금 고칠 것

**B1. `triage-issues`의 `claim.sh`가 데스크톱 워크트리 가드와 부딪힌다.**

| 값 | 수치 |
| --- | ---: |
| 가드 차단 | 36세션 104건 |
| 그중 `triage-issues`가 로드된 세션의 차단 | 61건 |
| 차단이 일어난 세션의 종류 | 104건 전부 Robo가 띄운 무인 세션(`robo-fly-*`, `robo-dea-*` 워크트리) |
| `claim.sh` 인자 오용(`missing value for --token`, `issue has no claim`) | 9세션 12건 |
| `triage-issues` 세션의 100호출당 오류 | 5.2 (다른 스킬은 1.5～2.1) |

차단된 형태는 전부 같다. `claim`이 출력한 sha와 token을 `verify`에 넘기려고
`$(cut ...)`, `read SHA TOK < 파일`, `; echo $?; sed ...` 체인을 쓰면 가드가
"실행 시점에 계산된 값"이라며 거부한다. 통과한 형태도 전부 같다. 값을 글자
그대로 적은 단일 명령이다. 스크립트가 출력값을 파일로 남기고 `verify --from
<파일>`로 읽거나, `claim`이 그대로 실행할 `verify` 명령 한 줄을 출력하면
에이전트는 체인을 만들 이유가 없어진다. 스킬 본문에 그 호출 형태를 적는다.
차단 104건이 전부 사람이 보지 않는 Robo 세션에서 났다는 점이 이 후보를 가장
앞에 둔다. 예약 실행 `flyn-triage-issues` 35회에는 가드 차단이 없었고, 대신
`claim.sh` 인자 오용이 섞여 있다. 같은 스크립트의 같은 인터페이스 문제다.

**B2. `expo-dev-loop`이 agent-device 래퍼를 세션마다 다시 만든다.**

| 값 | 수치 |
| --- | ---: |
| agent-device를 부른 세션 / 호출 | 185 / 11,521 |
| 세션당 호출 중앙값 / 90퍼센타일 | 43 / 134 |
| press류 호출 | 4,715 |
| 그중 `sleep`을 인라인으로 끼운 것 | 2,007 |
| 그중 `--settle`을 쓴 것 | 2,866 |
| `/tmp/*ad-ios.sh` 같은 래퍼를 세션 안에서 새로 쓴 세션 | 12 |

인터뷰의 Playwright 예시와 가장 닮았다. CLI 자체가 `--settle`을 안내하고 스킬
본문도 그렇게 적혀 있는데, 2,007번은 `sleep`으로 때웠다. 세션 안에서 `--udid`를
붙이는 셸 래퍼를 만들어 쓰고 버린 흔적이 12세션에 있다. 래퍼를 스킬이
`scripts/`로 싣고, 기다림을 `sleep` 대신 `--settle`과 `wait` 단언으로 고정하면
반복이 준다. 다만 호출 수가 줄어드는지는 고친 뒤 재측정해야 안다.

**B3. `pr`의 화면 증거 합성을 세션마다 다시 짠다.**

| 값 | 수치 |
| --- | ---: |
| `montage`/`ffmpeg`로 전후 비교를 합성한 세션 | 48 |
| 시뮬레이터 영상을 녹화한 세션 | 28 |
| `montage` 폰트 오류 | 6세션 |

[pr-descriptions](../../decisions/pr-descriptions.md)가 전후 영상을 기본 증거로
정했다. 녹화, 프레임 추출, 나란히 합성은 매번 같은 절차인데 세션마다 명령을
새로 쓴다. 입력 두 개를 받아 비교 이미지와 영상을 내는 스크립트 하나면 된다.

**B4. 워크트리를 지운 뒤 셸 cwd가 사라진다.**

24세션에서 `merge`/`clean-branches`가 워크트리를 지운 직후 "작업 디렉터리가
삭제됐다"로 한 턴을 잃었다. 스크립트 안의 `cd`는 서브셸에서 끝나므로 하네스의
셸 위치를 못 옮긴다. 고칠 곳은 스킬 본문이다. 지우는 명령을 canonical
체크아웃에서 같은 명령 안에 실행하라고 적는다(`cd <canonical> && bash
remove-worktree.sh ...`). 작지만 공짜다.

**B5. 브라우저 패널 — 부분적으로만 우리 것.**

| 값 | 수치 |
| --- | ---: |
| 브라우저 패널을 쓴 세션 | 181 |
| 오류가 1건 이상인 세션 / 오류 합계 | 126 / 553 |
| 첫 호출이 `preview_start`인 세션의 100호출당 오류 | 9.0 |
| 첫 호출이 `navigate`인 세션 | 12.0 |
| 첫 호출이 `computer`인 세션 | 13.6 |
| `launch.json` 없음 | 11세션 |
| "navigation denied" 73건 중 `preview_start`를 이미 부른 뒤 | 46 |

첫 호출 방식에 따른 오류율 차이가 작다. 패널 자체가 불안정한 몫이 크고, 그건
우리가 못 고친다. 우리 몫은 두 가지다. 프로젝트마다 `.claude/launch.json`을
커밋하는 것(flyn, dearly, turbo-repo-template, pado에 없음)과 `build-prototype`,
`human-review`의 미리보기 전달 문장에 `preview_start`부터 부르라고 적는 것이다.

### C. 프로젝트가 가진 스크립트 — 이미 하고 있다

flyn에는 `bun run dev`, `db:*`, `claim.sh`, `agent-device` 래퍼 같은 결정론적
도구가 이미 있다. 인터뷰가 말하는 전환을 사용자가 이미 손으로 해 왔다는 뜻이다.
남은 후보는 "절차를 산문으로 들고 있는" 메모리다.

- flyn 메모리 `codex-review-base-excludes-prompt`는 16세션이 다시 읽었다.
  `codex review`를 부르는 정확한 형태를 적어 둔 메모인데, 스크립트 한 개로
  바뀔 내용이다.
- turbo-repo-template 메모리 `mobile-dev-environment-traps`는 18세션이 다시
  읽었다. 로케일, `--device`, `ANDROID_HOME` 같은 환경 함정 목록인데, 인터뷰가
  말하는 "실수를 불가능하게 만드는 제약"(doctor 스크립트, env 고정)에 해당한다.

둘 다 이 저장소의 스킬이 아니라 각 프로젝트의 일이다. 이 조사가 찾아서 그
프로젝트의 follow-up으로 넘기면 된다.

### D. 결정론으로 바꿀 수 없다 — 다른 곳으로 간다

**사용자 교정.** 중간 발화 8,254개 중 "아니", "말고", "하지 마" 같은 강한
표지가 있는 것이 246세션 512개다. 70개를 무작위로 읽었다. 거의 전부 제품
판단이다. 홈 화면 문구를 줄여라, 주인공은 서양인이어야 한다, 차단 기능이 왜
필요하냐, 그 범위까지 하지 마라. 도구가 가져갈 수 있는 것이 아니다. 이 흐름의
주인은 이미 있다. 결정 계약과 프로젝트 메모리다. 세션 조사가 할 일은 같은
교정이 세 번 이상 나오는 주제를 찾아 결정 계약 후보로 올리는 것까지다.

**사용자 중단.** `[Request interrupted by user]`가 230세션 374건이다. 150건은
AI가 글을 쓰는 중, 37건은 `AskUserQuestion` 대화상자 중이었다. 대화상자는
225세션이 썼고 33세션에서 사용자가 거부했다. flyn 메모리에도 "선택
다이얼로그를 피한다"가 이미 있다. 이것은 `shape-idea`의 문장 문제이지
스크립트 문제가 아니다.

**슬래시 대신 말로 부른 것.** "머지해줘"를 32번 쳤지만 `merge`는 어차피
떴다(`gh pr merge` 396세션 중 379세션이 `merge` 로드). 비용 없음.

### E. 고친 뒤 재측정이 필요한 것 — 이 조사가 할 일의 핵심

| 신호 | 10-09 09:00 KST 이전 | 이후 |
| --- | ---: | ---: |
| `gh pr create` 세션 중 `pr` 미로드 | 242 / 382 | 1 / 2 |
| `merge` 세션의 `git rebase` 중 `pull` 미로드 | 209 / 259 | 2 / 2 |

`pr` 위임은 지난주 한 번의 수동 조사가 찾아 #127, #128로 고쳤다. 그러나 고친
뒤 효과를 보는 측정은 아무도 하지 않는다. 데이터는 아직 이틀치다. 2주 뒤에 같은
집계를 돌려야 "고쳐졌다"를 말할 수 있다. 그때 기준은 머지 날짜가 아니라 세션이
실제로 읽은 스킬 판이어야 한다. flyn과 dearly는 설치된 사본을 쓰고, 그 사본은
`update-project-skills` 자동화가 하루 한 번 갱신하므로 머지 뒤에도 옛 판으로 돈
세션이 섞인다. 세션이 읽은 SKILL.md의 판(플러그인 버전이나 해시)으로 나누는 것이
이 조사를 스킬로 만들 때 가져가야 할 제약이다. `rebase`→`pull` 위임도 같은 결정
([skill-design](../../decisions/skill-design.md))인데 같은 문제가 있을 가능성이
높다.

덧붙여 `merge`는 무거운 스킬이 아니었다. `/merge` 이후 git/gh 호출 중앙값은
10회이고, 301세션 중 190세션은 `/merge` 뒤 사용자 발화가 0이다. 세션당 171회라는
호출 수는 머지 전 구현 단계의 것이다.

## 3. 스킬로 만들 가치가 있는가

**있다고 보는 근거**

- 한 번의 수동 조사가 결정 계약의 증거와 수정 PR 두 개를 낳았다(`pr` 위임).
- 이번 한 시간짜리 조사가 스킬이 가진 수정 네 개(B1～B4)와 프로젝트 follow-up
  둘(C)을 찾았다.
- 하루에 Claude 세션 약 70개, Codex 약 20개가 쌓인다. 전수 조사는 못 하고
  표본 조사가 필요하다는 인터뷰의 전제가 그대로 맞는다.
- 고친 뒤 재측정(E)은 측정 틀이 남아 있어야 가능하다. 스킬의 `scripts/`가 그 틀이다.

**없다고 보는 근거**

- 가장 큰 숫자(A)는 하네스 것이다. 버전이 바뀌면 사라지고, 우리가 고칠 수 없다.
- 결과물의 자리는 이미 있다. 결함은 `docs/follow-ups/`, 측정치는 결정 계약의
  "Evidence worth preserving" 줄, 교정 패턴은 메모리와 결정 계약. 새 문서
  종류는 필요 없다.
- 예약 실행만 원한다면 `daily-code-cleanup`처럼 scheduled-task 프롬프트 한 장으로
  돌릴 수 있다. 스킬은 그 프롬프트가 "무엇을 세고 어디에 적는가"를 재사용할 때
  의미가 있다.

**경계.** [pipeline](../../decisions/pipeline.md)의 "개인 흔적을 캐지 않는다"는
제품 씨앗을 지어내지 말라는 뜻이다. 이 조사는 도구 신호를 캔다. 스킬을 만들면
그 구분을 스펙에 명시한다.

## 4. 남은 질문 하나

B1～B4는 스킬 결정과 무관하게 지금 고칠 가치가 있다. 각각 작은 PR이다.

정할 것은 하나다. 주기적 조사를 **스킬**로 만들 것인가, 아니면
`daily-code-cleanup`처럼 **scheduled-task 프롬프트**로만 둘 것인가.

추천은 스킬이다. 이유는 E다. 고친 뒤 같은 집계를 다시 돌리는 일이 조사의 절반인데,
그 집계 정의(무엇을 세션으로 치고, 무엇을 뺀다)가 프롬프트에 흩어지면 두 번째
측정이 첫 번째와 비교되지 않는다. 스킬이 추출·집계 스크립트를 싣고, 프롬프트는
"언제 돌리고 어디에 보고하는가"만 가지면 된다.
