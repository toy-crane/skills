# 테스트를 먼저 쓰되 하나씩 번갈아 쓰지 않는 `testing` 스킬

- 결정: [testing](../../decisions/testing.md). 테스트를 먼저 쓰는 범위, 실패 확인, 버그 재현, 테스트 범위, 테스트를 속이지 않는 규칙과 그 근거를 정한다.
- 결정: [pipeline](../../decisions/pipeline.md). `implement`와 `testing` 사이에서 무엇을 넘기고 돌려받는지, 런타임 증거가 언제 여전히 필요한지 정한다.
- 결정: [skill-naming](../../decisions/skill-naming.md). `testing`이라는 이름, 버린 후보, 이름을 바꿀 때 함께 바뀌어야 하는 범위를 정한다.
- 결정: [skill-design](../../decisions/skill-design.md). 고정 절차는 막는 실패를 밝혀야 하고, 의심 가는 기본값은 현실적인 프롬프트로 평가한다는 규칙이다.

## 문제

지금 `tdd` 스킬은 테스트 하나 쓰기, 실패 확인, 통과할 만큼만 구현하기를 번갈아 반복하게 한다. "앞으로 나올 테스트를 미리 고려하지 말라"고도 한다. 이 번갈아 쓰기가 막는 실패는 스킬에도 결정 문서에도 적혀 있지 않다. 반면 토큰이 늘고, 설계가 첫 테스트에 묶이고, 테스트를 떠올리지 못한 동작은 구현되지 않는다는 지적이 있다.

그렇다고 순서를 완전히 풀면 다른 구멍이 생긴다. 에이전트가 코드를 먼저 짜고, 코드가 내놓은 값을 정답으로 테스트에 적으면 코드의 버그가 테스트에 그대로 박힌다. 테스트를 먼저 쓰는 것은 이 구멍을 막는다. 문제는 먼저 쓰기가 아니라 하나씩 번갈아 쓰기다.

## 사용자에게 보이는 결과

- `tdd` 스킬이 `testing`으로 바뀐다.
- 에이전트는 지금 진행 중인 결과 전체를 보고 먼저 설계한다. 새 동작의 테스트는 그 동작을 구현하기 전에 쓰고, 테스트 여러 개를 먼저 쓴 뒤 한꺼번에 구현할 수 있다.
- 새 테스트는 모두 assertion으로 실패한 실제 출력(기대값과 실제값)을 기록으로 남긴다. 함수가 없어서 나는 오류는 실패로 치지 않는다.
- 버그 수정은 기존 코드에서 잘못된 동작으로 실패하는 재현 테스트부터 시작한다.
- 테스트마다 그 테스트가 증명하는 수용 기준이나 지키는 대상(재현한 버그, 기준이 닿지 않는 로직의 위험, 건드린 기존 동작)이 붙는다. 이유를 댈 수 없는 테스트와, 기준이나 이유가 요구하지 않는 코드는 생기지 않는다.
- `implement`의 최종 보고에서 모든 수용 기준이 검증 수단(자동 테스트, 런타임 증거, 또는 둘 다)과 그 증거로 한 줄씩 보인다.
- 사용자가 "TDD로", "red-green-refactor로"라고 요청하면 테스트 하나씩 번갈아 쓰는 순서를 따른다.

## 승인된 범위

- 공개 스킬 `tdd`의 이름을 `testing`으로 바꾸고, 본문을 [testing](../../decisions/testing.md) 결정에 맞게 다시 쓴다. 바뀌는 범위는 [skill-naming](../../decisions/skill-naming.md)의 이름 변경 경계 전체에, skills.sh 그룹 설정과 평가 파일을 더한 것이다.
- `implement`가 [pipeline](../../decisions/pipeline.md) 결정대로 수용 기준마다 검증 수단을 정하고, 자동 테스트로 증명할 기준을 `testing`에 넘기도록 바꾼다. seam 선택은 `testing`으로 옮긴다.
- 현행 `tdd`와 새 `testing`을 같은 과제로 돌려 비교하는 평가를 만들고, 이름 변경을 `main`에 합치기 전에 돌린다.
- 플러그인 사용자에게 업데이트가 보이도록 플러그인 버전을 올린다.

## 수용 기준

1. 설치하고 부를 수 있는 스킬 이름이 `testing`이다. 저장소에서 `.git`과 `docs/specs/`를 빼고 `tdd`를 단어 단위로 검색하면, 이름의 역사나 결정 근거를 설명하는 줄과 마켓플레이스 검색 키워드만 나온다. `claude plugin validate . --strict`가 통과한다.
2. 트리거 평가가 있고, 다수결로 통과한다. 다음 요청은 `testing`을 부른다: "TDD로", "test-first로", "red-green-refactor로", "이 동작에 대한 테스트를 써 줘", "이 버그를 테스트로 재현해 줘". "기존 테스트 돌려 줘"처럼 테스트를 실행만 하는 요청은 부르지 않는다.
3. `testing` 본문은 [testing](../../decisions/testing.md) 결정의 모든 규칙을 담는다. 다음이 포함된다.
   - 새 동작 테스트는 동작보다 먼저 쓰고, 없는 이름은 껍데기를 만든 뒤 assertion 실패를 확인한다.
   - 기존 동작 테스트는 구현을 망가뜨리거나 고치기 전 코드에 돌려 실패를 확인한다.
   - 버그 수정은 재현부터 한다.
   - 수용 기준이 최소선이고, 그 밖의 테스트는 지키는 대상을 밝힌다.
   - 기준이나 이유가 요구하지 않는 코드는 쓰지 않는다.
   - 건드린 기존 테스트를 찾아 돌린다.
   - 실패하는 테스트를 지우거나 건너뛰거나 약하게 만들지 않고, 실행 후 테스트를 고칠 때는 승인된 계약의 근거 줄을 댄다.
   - 지금 `tdd`가 하는 일 중 용어집과 관련 결정 문서 읽기, 결정 수준의 충돌 드러내기, 현재 용어 쓰기, 기존 seam 재사용과 안정적인 use case나 도메인 개념에만 새 seam 만들기는 그대로 남는다.
   - 공개 seam, 경계에서만 mock, 구현과 독립된 기대값 규칙도 그대로 남는다.
   - 테스트 하나씩 번갈아 쓰기는 요구하지 않는다. 사용자가 명시적으로 요청할 때만 따른다.
4. `testing`을 단독으로 부르면 스펙 없이 사용자 요청에서 기대 동작을 뽑는다. 버그라면 재현 테스트가 기존 코드에서 잘못된 동작으로 실패하는 것부터 보인다. 이 두 경우와 TDD를 명시한 요청이 각각 평가 사례로 있다.
5. `testing`이 끝나면 다음을 돌려준다.
   - 코드 변경.
   - 새 테스트마다 한 줄: 테스트 이름, 묶인 기준이나 이유, 관찰한 assertion 실패 출력의 발췌.
   - 넘겨받았지만 자동 테스트로 증명하지 못한 기준과 그 이유.
6. `implement`는 `testing`을 필수 스킬로 확인하고, 없으면 `npx skills@latest add toy-crane/skills --skill testing`과 함께 멈춘다. 이때 `implement`는 다음을 따른다.
   - 지금 진행 중인 결과의 수용 기준마다 검증 수단을 하나 이상 정한다.
   - 실행 중인 제품의 동작은 테스트가 있어도 런타임 증거를 여전히 확인한다.
   - `testing`에는 진행 중인 결과, 자동 테스트로 증명할 기준, 작업의 제약과 승인된 참조, 설계 맥락인 스펙을 넘긴다. 다른 결과나 막힌 결과를 구현할 권한은 넘기지 않는다.
   - seam을 직접 고르지 않는다.
   - `testing`이 증명하지 못한 기준은 런타임 증거로 확인하거나 미완료로 보고한다.
   - 최종 보고에는 모든 기준이 검증 수단과 증거로 나온다.
   - 자동 테스트는 통과했지만 런타임 증거를 얻지 못한 경우가 완료로 처리되지 않는 평가 사례가 있다.
7. `update-project-skills`의 평가가 이름 변경을 다룬다. 잠금 파일에 `tdd`가 있는 프로젝트에서는 `tdd`가 정리되고 `testing`이 설치된다. 프로젝트에 같은 이름의 로컬 `testing`이 이미 있으면 로컬 것을 보존하고, 마이그레이션이 막혔다고 보고하고, 기존 채택 승인 절차를 따른다. upstream에서 지워진 항목을 사용자 판단에 맡기는 단계와 Toycrane 관리 스킬의 은퇴가 부딪히면 은퇴가 이긴다.
8. 비교 평가가 있고, 이름 변경을 `main`에 합치기 전에 통과한다.
   - **기준선**: 변경 직전 커밋의 `tdd`를 git에서 꺼내 쓴다. 옛 `SKILL.md` 사본은 저장소에 커밋하지 않는다.
   - **과제**: 번호 붙은 수용 기준이 있는 기능 과제 하나와 버그 수정 과제 하나. 각 과제에는 에이전트가 보지 못하는 숨긴 정답 테스트와, 시그니처는 맞지만 값은 틀린 껍데기 구현이 있다.
   - **실행**: 같은 모델로 두 스킬을 각각 과제마다 3회 돌린다. 프롬프트는 스킬 이름만 다르고 "TDD"나 "test-first"라는 말을 쓰지 않는다. 실행 자체가 실패하면 다시 돌리고 점수에 넣지 않는다.
   - **측정**: 다음을 기록한다.
     - 숨긴 테스트로 본 기준 충족.
     - 가짜 red: 에이전트가 쓴 테스트를 껍데기 구현(버그 과제는 고치기 전 코드)에 다시 돌렸을 때 통과하거나 assertion이 아닌 오류로 실패하는 테스트 수.
     - 최종 코드에 스펙을 어기는 버그 3–5개를 심었을 때 테스트가 잡은 수.
     - 처음 실행한 뒤 고쳐진 테스트 수.
     - 이유 없는 테스트 수(어느 스킬이 만들었는지 모르는 채점자가 판정).
     - 토큰 사용량.
   - **통과 조건**:
     - `tdd`가 3회 중 2회 이상 충족한 기준을 `testing`도 3회 중 2회 이상 충족한다.
     - 가짜 red 합계가 기준선 이하다.
     - 심은 버그를 잡은 수가 기준선 이상이다.
     - 절대 조건으로, `testing` 실행에서 새 테스트는 모두 기록된 assertion 실패를 갖고, 버그 수정 과제에서는 재현 테스트가 수정보다 먼저 실패한다. 이 판정은 에이전트의 마지막 보고가 아니라 실행 기록으로 한다.
   - **결과 보관**: 요약 수치를 [testing](../../decisions/testing.md) 결정에 남긴다. 실행 결과물은 남기지 않는다.
   - **실패 시**: 통과하지 못하면 이름 변경을 합치지 않고, 이 방향을 다시 연다.
9. 플러그인 버전이 `main`보다 올라가 있다.

## 확정된 제약과 이유

- 테스트를 먼저 쓰는 것은 남긴다. 코드가 없으면 코드가 낸 값을 정답으로 베낄 수 없어서, 기대값이 구현과 독립된다. 테스트를 나중에 쓰고 구현을 망가뜨려 실패를 보이는 방식은 테스트가 변화에 반응한다는 것만 증명하고, 기대값이 맞다는 것은 증명하지 못한다.
- 하나씩 번갈아 쓰기는 뺀다. Böckeler의 탐색적 실험(Sonnet 4.6, 22회)에서는 TDD 유무에 따른 품질 차이를 측정하지 못했다. 토큰은 약 3–8.5배 더 들었는데, 캐시 읽기가 포함되어 실제 비용보다 크게 잡혔을 수 있다. 테스트를 먼저 쓰되 번갈아 쓰지 않은 조건은 지시가 없는 조건만큼 결과가 좋았다. 번갈아 쓰기가 설계를 굳힌다는 것은 그의 가설이다.
- 근거는 엇갈린다. Kent Beck과 Anthropic의 사내 도입 가이드는 에이전트와 테스트 하나씩 번갈아 쓰는 루프를 권한다. TDAD의 결과는 4비트 소형 모델 두 종에서 나왔고, 저자는 최상위 모델에서는 다를 수 있다고 밝혔다. 그래서 이 변경은 비교 평가로 확인하는 가설이고, 평가를 통과하기 전에는 `main`에 합치지 않는다.
- 진짜 red를 요구한다. 테스트를 먼저 써도 컴파일 오류를 red로 착각해 버그가 재현되지 않은 사례가 있다(mattpocock/skills#1210).
- 수용 기준은 최소선이지 최대선이 아니다. 스펙은 구현 세부를 담지 않으므로, 기준만 테스트하면 버그 재현, 복잡한 내부 로직의 경계 사례, 건드린 기존 동작이 빠진다.
- 실패하는 테스트를 약하게 만들지 않는다. Kent Beck이 겪었고 Anthropic의 장시간 하네스가 금지하는 실패다. 구현을 한꺼번에 하면 실패가 무더기로 나오므로, 실행 후 테스트를 고칠 때 근거 줄을 대게 해서 "테스트가 틀렸다"는 탈출구를 좁힌다.
- 런타임 증거는 테스트로 대신하지 않는다. 기존 `implement` 규칙이 그렇고, 이번 변경은 그 규칙을 바꾸지 않는다.
- 기준과 검증 수단을 대응시키는 일은 `implement`가, seam 선택은 `testing`이 맡는다. 런타임 증거와 최종 보고가 이미 `implement`에 있고, `testing`은 진행 중인 결과 전체를 보고 설계하기 때문이다.

## 가정 (수정 가능)

- 구현 뒤 리팩터링은 테스트가 계속 통과하는 한 허용하고, 끝난 변경의 리뷰는 그 작업을 맡은 흐름이 한다는 지금 규칙을 유지한다.
- 마켓플레이스 검색 키워드의 `tdd`는 사용자가 찾을 수 있도록 남긴다.
- `triage-issues`와 `resolve-follow-ups`는 자기 흐름 안에 둔 테스트 문구를 유지하고 `testing`을 부르지 않는다. 두 스킬을 맞추는 일은 이번 범위 밖이다.
- 비교 평가의 과제, 숨긴 테스트, 껍데기 구현, 채점 기준은 저장소에 남긴다.

## 범위 밖

- hook으로 테스트 순서나 실패 확인을 강제하는 일. 규칙은 스킬 본문에만 둔다.
- 검증 방법만 따로 고르는 새 스킬. 기준별 검증 수단은 `implement` 안에서 정한다.
- `implement`의 런타임 증거, 자동 리뷰, 실행 가능한 결과 전달 규칙. 이번 변경은 테스트 쪽 경계만 바꾼다.
- `shape-idea`가 수용 기준을 쓰는 방식. 기준 자체가 틀리거나 모호한 문제는 shaping과 리뷰가 맡는다.
- `tdd`를 언급하는 다른 스펙 폴더. 완료된 스펙의 정리는 `maintain-project-context`가 맡는다.

## 남은 위험

- 비교 평가는 과제 두 개, 실행 각 3회라서 차이가 우연일 수 있다. 우리 세션에서 `tdd` 루프가 실제로 어땠는지는 보지 않았다.
- 에이전트가 assertion 실패를 관찰하지 않고 지어낸 출력을 적을 수 있다. 실제 출력 발췌를 요구해 어렵게 만들 뿐, 리뷰가 실행 기록을 보지 않으면 잡히지 않는다.
- 지키는 대상을 밝히라는 규칙은 느슨하면 이유를 지어내 테스트가 늘고, 엄격하면 필요한 경계 사례 테스트가 빠질 수 있다.
- `testing`은 흔한 이름이라 다른 출처의 스킬과 겹칠 수 있다. skills.sh는 이름으로 중복을 지우므로, 겹치면 한쪽만 설치된다.
- 이름이 바뀌면 `/tdd`로 직접 부르던 사용자는 새 이름을 알아야 한다. skills.sh로 `implement`만 따로 설치한 사용자는 `testing`이 없어서 `implement`가 멈춘다.
- `triage-issues`와 `resolve-follow-ups`가 테스트를 쓰는 방식이 `testing`과 어긋난 채로 남는다.
