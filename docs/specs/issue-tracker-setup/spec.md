# 이슈 트래커로 스펙 폴더를 병렬 조정하기

## 목적과 승인 범위

`docs/specs/<slug>/` 폴더 여러 개를 서로 다른 세션이 동시에 구현할 수 있게,
저장소 밖 이슈 트래커를 **조정 층**으로 붙인다. 스펙 폴더는 지금처럼 유일한
계약이고, 이슈는 그 폴더를 가리키는 포인터와 클레임·선행 관계만 담는다.

2026-09-18 사용자가 다음을 승인했다.

- 새 스킬 `setup-issue-tracker`가 저장소마다 한 번 트래커 규약을 기록한다.
- 이슈는 스펙 폴더가 default branch에 들어가는 머지 시점에 `merge`가 만든다.
  shaping이나 task 분할 시점에는 트래커를 건드리지 않는다.
- `setup-issue-tracker`를 실행하지 않은 저장소에서는 다른 모든 스킬이 지금과
  똑같이 동작한다. 트래커는 옵트인이다.
- GitHub Issues 하나에 고정하지 않는다. 규약이 트래커를 정한다.

2026-09-22 사용자가 다음 확장을 승인했다.

- `merge`는 머지 직후 변경된 스펙의 이슈를 증분 동기화하고,
  `maintain-project-context`는 원격 default branch 전체와 관리 이슈 전체를
  주기적으로 대조해 누락과 drift를 복구한다.
- tracker는 계속 파생 조정층이다. 이슈 본문이나 댓글은 제품 의미의 근거로
  프로젝트 문서에 역수입하지 않는다.
- 같은 정확한 `spec:<slug>` 키를 쓰는 이슈가 여러 개면 자동으로 하나를 고르거나
  닫지 않고 모두 보고한다.

## 요구 동작

### 트래커 규약

1. `setup-issue-tracker`는 사용자가 직접 부르는 스킬이다. 저장소를 살펴
   원격 호스트, 기존 `AGENTS.md`/`CLAUDE.md`, 기존 트래커 섹션, 사용 가능한
   트래커 도구를 파악한 뒤 추천안을 먼저 제시하고 한 번에 한 항목씩 확인한다.
2. 확인된 규약은 `AGENTS.md` 또는 `CLAUDE.md`의 이슈 트래커 섹션에 기록한다.
   둘 중 이미 있는 파일을 고치고, 둘 다 있으면 `AGENTS.md`에 쓰며, 둘 다
   없으면 어느 쪽을 만들지 사용자에게 묻는다. 이미 섹션이 있으면 제자리에서
   갱신하고 주변 내용은 보존한다. 섹션을 읽는 스킬은 두 파일을 모두 보고 먼저
   찾은 섹션을 쓴다.
3. 규약은 트래커 이름, 스펙 폴더와 이슈를 잇는 키, 사용할 도구, 그리고 다른
   스킬이 부르는 일곱 동작을 정한다: 모든 상태의 관리 이슈 열거, 폴더에
   대응하는 이슈 찾기(열림 여부, 담당자, 열린 선행 이슈를 함께 돌려준다), 이슈
   발행, 파생 제목·본문 갱신, 오래된 edge를 제거하고 빠진 edge를 추가하는 선행
   관계 전체 갱신, 클레임, 닫기. 열거 동작은 식별자, 제목, 상태를 반환해 고아와
   중복 키를 찾을 수 있게 한다. GitHub Issues와 Linear는 템플릿에서 시작하고,
   그 밖의 트래커는 사용자의 한 문단 서술을 그대로 적는다.
4. 다시 실행하면 기존 규약을 보여 주고 바꿀 항목만 고친다.
   `List managed issues`가 없는 예전 규약은 tracker·key·tool과 이미 완전한
   동작을 보존한 채 그 동작을 추가한다. 동시에 본문만 바꾸던 동작은 파생
   제목·본문 전체 갱신으로, edge를 추가만 하던 동작은 오래된 edge 제거와 빠진
   edge 추가가 모두 가능한 전체 갱신으로 현대화한다.

### 머지 시점 이슈 정리

5. `merge`는 머지가 확인된 뒤 트래커 섹션이 있을 때만 이슈를 정리한다.
   머지 범위에 추가된 `docs/specs/<slug>/`마다 이슈를 발행하고, spec.md가
   바뀐 폴더는 이슈 본문을 다시 만들어 덮어쓰며 `Blocked by`가 바뀌었으면
   선행 관계를 갱신하고, 삭제된 폴더의 열린 이슈는 닫는다.
6. 이슈 본문은 사람이 쓰는 글이 아니라 spec.md에서 뽑아낸 파생물이다. 제목에
   키, 본문에 spec.md의 첫 제목, 첫 섹션의 본문, 그 아래 모든 섹션 제목, 폴더
   경로, 선행 스펙의 이슈를 담아 트래커만 보고도 그 스펙이 무엇인지 알 수 있게
   한다. 추출은 섹션 이름이 아니라 문서 구조로 하므로 스펙의 언어와 무관하다.
   본문은 `merge`가 매번 다시 만들므로 손으로 고치지 않으며, prototype.html,
   tasks/, 수용 기준 전문은 저장소에서 읽는다.
7. `merge`는 같은 실행에서 default branch에 있으나 이슈가 없는 스펙 폴더도
   함께 발행한다. 다른 경로로 머지된 PR을 다음 `merge`가 따라잡고, 같은
   폴더에 이슈가 둘 생기지 않는다. 따라잡기에서는 열려 있든 닫혀 있든 키가
   맞는 이슈가 하나라도 있으면 발행하지 않으므로, 출하 뒤 아직 치우지 않은
   폴더에 이슈가 다시 생기지 않는다. 머지 범위에 새로 추가된 폴더는 닫힌
   이슈만 있어도 새 이슈를 발행한다.
8. 이슈 정리 실패는 이미 확인된 머지를 되돌리지 않는다. 실패한 동작과
   원인을 결과에 보고하고 다음 `merge`의 따라잡기에 맡긴다.

### 주기적 전체 이슈 정리

9. `maintain-project-context`는 트래커 섹션이 있을 때 원격이 광고하는 default
   branch를 fetch하고, 그 revision의 `docs/specs/<slug>/`와 모든 관리 이슈를
   대조한다. 현재 checkout에만 있는 미머지 변경은 tracker에 반영하지 않는다.
10. 정확한 키의 이슈가 없으면 발행하고, 하나면 원격 `spec.md`에서 제목과 본문을
    재생성하고 오래된 edge 제거와 빠진 edge 추가로 선행 관계 전체를 맞춘다.
    이때 assignee와 열린/닫힌 상태는 보존하며, 폴더가 남았다는 이유만으로 닫힌
    이슈를 다시 열지 않는다.
11. 원격 default branch에 폴더가 없는데 관리 이슈가 열려 있으면 닫고, 이미
    닫힌 고아 이슈는 그대로 둔다. 같은 정확한 키의 이슈가 여러 개면 식별자와
    상태를 모두 보고하고 어느 것도 고치지 않는다.
12. 예전 규약에 관리 이슈 열거 동작이 없으면 default branch의 각 폴더를 `Find`
    해서 가능한 단방향 동기화만 수행한다. 고아와 중복 검색은 완료로 보고하지
    않고 `setup-issue-tracker` 재실행이 필요하다고 알리며, tracker별 명령을
    임의로 추측하지 않는다.
13. tracker 도구가 없거나 동작이 실패해도 저장소 안의 맥락 정리는 계속한다.
    끝나지 않은 tracker 동작과 원인을 보고하고 나머지 외부 상태는 보존한다.

### 클레임과 구현

14. `implement`의 입력은 지금처럼 `docs/specs/<slug>/` 폴더 하나다. 이슈
    번호를 입력으로 받지 않는다. 트래커가 없어도 워크플로가 같은 입력으로
    동작해야 하기 때문이다.
15. 트래커 섹션이 있으면 `implement`는 폴더의 slug로 이슈를 찾아 첫 쓰기로
    자신을 담당자로 지정한 뒤 지금의 흐름을 그대로 따른다. 담당자가 이미
    있는데 그것이 현재 트래커 계정이면 재개로 보고 진행하고, 다른 계정이거나
    열린 선행 이슈가 있으면 소스를 바꾸지 않고 그 사실을 보고한다. 대응하는
    이슈가 없으면 그냥 진행한다. 규약이 정한 트래커 도구를 현재 세션에서 쓸 수
    없으면 클레임 없이 진행하지 않고 멈춰 보고한다. 충돌 방지가 이 기능의
    존재 이유이므로 사용자가 명시적으로 지시할 때만 클레임 없이 진행한다.
16. `implement`는 자기 커밋에 `Spec-Folder: docs/specs/<slug>/` 트레일러를
    남긴다. 트래커 섹션이 있을 때 PR을 만드는 `pr`과 `merge`는 그 트레일러로
    이슈를 찾아 PR 본문에 규약이 정한 닫기 참조를 넣고, 자동 닫힘이 없는
    트래커는 `merge`가 머지 확인 뒤 규약대로 직접 닫는다.

### 스펙 간 선행 관계

17. 스펙 폴더 사이의 선행 관계는 spec.md의 `Blocked by` 항목에
    `docs/specs/<other>/` 경로로 적는다. 항목 이름은 스펙의 언어와 무관하게
    영어로 고정한다. 스킬은 영어로 공개되어 다른 프로젝트에 설치되므로
    `merge`가 찾는 이름이 언어에 따라 달라지면 안 된다. `shape-idea`는 다른 스펙 폴더에
    의존하는 결정을 내릴 때 이 항목을 쓴다. `merge`가 이 항목을 이슈의 선행
    관계로 옮긴다.

### 트래커가 없을 때

18. 트래커 섹션이 없으면 `merge`, `pr`, `implement`,
    `maintain-project-context`는 현재 동작과 같다.
    `shape-idea`의 `Blocked by` 항목과 `implement`의 커밋 트레일러는 저장소
    안 정보라 트래커와 무관하게 늘 쓴다. 어떤 스킬도 `setup-issue-tracker`를
    요구하거나 그 텍스트를 가정하지 않으며, 필요한 규칙은 각 스킬 본문에
    스스로 담는다.

## 수용 기준

- 트래커 섹션이 없는 저장소에서 `merge`, `pr`, `implement`의 관찰 가능한
  동작이 변경 전과 같다. `Blocked by` 항목과 커밋 트레일러는 예외다.
- `setup-issue-tracker` 실행 후 `AGENTS.md` 또는 `CLAUDE.md` 한 파일에
  섹션이 하나만 있고, 일곱 동작과 키가 모두 적혀 있다. 두 번째 실행은 파일을
  하나 더 만들거나 섹션을 중복시키지 않는다.
- 예전 여섯 동작 규약을 다시 설정하면 tracker·key·tool과 완전한 기존 동작은
  유지하고, 모든 관리 이슈를 제한 없이 열거하는 일곱 번째 동작을 추가하며,
  body-only 및 additive-only 갱신 동작은 완전 교체 동작으로 현대화한다.
- 스펙 폴더를 추가하는 PR을 `merge`로 머지하면 그 폴더의 이슈가 하나 생기고,
  본문에 spec.md의 첫 제목, 첫 섹션 본문, 나머지 섹션 제목, 경로가 있다.
  영어 제목만 있는 스펙에도 같은 구조로 채워진다.
- 이슈가 닫혔지만 폴더가 남아 있는 상태에서 `merge`를 실행해도 새 이슈가
  생기지 않는다.
- spec.md를 고친 PR을 `merge`로 머지하면 같은 이슈의 본문이 새 내용으로
  바뀌고 이슈 번호와 담당자는 유지된다.
- 다른 경로로 머지돼 이슈가 없던 폴더가 다음 `merge` 실행에서 발행되고, 이미
  이슈가 있는 폴더는 다시 발행되지 않는다.
- `Blocked by`가 적힌 폴더의 이슈는 선행 폴더의 이슈에 막힌 상태로 생성되고,
  선행 이슈가 열려 있는 동안 `implement`는 시작하지 않는다.
- 트래커 섹션이 있는 저장소에서 `implement`에 폴더 경로를 주면 첫 쓰기가
  담당자 지정이고, 담당자가 다른 계정이면 소스를 바꾸지 않고 끝나며, 담당자가
  현재 계정이면 재개한다.
- 트래커 도구가 없는 세션에서 `implement`는 소스를 바꾸지 않고 멈춰 보고한다.
- `implement`의 구현 커밋에 `Spec-Folder` 트레일러가 있고, `pr` 또는 `merge`가
  만든 PR 본문에 닫기 참조가 있으며, 구현 PR이 머지되면 클레임된 이슈가
  닫힌다.
- 이슈 정리 도구가 없는 세션에서 `merge`는 머지를 완료하고 정리 실패를
  보고한다.
- `maintain-project-context`는 원격 default branch에 있는 모든 스펙을 기준으로
  빠진 이슈를 만들고, 파생 제목·본문과 blocker 전체를 갱신하고, 열린 고아
  이슈를 닫는다. 닫힌 이슈는 다시 열지 않고 assignee를 보존한다.
- 같은 정확한 키의 이슈가 여러 개면 모두 보고하고 어느 것도 변경하지 않는다.
  이슈 댓글의 미확정 제품 요구는 저장소의 권위 문서에 옮기지 않는다.
- 관리 이슈 열거 동작이 없는 규약에서는 가능한 폴더별 동기화만 하고, 고아·중복
  검사가 불완전하다는 사실과 설정 업그레이드 필요를 보고한다.
- 새 스킬은 두 배포 채널(skills.sh, 플러그인)과 두 하네스(Claude Code,
  Codex)에서 호출된다.
- 스킬 본문, 공개 설명, 결정 계약이 같은 동작을 설명한다.

## 설정된 제약과 근거

- **이슈 본문은 파생물이다.** 사람이 이슈에 직접 쓰면 `babysit-specs`가
  spec.md를 고칠 때마다 이슈도 고쳐야 하고 둘 중 하나가 낡는다. 이 저장소에서
  스펙 아홉 개 중 셋이 사후 편집됐던 사례가 그 위험이다. 본문을 `merge`가
  spec.md에서 매번 다시 만들면 트래커에서 읽을 만큼 담으면서도 출처는 하나로
  남는다. prototype.html과 tasks/는 어차피 이슈에 들어갈 수 없다.
- **`implement`의 입력은 폴더다.** 트래커가 없어도 같은 명령이 같은 일을 해야
  하므로 이슈 번호는 입력이 아니다. 이슈는 폴더에서 키로 찾는다.
- **발행은 머지 시점이다.** shaping 시점에 발행하면 폴더가 default branch에
  들어가기 전까지 이슈의 경로가 깨져 있다. 머지 시점에 만들면 그 구간이 없다.
- **병렬 단위는 스펙 폴더다.** 사용자의 병목은 스펙 간 병렬이고, 폴더 안
  task는 `implement`가 저장소 안에서 순차로 다룬다. task까지 이슈로 올리면
  상태 carrier가 둘이 된다. 담당자 표시가 폴더가 아니라 이슈에 있는 이유는
  브랜치 가시성이다: 폴더 안 파일은 그 브랜치에만 있어 main을 본 다른 세션이
  같은 폴더를 또 잡지만, 이슈의 담당자는 쓰는 순간 모든 세션에 보인다.
- **트래커는 옵트인이다.** skills.sh 사용자는 스킬을 하나씩 설치하므로,
  어떤 스킬도 다른 스킬의 실행이나 텍스트를 전제하지 않는다.
- **`merge`와 `maintain-project-context`가 서로 다른 범위를 정리한다.** CI
  워크플로는 GitHub Actions와 GitHub Issues에 묶이지만 두 스킬은 규약이 말하는
  트래커를 따른다. `merge`는 방금 머지된 변경을 증분 반영하고,
  `maintain-project-context`는 원격 default branch 전체를 기준으로 누락과 drift를
  복구한다.

## 가정

- 클레임된 이슈는 폴더 retirement가 아니라 구현 PR 머지에서 닫힌다.
  트래커의 "done"이 실제 출하 시점과 일치한다. 사용자가 덮어쓸 수 있다.
- 키는 이슈 제목 앞의 `spec:<slug>`이며, 뒤에 공백이나 제목의 끝이 와야
  일치한다. `spec:checkout`은 `spec:checkout-v2`와 일치하지 않는다. 라벨을
  쓸 수 없는 트래커에서도 동작한다.
- 규약은 별도 파일 없이 `AGENTS.md`/`CLAUDE.md` 섹션 안에 직접 둔다. 자유
  서술이 한 문단을 넘으면 `setup-issue-tracker`가 파일로 분리하고 섹션은
  라우트만 남긴다.
- 새 스킬은 `workflow` 그룹에 들어간다.
- Linear 템플릿은 조작만 정하고, 도구(MCP 또는 CLI)는 setup이 그 세션에서
  실제로 쓸 수 있는 것을 확인해 채운다.

## 범위 밖

- task 단위 이슈, triage 라벨 어휘, 프론티어 자동 선택 스킬: 병렬 단위가
  스펙 폴더이므로 필요하지 않다.
- `.github/workflows`로 이슈를 동기화하는 CI: GitHub에 고정된다.
- `merge`의 PR 호스팅을 GitLab 등으로 넓히는 일: 트래커 중립은 이슈 위치에
  한정된다.
- follow-up을 트래커로 옮기는 일: `document-lifecycles`의 기존 결정을 유지한다.
- `shape-idea`, `split-into-tasks`, `babysit-specs`가 트래커에 쓰는 일:
  증분 반영은 `merge`, 전체 복구는 `maintain-project-context`가 맡는다.
  `babysit-specs`의 결과는 머지될 때 반영된다.
- `resolve-follow-ups`의 worktree·워커 모델 변경.

## 유보된 점

- `implement`가 폴더 없이 프론티어(열려 있고, 담당자 없고, 선행이 닫힌
  이슈)를 스스로 골라 잡는 동작. 사용자가 폴더를 지정하는 것으로 시작하고,
  자동 선택은 실제 병렬 사용에서 필요가 드러나면 별도 shaping으로 정한다.

## 의존하는 결정

- [파이프라인](../../decisions/pipeline.md): 순차 구현 기본값과 "사용자가
  병렬 실행 모델을 선택하면 재고" 조건. 이 작업이 그 조건에 해당하므로 구현이
  같은 계약에 스펙 폴더 단위 병렬과 옵트인 트래커를 반영한다.
- [문서 수명](../../decisions/document-lifecycles.md): 스펙 폴더의 수명과
  "호스팅 트래커를 follow-up carrier로 쓰지 않는다"는 결정. 후자는 유지하고
  스펙 폴더에만 트래커를 붙인다.
- [스킬 설계](../../decisions/skill-design.md): 독립 실행과 옵트인 규칙.
- [스킬 이름](../../decisions/skill-naming.md): `setup-issue-tracker`는
  사용자가 직접 부르는 verb-object 이름이며 출처 전통을 이름에 넣지 않는다.
- [스킬 배치](../../decisions/skill-layout.md): 새 스킬의 그룹과 배포 경로.
- [shape-idea](../../decisions/shape-idea.md): spec.md의 필드 목록. `Blocked by`
  항목은 그 목록 옆에 놓이는 링크이므로 구현이 같은 계약에 반영한다.
- [PR 설명](../../decisions/pr-descriptions.md): PR 본문의 구성. 닫기 참조가
  들어가므로 구현이 같은 계약에 반영한다.

## 남은 위험

- `merge`를 거치지 않는 머지가 잦으면 이슈 발행이 다음 `merge`나
  `maintain-project-context` 실행까지 늦어져 그 사이 다른 세션이 같은 스펙을
  잡을 수 있다. 사용 중 관찰한다.
- 클레임이 담당자 필드 하나에 의존하므로 두 세션이 같은 순간에 잡으면 트래커의
  마지막 쓰기가 이긴다. `resolve-follow-ups`와 같은 원자적 클레임은 두지 않는다.
- 같은 트래커 계정으로 도는 세션 둘은 담당자만으로 구분되지 않는다. 한 사용자의
  병렬 세션은 서로 다른 폴더를 지정하는 것으로 충돌을 피한다.
- Linear 등 자동 닫힘이 없는 트래커에서 `merge`가 닫기를 놓치면 이슈가 열린
  채 폴더만 사라진다. 다음 관련 `merge` 또는 `maintain-project-context`의 전체
  정리가 삭제된 폴더의 열린 이슈를 닫아 준다.
- 설정 스킬의 트리거 평가는 아직 없다. 사용자가 직접 부르는 스킬이라 설명문은
  사람이 읽는 한 줄로 충분하다.
