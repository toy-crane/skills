# 일반 이슈를 정리하고 다음 작업으로 연결하기

## 목적과 승인 범위

사람이 자유롭게 작성한 일반 이슈를 예약 실행에서 살펴, AI가 조사와 작은 판단을
스스로 끝내고 사람에게 필요한 결정만 충분한 맥락과 함께 요청한다. 사람은
원래 이슈 하나에서 조사 결과, 질문, spec, PR과 구현 진행을 이어서 볼 수
있어야 한다. 이 스킬은 Linear 전용이 아니며, 저장소가 설정한 이슈 트래커
규약을 따른다.

기존 `spec:<slug>` 이슈는 이미 저장소 spec 폴더에서 파생된 포인터다. 이
작업의 입력인 일반 이슈와 구별하며 triage 대상으로 삼지 않는다.

## 사용자에게 보이는 결과

- 명확하고 작은 이슈는 AI가 구현과 검증을 마친 PR로 이어진다. PR은 원래
  이슈에 연결되고 변경 이유, 확인한 동작, 남은 한계를 보여 준다.
- 요구 결과가 명확하지만 설계가 필요한 이슈는 AI가 저장소의 spec을 쓰고
  spec PR을 올린다. 같은 원래 이슈에 사람이 읽을 수 있는 spec 내용과 PR
  링크가 남는다. PR이 열려 있는 동안 spec은 초안으로 표시하고, 병합된
  내용으로 동기화한다. spec PR이 병합돼도 새 포인터 이슈를 만들지 않으며, 기존
  spec 구현 흐름이 같은 이슈를 이어받는다. 이 triage 실행은 spec PR에서
  끝나고 구현까지 중복으로 시작하지 않는다.
- 정보가 부족하거나 제품 선택이 필요한 이슈는 그 이슈 안에 답할 질문이
  남는다. 사용자는 여러 문서를 다시 조사하지 않고 선택지, AI의 추천과
  근거, 선택의 결과를 보고 답할 수 있다.
- 이슈 본문에서 제보자의 원문은 보존된다. AI가 갱신하는 `Triage 요약`은
  확인된 사실, 현재 단계, 다음 행동을 짧게 보여 준다. spec이 생기면 같은
  본문에 AI가 관리하는 spec 부분을 두고 저장소의 `spec.md`와 동기화한다.
  질문과 답변은 댓글에 남기고 확정된 내용은 요약과 spec에 반영한다.
- 새 결정 요청이 생긴 예약 실행에서만 결정이 필요한 이슈 링크를 묶어
  사용자에게 알린다. 다른 실행은 결과를 각 이슈와 PR에 남긴다.

## 승인된 범위

1. 저장소의 `setup-issue-tracker` 규약이 triage 대상, 상태/라벨 대응,
   도구, 원래 일반 이슈와 spec 폴더의 연결 방법을 정의한다. 기본 역할은
   `needs-triage`, `needs-info`, `needs-decision`이다. 트래커의 고유한
   Triage 기능을 활용할 수 있지만, 스킬의 동작은 특정 제품의 상태 모델에
   묶이지 않는다. 작업 중 표시용 `agent-working` 라벨은 필수가 아니다.
2. 처음에는 기존의 열린 일반 이슈와 Backlog도 후보에 넣는다. 이후에도
   새 이슈, 사람의 새 댓글, 본문 수정이 있는 이슈를 놓치지 않고 재평가한다.
   한 예약 실행은 적격 이슈를 최대 3개 순서대로 살피고 PR은 최대 1개만
   올린다. 정보나 결정 요청만 남긴 경우 남은 후보를 계속 살핀다.
3. 이미 작업 중이거나 PR이 연결된 이슈, `spec:<slug>` 포인터 이슈는
   건너뛴다. 단, `needs-info` 또는 `needs-decision`에 새 사람 답변이나
   본문 수정이 있으면 다시 후보가 된다. 답변을 읽고 즉시 재평가하여
   기다림 라벨만 제거한 채 중간 상태로 방치하지 않는다.
4. 동시에 도는 실행은 같은 이슈를 둘 다 처리하지 못해야 한다. 작업을
   시작하기 전 공유된 원자적 클레임을 얻고, 얻지 못하면 다음 후보로
   넘어간다. 중단된 실행은 복구되며, 재시도는 기존 댓글·spec·PR을
   확인해 중복 게시와 중복 PR을 피한다. 표시용 라벨이나 담당자만으로
   배타성을 주장하지 않는다.
5. AI는 원문, 첨부, 댓글, 저장소의 현재 동작과 관련 결정을 조사한다.
   예상 결과가 충분히 명확하고 변경이 작으면 바로 구현한다. 결과는
   명확하지만 여러 기능에 걸치거나 중요한 설계 선택을 기록해야 하면
   spec을 쓴다. 필요한 사실이 없으면 `needs-info`, 제품 동작을 바꿀
   선택이 남았으면 `needs-decision`으로 보낸다. 쉬워 보이는 구현도
   원하는 결과가 불명확하면 먼저 묻는다.
6. 결정 요청은 한 번에 결정할 질문, 가능한 선택지와 각각의 결과, AI의
   추천과 근거를 포함한다. 실제 화면, 재현 절차, 스크린샷, 짧은 영상,
   비교 자료, 로그, 동작 링크 등 판단 시간을 줄이는 증거를 필요에 따라
   만들어 이슈에서 바로 볼 수 있게 한다. 관찰한 사실, 추론, 아직
   확인하지 못한 점을 구분한다. 자료를 만들 수 없으면 그 빈자리가
   결정에 미치는 영향을 설명한다.
7. 별도의 결정권자 설정은 요구하지 않는다. 사람의 답변이 명확하면
   결정으로 반영한다. 답변이 모호하거나 서로 충돌하면 추측해 진행하지
   않고 같은 이슈에서 필요한 차이만 다시 확인한다.
8. 명백한 중복 요청이나 이미 구현된 동작은 연결된 근거와 이유를 남기고
   정리할 수 있다. 새로운 기능이나 제품 요청을 진행하지 않겠다는 판단은
   AI가 단독 확정하지 않고 추천안과 함께 사용자에게 맡긴다.

## 관찰 가능한 수용 기준

- 설정된 트래커의 열린 일반 이슈를 예약 실행으로 처리할 때, Backlog를
  포함해 최대 3개를 살피고 둘 이상의 PR을 만들지 않는다. 작업 중 이슈,
  연결 PR이 있는 이슈, `spec:<slug>` 이슈는 가져가지 않는다.
- 같은 이슈를 두 실행이 동시에 발견해도 한 실행만 댓글·본문·브랜치·PR을
  만들 수 있다. 중단 뒤 재실행해도 이미 만든 산출물이 복제되지 않는다.
- 사람의 원문이나 새 본문 수정을 잃지 않으면서 AI 관리 부분만 갱신한다.
  사람이 댓글에 답하거나 본문을 고친 기다림 이슈는 다음 실행에 다시
  평가되고, 확정된 답변이 최신 요약에 반영된다.
- 명확한 작은 요청은 실제 변경과 검증 근거가 있는 구현 PR에 도달한다.
  설계가 필요한 명확한 요청은 spec PR에 도달하고, 그 PR이 병합된 뒤에도
  구현은 원래 일반 이슈를 사용한다. 새 `spec:<slug>` 이슈가 생기지 않는다.
- 정보 부족과 미확정 제품 선택은 서로 다른 기다림 상태와 구체적인
  질문으로 나타난다. 결정 요청에는 추천안과 선택별 영향, 필요한 시각적
  또는 실행 증거가 제공된다. 새 결정 요청이 없는 실행은 사용자에게
  별도 묶음 알림을 보내지 않는다.
- AI가 중복·이미 해결됨을 판정하면 근거를 볼 수 있다. 새로운 요청의
  거절은 사람의 답변 전까지 확정되지 않는다.

## 설정된 제약과 근거

- **원래 이슈 하나가 이어진다.** 일반 이슈에서 spec이 나온 경우 기존
  포인터 이슈를 하나 더 만들면 사용자가 두 기록의 차이를 파악해야 하고
  업데이트도 갈라진다. spec 폴더와 PR은 같은 이슈에서 찾을 수 있어야 한다.
- **본문은 현재 상태, 댓글은 대화 기록이다.** AI가 매번 긴 댓글을
  재구성하지 않아도 현재 결론을 읽을 수 있다. 제보 원문과 AI 관리 부분을
  구분해 사람이 수정한 내용을 덮어쓰지 않는다.
- **spec.md가 구현 계약이다.** 이슈의 spec 부분은 저장소 계약을 읽기
  쉽게 보여 주는 동기화된 표현이다. 구현에 필요한 승인된 자료와 spec의
  수명은 기존 저장소 규약을 따른다.
- **자동 판단은 조사와 근거가 있는 범위에 한정한다.** 부족한 제품 의미를
  AI의 추측으로 채우면 검토 비용이 뒤로 밀린다. 사람에게 물을 때는
  선택에 필요한 맥락까지 AI가 준비한다.

## 가정

- 스킬 이름은 `triage-issues`, 배포 그룹은 `workflow`로 시작한다.
- 한 실행의 상한은 적격 이슈 3개와 PR 1개이며, 실제 운영 결과에 따라
  설정에서 조정할 수 있다.
- 명확한 사람 답변은 작성자 역할을 별도로 검사하지 않고 반영한다.
  충돌이 드러나면 재질문한다.

## 범위 밖

- 예약 주기와 특정 저장소·팀의 실제 트래커 연결 설정. 스킬은 예약
  실행 가능하게 만들고, 연결은 해당 저장소의 설정을 읽는다.
- spec PR 병합 후 구현을 이 triage 실행에서 자동 시작하는 일. 기존
  spec 구현 흐름이 같은 원래 이슈로 진행한다.
- 이미 존재하는 `spec:<slug>` 포인터 이슈를 일반 이슈로 변환하는 일.
- 새 기능 요청을 AI가 독자적으로 거절하는 일.

## 유보된 점

- 없음. 첫 운영에서 이슈 처리 상한, 시각 자료의 효용, 결정 요청의
  재질문 빈도는 관찰하여 조정한다.

## 의존하는 결정

- [파이프라인](../../decisions/pipeline.md): spec 폴더, 구현, PR,
  병합 후 이슈 조정의 기존 수명. 일반 이슈에서 출발한 작업은 같은
  이슈를 이어 사용하도록 확장한다.
- [문서 수명](../../decisions/document-lifecycles.md): `spec.md`가
  구현 계약이고 Git이 변경 이력을 보존한다.
- [스킬 설계](../../decisions/skill-design.md): 독립 설치 가능한 스킬과
  근거 있는 고정 절차.
- [스킬 이름](../../decisions/skill-naming.md): 직접 실행할 수 있는 짧은
  동사·목적어 이름.
- [스킬 배치](../../decisions/skill-layout.md): 범용 워크플로 스킬의
  배포 위치.
- [PR 본문](../../decisions/pr-descriptions.md): 변경 이유, 검증,
  시각 자료의 기존 PR 설명 규약.

## 남은 위험

- 설정된 트래커가 원자적 클레임이나 필요한 첨부를 직접 지원하지 않을 수
  있다. 구현은 실제 도구의 동작을 검증하고, 같은 이슈를 단독으로 소유할
  수 없으면 쓰지 않은 채 다음 실행에 맡겨야 한다.
- spec을 쓰는 PR과 사람이 원래 이슈를 편집하는 시점이 겹칠 수 있다.
  동기화 직전에 최신 원문을 확인하지 않으면 새 정보를 잃거나 오래된
  spec을 게시할 수 있다.
- 기존 `spec:<slug>` 키만으로 찾고 발행하는 규약은 원래 일반 이슈를
  재사용하지 못한다. setup, merge, implement, PR 연결과 전체 동기화의
  해당 경로를 함께 바꾸지 않으면 중복 이슈가 생긴다.
