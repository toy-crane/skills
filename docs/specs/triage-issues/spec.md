# 새 일반 이슈를 한 번 판단하고 다음 작업으로 넘기기

## 목적과 승인 범위

사람이 자유롭게 작성한 새 일반 이슈를 AI가 한 번 판단해, 사람이 이슈마다 어디로
보낼지 정하지 않아도 되게 한다. triage는 판단만 하고, 구현은 `implement`, 질문과
결정은 `shape-idea`에 같은 실행 안에서 넘긴다. 이 스킬은 특정 트래커 전용이
아니며, 저장소가 설정한 이슈 트래커 규약을 따른다.

spec 폴더가 `Issue:` 줄로 가리키는 이슈는 리뷰 중이거나 구현을 기다리므로
이 작업의 입력인 일반 이슈와 구별하며 triage 대상으로 삼지 않는다.

2026-10-02에 역할을 나눴다. 그 결정과 근거는
[issue-skill-roles](../issue-skill-roles/spec.md)에 있다.

## 사용자에게 보이는 결과

- 중복이나 이미 구현된 요청은 연결된 근거와 함께 닫힌다.
- 결과가 분명하고 작은 요청은 같은 실행에서 `implement`로 이어져, 원래 이슈를
  닫는 구현 PR이 된다.
- 정보나 결정이 필요한 요청, 큰 변경이라 계약을 써야 하는 요청은 같은 실행에서
  `shape-idea` 대화로 이어진다. 첫 질문은 `shape-idea`가 쓴다.
- 이슈 본문에서 제보자의 원문은 보존된다. AI가 갱신하는 `Triage 요약`은 확인된
  사실, 판단과 이유, 다음 단계를 짧게 보여 준다. 판단 결과는 규약의 라벨·상태로도
  남는다.
- 판단한 이슈는 다음 실행에서 다시 판단되지 않는다.

## 승인된 범위

1. 저장소의 `setup-issue-tracker` 규약이 triage 대상, "아직 판단하지 않음"
   조회, 판단 결과의 라벨·상태 대응, 요약 구역 표식, 도구를 정의한다. 판단
   결과는 `needs-info`, `needs-decision`, 구현 대기, 완료 처리다. 트래커의 고유한
   Triage 기능을 활용할 수 있지만, 스킬의 동작은 특정 제품의 상태 모델에 묶이지
   않는다.
2. 이슈 번호를 받으면 그 하나만 다룬다. 받지 않으면 "아직 판단하지 않음" 조회가
   돌려준 이슈를 오래된 순서로 본다. 중복·이미 됨은 닫고 다음으로 넘어가며,
   처음 넘긴 이슈에서 멈춘다. 한 실행은 이슈 하나만 넘긴다.
3. 이미 작업 중이거나 리뷰 신호가 있거나 열린 PR이 연결된 이슈, default branch의
   spec 폴더가 `Issue:` 줄로 가리키는 이슈는 건너뛴다. 제목으로 거르지 않는다.
   이미 판단한 이슈는 사람이 다시 판단하라고 분명히 말할 때만 다시 판단한다.
4. 동시에 도는 실행은 같은 이슈를 둘 다 판단하지 못해야 한다. 판단을 쓰기 전에
   공유된 원자적 클레임을 얻고, 얻지 못하면 다음 후보로 넘어간다. 판단을 쓴 뒤
   넘기기 전에 클레임을 푼다. 표시용 라벨이나 담당자만으로 배타성을 주장하지
   않는다.
5. AI는 원문, 첨부, 댓글, 저장소의 현재 동작과 관련 결정을 조사한다. 댓글은
   판단 근거로만 읽고, 언제 다시 실행할지는 실행하는 쪽이 정한다.
6. 넘기기 전에 요약 구역과 판단 결과를 먼저 쓴다. 넘길 스킬이 없거나 실패해도
   판단은 남고, 사람이 할 다음 단계를 보고한다.
7. 새 제품 요청을 진행하지 않겠다는 판단은 AI가 단독 확정하지 않는다. 그런
   요청은 결정이 필요한 요청으로 `shape-idea`에 넘긴다.

## 관찰 가능한 수용 기준

- 번호를 받은 실행은 그 이슈 하나만 다룬다. 번호 없는 실행은 판단하지 않은
  이슈만 고르고, 넘긴 이슈가 하나 생기면 멈춘다.
- 같은 이슈를 두 실행이 동시에 발견해도 한 실행만 판단을 쓴다.
- 사람의 원문이나 새 본문 수정을 잃지 않으면서 요약 구역만 갱신한다.
- 대기 중인 이슈에 사람이 댓글을 달거나 본문을 고쳐도 triage가 그 이슈를 다시
  고르지 않는다.
- triage는 소스를 바꾸거나 spec을 쓰거나 질문 댓글을 남기거나 PR을 열지 않는다.
- AI가 중복·이미 해결됨을 판정하면 근거를 볼 수 있다.

## 설정된 제약과 근거

- **원래 이슈 하나가 이어진다.** 이슈에서 출발한 spec과 구현 PR은 같은 이슈를
  `Issue:` 줄로 가리킨다. 새 이슈를 만들지 않는다.
- **본문은 현재 상태다.** AI가 관리하는 요약 구역만 갱신하고 제보 원문은 두어,
  사람이 수정한 내용을 덮어쓰지 않는다.
- **판단은 조사와 근거가 있는 범위에 한정한다.** 부족한 제품 의미를 AI의 추측으로
  채우지 않고 `shape-idea`의 대화로 넘긴다.
- **사람이 답했는지는 실행하는 쪽이 안다.** 댓글 작성자·시각·본문 지문으로 답을
  추측하지 않는다.

## 가정

- 스킬 이름은 `triage-issues`, 배포 그룹은 `workflow`다.
- 요약 구역이 있는 이슈는 판단한 이슈로 본다. 사람이 요약 구역을 지우면 다시
  판단 대상이 된다.

## 범위 밖

- 예약 주기, 실행기, 특정 저장소·팀의 실제 트래커 연결 설정.
- 구현, spec 작성, 질문과 답 받기. 각각 `implement`와 `shape-idea`가 맡는다.
- 합치지 않고 닫힌 spec PR의 이슈를 되돌리는 일. 사람이 정한다.
- 새 기능 요청을 AI가 독자적으로 거절하는 일.

## 남은 위험

- 설정된 트래커가 원자적 클레임을 직접 지원하지 않을 수 있다. 같은 이슈를 단독으로
  소유할 수 없으면 쓰지 않은 채 다음 실행에 맡긴다.
- 요약 구역을 쓰는 시점과 사람이 원래 이슈를 편집하는 시점이 겹칠 수 있다. 쓰기
  직전에 최신 원문을 다시 읽고 쓴 뒤 확인한다.
- 실행기가 없는 프로젝트에서는 결정을 기다리는 이슈가 사람이 `shape-idea`를 다시
  실행할 때까지 멈춘다.
