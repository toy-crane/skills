# triage-issues 회귀 스위트

- 결정: [testing](../../decisions/testing.md). 회귀 스위트는 capability eval을 졸업시켜 만든다는 규칙, 동작이 바뀌지 않는 기존 스킬은 스킬 없음을 기준선으로 쓴다는 규칙, 셀 기록과 두 tier 규칙, 답하지 못한 시행은 결과가 아니라는 규칙을 정한다.
- 용어: [GLOSSARY](../../../GLOSSARY.md). Capability eval, 회귀 스위트, 졸업, 셀, 셀 기록의 정의다.

## 문제

`triage-issues`는 Robo가 새 이슈마다 사람 없이 실행하고, 결과를 Slack과 이슈 트래커에 올리고 PR도 연다. 잘못 동작하면 이미 사람이 보고 있는 이슈를 다시 건드리거나 측정값을 추정해서 적고, 실행 중에는 아무도 이를 보지 않는다. `test-claim.sh`와 `test-body-sections.sh`는 형식만 검사하고, 판단은 `skill-evals/triage-issues/evals.json`의 11개 케이스에 글로만 적혀 있다. 스킬 본문이나 모델이 바뀌어 이 동작이 깨져도 알아챌 방법이 없다.

## 사용자에게 보이는 결과

- `skill-evals/triage-issues/regression/` 아래에 회귀 스위트가 생긴다. 다른 스킬과 같은 방식으로 한 줄 명령으로 다시 돌릴 수 있다.
- 스위트의 각 셀은 스킬 없이 돌린 에이전트가 저지르는 실수 중 `triage-issues`가 실제로 막아 주는 것을 보여 준다.
- `regression/log.md`에 졸업 기록 한 줄이 남고, `cell-history.json`에 셀마다 시행 기록이 남는다.

## 승인된 범위

- `triage-issues`의 eval 루트(`skill-evals/triage-issues/`)에 러너, 케이스, grader를 만든다.
- 스킬 없음을 기준선으로 capability eval을 돌리고, 그린에 닿으면 회귀 스위트로 졸업시킨다.
- `triage-issues`의 `SKILL.md`는 바꾸지 않는다.

## 인수 기준

1. **지켜야 할 동작.** 현재 `triage-issues` 본문을 따른 에이전트가 다음을 지킨다.
   - 이미 분류한 이슈는 새 답글이 달려도 다시 해석하거나 요약을 고쳐 쓰지 않는다.
   - 기한이 지난 이슈를 기한 없는 이슈보다 먼저, 기한이 아직 오지 않은 이슈는 건드리지 않는다.
   - 한 번에 처리하는 이슈 수 한도를 지킨다.
   - 출시 뒤 점검 이슈는 측정 파일을 적힌 대로 돌리고, 돌릴 수 없으면 값을 추정하지 않는다.
   - 필수 스킬이 없으면 이슈를 claim하기 전에 멈추고 설치 명령을 알린다.
   - 처리할 것이 없으면 알림 없이 한 줄로 보고한다.
   - 지표: held-out 케이스의 (케이스 × 반복 × 검사 항목) 행 통과율. 끝 상태(대역 트래커에 남은 댓글, 상태, 라벨과 저장소 변경) 검사와 루브릭 판정으로 채점한다.
   - 목표: held-out 90% 이상, 반복 2회. 스킬 없이 돌린 기준선보다 노이즈 범위 밖으로 높다.
   - 케이스 출처: `skill-evals/triage-issues/evals.json`의 11개 케이스에서 시작하고, 실제 세션 기록에서 같은 상황의 변형을 뽑아 12개 이상으로 늘린다. train과 held-out으로 나눈다.
2. **졸업.** 모든 반복에서 통과한 케이스만 `regression/`으로 옮긴다. grader와 그것이 읽는 픽스처를 함께 옮기고, climb의 변형과 결과 폴더는 지운다. 스킬 없이도 통과한 셀은 케이스에 `guards`가 적혀 있을 때만 상위 tier로 간다.
3. **러너.** 모델 진입점이 오류로 끝났다고 보고한 시행은 채점하지 않는다. 이미 채점된 (변형, 케이스, 반복)은 다시 돌리지 않는다.
4. `triage-issues`의 `SKILL.md`가 이 작업 전과 같다.

## 확정된 제약과 이유

- **기준선은 스킬 없음이다.** 본문이 바뀌지 않으니 "바꾸기 전 본문"은 최종 변형과 같아서 오를 언덕이 없다. 근거는 [testing](../../decisions/testing.md)에 있다.
- **목표는 90%다.** 막는 실수가 되돌릴 수 없는 종류라 높게 잡고, 판정 모델이 한 번 흔들려도 그린에 닿을 여유를 둔다.
- **스킬 본문을 고치지 않는다.** 이 작업은 지금 동작을 지키는 것이다. 현재 본문으로 통과하지 못하는 케이스는 졸업하지 않고 알려진 실패로 기록한다.
- **에이전트는 `claude-sonnet-5-5`로 돌린다.** 이 스킬은 Sonnet에서도 동작해야 하므로, 스위트는 그 하한에서 지킨다는 것을 보여야 한다. 더 강한 모델에서만 통과하는 셀은 Sonnet 사용자의 실패를 숨긴다.
- **케이스와 grader를 약하게 만들어 그린에 닿지 않는다.** 승인 뒤에 바꾸려면 다시 승인을 받는다.

## 가정

- 판정 모델은 `claude-opus-5-5`로 기존 스위트와 같게 둔다. 바꿀 수 있는 가정이다.
- GitHub Issues와 Linear는 대역 CLI나 대역 MCP 응답으로 대신하고, Slack 알림은 보낸 내용만 기록한다. 기존 `fixtures/post-release`를 그대로 쓴다.
- 반복 2회, 동시 실행 4개로 둔다.

## 범위 밖

- `triage-issues` 본문 수정. 실패가 드러나면 별도 작업이다.
- 모든 스킬의 `evals.json`을 채점하는 공용 러너. [no-runner-for-behavior-eval-cases](../../follow-ups/no-runner-for-behavior-eval-cases.md)가 다룬다.

## 미뤄 둔 것

- 현재 본문이 지켜야 할 동작을 반복해서 놓치는 경우의 수정. 다시 여는 조건: 이 climb에서 알려진 실패로 기록된 케이스가 생기면, 그 증거로 `docs/follow-ups/`에 항목을 남기고 그 항목이 다시 연다.

## 남은 위험

- 트래커 대역이 실제 Linear MCP나 `gh`의 응답 모양과 다르면, 에이전트가 대역에서만 맞게 행동할 수 있다. 구현할 때 실제 응답을 한 번 떠서 대역의 근거로 남긴다.
- 세션 기록에서 뽑은 변형이 적으면 12개를 채우지 못할 수 있다. 그때는 나누지 않고 전체를 채점하며 결과를 방향성으로 읽는다.
