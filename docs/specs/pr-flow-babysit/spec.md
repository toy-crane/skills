# PR을 올린 뒤 CI와 리뷰 봇까지 대응하기 (`babysit-pr`)

- 결정: [skill-design](../../decisions/skill-design.md). 다른 스킬을 부르는 스킬이 그 스킬을 요구하는 방식, Git 전달 스킬이 적어야 할 결과·권한·보존·증거, `implement`의 실행 가능한 결과 전달 규칙이다. 이 작업이 마지막 규칙의 시점을 바꾼다.
- 결정: [pipeline](../../decisions/pipeline.md). `implement`가 리뷰와 결과 전달을 끝내는 순서다.
- 결정: [skill-naming](../../decisions/skill-naming.md). `babysit-pr`은 `babysit-specs`와 같은 "babysit-대상" 형식을 따른다.
- 결정: [skill-layout](../../decisions/skill-layout.md). 새 스킬이 들어갈 그룹과 배포 경로다.
- 결정: [pr-descriptions](../../decisions/pr-descriptions.md). PR 본문 규칙이다. 이 작업은 제목 규칙만 더한다.
- 관련 spec: [codex-review-gate](../codex-review-gate/spec.md). main의 "대화 해결 필수" 설정과 그 이유다. 이 작업이 그 이유 문장을 고친다.
- 참고 자료: t3dotgg/tstack의 `babysit-pr`, `file-pr`, `leaving-pr-comments` (MIT). 대기 방식, 봇 지적 처리, 코멘트 표시를 여기서 가져온다.

## 문제

`pr`은 PR을 만들고 끝난다. `merge`는 체크가 통과하기만 기다린다. 리뷰 봇이 남긴 지적을 읽고 고치거나 답하는 단계가 어디에도 없다. 이 저장소는 Codex 리뷰가 붙어 있고 대화 해결이 머지 조건이라, 지적이 하나라도 남으면 사람이 직접 읽고 고치고 닫아야 머지된다.

`implement`도 PR로 이어지지 않는다. 검증과 리뷰를 마친 뒤 로컬 서버를 넘기고 끝나서, 사용자가 `pr`이나 `merge`를 따로 불러야 한다. 그때 `pr`은 `implement`가 모은 증거를 모르는 채로 본문을 다시 만든다.

## 사용자에게 보이는 결과

- 새 스킬 `babysit-pr`은 열린 PR 하나를 맡아, 머지할 수 있는 상태가 되거나 사람이 필요한 상태가 될 때까지 지켜보고 대응한다.
- `implement`가 완료되면 ready 상태의 PR을 만들고, `babysit-pr`로 봇과 CI 대응을 마친 뒤 로컬 서버 주소와 "머지 준비됨"을 함께 넘긴다.
- `merge`는 머지하기 전에 `babysit-pr`로 PR을 머지할 수 있는 상태로 만든다.
- 에이전트가 사용자 대신 단 PR 코멘트에는 에이전트가 썼다는 표시가 붙는다.
- `pr`이 만드는 PR 제목은 무엇을 만졌는지가 아니라 어떤 효과가 있는지를 말한다.

## 승인된 범위

- `babysit-pr` 스킬을 새로 만들고 배포 목록, 두 에이전트 디렉터리 링크, README에 넣는다.
- `implement`가 완료 뒤 `pr`과 `babysit-pr`을 부르고, 결과 전달 시점을 그 뒤로 옮긴다.
- `merge`가 머지 전에 `babysit-pr`을 부른다.
- `pr`에 제목 규칙을 더한다.
- `codex-review-gate` spec의 대화 해결 이유 문장을 고친다.
- 위 스킬들의 평가 사례를 더한다.
- 플러그인 버전을 올린다.

## 수용 기준

1. `babysit-pr` 본문은 다음을 담는다.
   - 입력은 열린 PR 하나다. 끝나는 상태는 둘이다. **준비됨**은 필수 체크가 현재 head에서 통과했고, GitHub가 요구하는 리뷰가 현재 head를 봤고, 해결되지 않은 리뷰 스레드가 없고, GitHub가 머지 가능하다고 보고하는 상태다. **사람 필요**는 에이전트가 스스로 풀 수 없는 상태다. 고칠 수 없는 체크 실패, 변경을 요청한 사람 리뷰, 의도가 불분명한 충돌, 30분 동안 아무 이벤트가 없는 경우가 여기 해당한다.
   - 기다리는 동안 CI 완료, 새 리뷰 코멘트, 충돌이 생기면 깨어난다. PR 하나에 대기 장치는 하나만 둔다. 다시 시작해도 그 사이에 온 이벤트를 놓치지 않는다. 직접 짠 sleep 반복문으로 기다리지 않는다.
   - 이벤트에 할 일이 없으면 메시지 없이 다시 기다린다. "아직 기다리는 중" 같은 보고나 코멘트를 남기지 않는다.
   - 체크 결과와 리뷰 완료 여부는 현재 head 기준으로만 인정한다. 해결되지 않은 리뷰 스레드는 언제 달렸든 전부 현재 소스와 대조해 처리한다. 봇 지적은 소스와 대조해 확인한 뒤에만 고친다. 고친 지적에는 무엇을 고쳤는지 답하고, 동의하지 않는 지적에는 근거(file:line, 테스트, 출력)를 달아 답한 뒤 스레드를 닫는다. 답글이 실제로 올라간 뒤에만 닫는다.
   - 저장소 실패와 인프라 일시 장애를 구분한다. 일시 장애는 다시 돌리고, 코드를 고치지 않는다.
   - 리뷰 대응으로 PR이 커지지 않게 한다. 의도한 경우에서 실제로 일어나는 버그만 고치고, 다른 경로나 드문 경우, 작은 성능 차이, 의도에 없는 테스트와 방어 코드는 이유를 달아 거절한다.
   - GitHub가 강제하지 않는 봇은 참고로만 다루고, 그 봇을 기다리지 않는다. 필수 리뷰 봇이 현재 head를 리뷰하지 않았으면, 그 봇이 받는 요청 방법으로 한 번 요청한다(Codex는 `@codex review`).
   - 사람의 코멘트나 리뷰가 들어오면 봇 대응보다 먼저 처리한다.
   - 사용자 대신 다는 모든 코멘트는 첫 줄에 GitHub 노트 블록으로 에이전트가 사용자 대신 썼다는 표시를 붙인다. 모델 이름은 넣지 않는다. 올리기 전에 비밀값과 개인 정보를 확인한다.
   - 끝날 때 상태(준비됨 또는 사람 필요), 고친 것, 이유를 달고 거절한 것, 남은 일을 보고한다.
2. `implement` 본문은 다음을 담는다.
   - 완료 조건을 모두 충족했을 때 `pr`로 ready PR을 만들고, 이어서 `babysit-pr`을 부른다. 완료되지 않았거나 막혔으면 PR을 만들지 않고 지금처럼 막힌 지점을 보고한다. draft PR은 만들지 않는다.
   - 사용자가 PR을 올리지 말라고 했거나 저장소에 GitHub 원격이 없으면, PR과 `babysit-pr` 단계를 건너뛰고 지금처럼 결과를 넘긴다.
   - 로컬 서버 주소는 `babysit-pr`이 끝난 뒤 넘긴다. 마지막 보고에는 PR 링크, `babysit-pr`의 결과 상태, 로컬 서버 주소와 확인할 것이 함께 나온다.
   - 머지하지 않는다.
   - `pr`과 `babysit-pr`을 필수 스킬로 확인하고, 없으면 설치 명령과 함께 멈춘다.
3. `merge` 본문은 PR을 만들거나 갱신한 뒤 머지하기 전에 `babysit-pr`을 부르고, 준비됨을 받았을 때만 머지 단계로 간다. 사람 필요를 받으면 PR을 열어 둔 채 그 이유를 보고한다. `babysit-pr`을 필수 스킬로 확인한다.
4. `pr` 본문의 제목 규칙: 저장소의 제목 관례를 따르되, 어떤 파일이나 메커니즘을 바꿨는지가 아니라 사용자나 시스템에 어떤 효과가 있는지를 말한다.
5. `codex-review-gate` spec의 "Require conversation resolution" 이유는, 스레드마다 누군가 고치거나 이유를 달아 대응해야 닫힌다는 뜻으로 고친다. 에이전트가 대응 뒤 닫는 것을 허용한다.
6. 위 동작을 eval로 증명한다.
   - 지표: 사례별 기대 항목 충족률. `skill-evals/<name>/evals.json`의 `expectations` 형식이다.
   - 목표: 보지 않은 사례에서 `babysit-pr`의 기대 항목을 모든 반복에서 전부 충족한다. `implement`, `merge`, `pr`의 기존 사례 충족률은 이번 변경 직전 본문의 기준선 아래로 떨어지지 않는다. `babysit-pr`의 기준선은 스킬 없음이다.
   - 사례 출처: 이 저장소의 실제 PR 중 Codex 리뷰 스레드가 있었던 PR(예: #106)의 체크·코멘트·리뷰 이력을 재생할 수 있는 고정 데이터로 만든다. 다음 상황을 최소한 담는다. 맞는 봇 지적, 틀린 봇 지적, 일시 장애로 실패한 체크, 고칠 수 없는 체크 실패, 봇 대응 중 들어온 사람 코멘트, 범위를 키우는 지적, 아무 이벤트도 오지 않는 경우. `implement` 사례는 기존 `skill-evals/implement/fixtures`에 완료 경우와 미완료 경우를 더한다.
7. 플러그인 버전이 `main`보다 올라가 있고 `claude plugin validate . --strict`가 통과한다.

## 확정된 제약과 이유

- 에이전트가 대응한 리뷰 스레드는 에이전트가 닫는다. 대화 해결 설정이 막으려던 사고는 지적이 대응 없이 머지된 경우(#106)였고, 사람이 직접 닫는 것 자체가 목적이 아니었다. 닫힌 스레드마다 고친 내용이나 거절 이유가 남아 나중에 검토할 수 있다.
- 로컬 서버는 `babysit-pr`이 끝난 뒤 넘긴다. 사용자가 최종 코드를 한 번만 보고 머지까지 판단하는 쪽을 골랐다. 기다리는 동안 볼 게 없는 대가를 받아들인다.
- `implement`는 PR까지 만들고 머지는 하지 않는다. 머지 권한은 사용자가 `merge`를 부르거나 `self-ship`을 부를 때만 생긴다.
- 대기 장치를 스크립트로 둘지, 각 도구의 감시 기능을 쓸지는 구현이 정한다. 위 수용 기준의 동작을 지키면 된다.

## 가정 (수정 가능)

- 이벤트 없이 30분이 지나면 사람 필요로 끝낸다.
- 코멘트 표시 문구는 "🤖 에이전트가 <사용자> 대신 답함"이다. 사용자 이름은 GitHub 로그인으로 쓴다.
- `babysit-pr`은 PR 브랜치에 자기가 고친 커밋을 push하고, 리베이스가 필요하면 그 PR 브랜치에만 `--force-with-lease`로 push한다.

## 범위 밖

- 머지 결정과 머지 실행. `merge`와 `self-ship`이 맡는다.
- 다른 회사 모델로 하는 교차 리뷰.
- 여러 PR의 머지 순서 조율.

- 없음.

## 남은 위험

- 봇 지적을 "소스와 대조해 확인"하는 판단이 약하면, 틀린 지적을 고치거나 맞는 지적을 거절할 수 있다. 닫힌 스레드의 답글로 드러나지만 막지는 못한다.
- 대기 장치가 도구마다 달라서, 한쪽 도구에서만 이벤트를 놓치는 경우가 생길 수 있다.
- `implement`의 마지막 단계가 길어진다. Codex 리뷰가 보통 몇 분 걸리고, 지적이 있으면 대응과 재리뷰가 더해진다.
