# PR 화면 증거의 영상 우선

[PR 본문 결정](../../decisions/pr-descriptions.md)이 PR 본문 설명, 화면 증거, 첨부, 민감 정보 검사의 기준이다. 이 스펙은 그중 화면 증거의 기본 매체를 사진에서 영상으로 바꾸는 작업이다.

## 문제

지금 `pr`과 `merge`는 화면 변경이 있으면 전후 스크린샷을 나란히 두는 것을 기본으로 한다. 영상은 정지 화면으로 중요한 동작을 설명할 수 없을 때만 덧붙인다. 그 판단을 에이전트가 하므로, 찍기 쉬운 사진 쪽으로 기울기 쉽다. 그 결과 클릭한 뒤의 상태, 로딩과 오류, 화면 전환처럼 PR에서 실제로 판단해야 하는 동작이 본문에 보이지 않는다.

## 사용자에게 보이는 결과

- 화면 변경이 있는 PR의 본문은 기본으로 변경 전과 변경 후의 실제 동작 영상을 보여 준다.
- 두 영상은 같은 흐름, 같은 데이터, 같은 화면 크기로 찍혀서 무엇이 달라졌는지 비교할 수 있다. 영상 아래에는 달라진 점과 이유를 적는다.
- 사진만 보이는 PR은 그 이유가 본문에 적혀 있다. 이유는 사진으로 충분한 정적 변경이거나, 영상을 쓸 수 없는 구체적 한계다.
- 동작 변경과 세밀한 스타일 변경이 함께 있으면, 영상과 함께 세밀한 부분의 전후 사진이 나란히 놓인다.

## 승인된 범위

`pr`과 `merge`의 화면 증거 규칙을 다음처럼 바꾼다. 아래 상황들은 기대하는 판단을 보여 주는 예시이자 평가 사례다. 스킬에는 이 목록을 그대로 옮기지 않고 목적을 쓴다(확정된 제약 참고).

1. **기본은 전후 영상이다.** 아래 예외에 해당하지 않는 화면 변경은 상호작용, 전환과 애니메이션, 로딩·성공·실패 같은 비동기 상태, 여러 단계로 된 흐름, 스크롤과 제스처, 버그 재현을 포함해 모두 영상을 기본으로 한다. 변경 전 영상은 base를 실행해 같은 흐름으로 찍는다.
2. **사진으로 충분한 변경은 사진만 쓴다.** 영상을 찍지 않고 전후 사진을 나란히 둔다.
   - 문구, 번역, 아이콘만 바뀐 경우
   - 색, 글꼴, 간격, 크기처럼 스타일만 바뀐 경우
   - 상호작용 없이 정적 레이아웃만 바뀐 경우(배치, 정렬, 반응형 구간별 모양)
3. **영상을 쓸 수 없으면 사진으로 내려가고 이유를 밝힌다.**
   - 현재 환경에 녹화 수단이 없거나 녹화가 실패한 경우
   - 판단할 동작만 남기도록 줄여도 GitHub 첨부 한도를 넘는 경우
   - 민감 정보를 영상 전체에서 가릴 수 없고, 안전한 테스트 데이터로 다시 찍을 수도 없는 경우
4. **섞인 변경은 영상과 사진을 함께 쓴다.** 동작은 전후 영상으로 보여 주고, 세밀한 스타일 차이는 전후 사진을 나란히 덧붙인다.
5. 변경 전이 없는 새 화면은 변경 후 영상만 올린다. base를 실행할 수 없으면 기존 규칙대로 그 한계를 밝히고 확보한 증거만 올린다.

## 수용 기준

1. 버튼을 누르면 로딩 뒤 결과가 바뀌는 화면 변경에서, 녹화와 첨부가 가능하면 본문이 같은 흐름의 전후 영상을 담고 그 아래에 달라진 점과 이유를 적는다. 사진 비교만으로 끝내지 않는다.
2. 문구나 색만 바뀐 변경에서는 영상을 만들지 않고 전후 사진을 나란히 둔다.
3. 동작 변경과 세밀한 간격 변경이 섞인 경우, 본문은 전후 영상과 함께 간격 부분의 전후 사진을 나란히 담는다.
4. 녹화 수단이 없거나 실패하면 사진으로 비교하고, 영상이 없는 이유를 본문에 구체적으로 적는다.
5. 잘라도 첨부 한도를 넘는 영상은 올리지 않고 사진으로 내려가며, 한도 초과를 이유로 적는다.
6. 실제 고객 정보가 찍힌 영상은 올리지 않는다. 안전한 테스트 데이터로 다시 찍을 수 있으면 다시 찍은 영상을 올리고, 그럴 수 없고 모든 프레임을 가릴 수도 없으면 검사한 사진으로 내려가며 그 이유를 적는다.
7. 버그 수정 PR에서 base를 실행할 수 있으면, 변경 전 영상이 버그가 나타나는 과정을 보여 준다.
8. 새 화면을 추가한 PR은 변경 후 영상만 올리고 변경 전이 없다는 점을 밝힌다.
9. 원격 본문에서 영상 첨부가 플레이어로 보이는지 확인한 뒤에만 리뷰어가 볼 수 있다고 보고한다.
10. 기존 PR을 갱신할 때 예전 사진 비교만 있고 이번 변경이 영상 대상이면, 최종 변경에 맞는 영상으로 증거를 바꾼다.

## 확정된 제약과 이유

- **스킬 문장은 목적 중심으로 쓴다.** AI가 충분히 판단할 수 있다고 보고, 스킬에는 상황 목록이나 단계 대신 목적을 적는다. 목적은 세 가지다. 리뷰어가 판단할 동작을 실제로 보게 할 것, 움직임이 판단에 보탬이 없으면 사진으로 나란히 비교할 것, 영상이 없으면 그 이유를 밝힐 것. 위 범위의 상황 목록은 이 목적에서 나와야 하는 결과이며, 평가 사례로 확인한다. 사용자가 요청했고, [skill-design](../../decisions/skill-design.md)의 방향(모델이 이미 하는 절차를 늘어놓지 않고 결과에 집중하게 함)과도 맞는다.
- **사진이 아니라 영상이 기본이다.** 기존처럼 사진을 기본으로 두고 영상 상황 목록만 늘리면, 목록에 딱 맞지 않는 변경은 다시 사진으로 간다. 기본을 바꾸면 영상을 생략할 때 이유를 밝혀야 하므로 리뷰어도 왜 사진뿐인지 알 수 있다.
- **변경 전도 영상이다.** 비교 대상이 동작이면 변경 전 동작도 영상이어야 비교된다. 기존 규칙이 이미 base 실행과 같은 조건의 촬영을 요구하므로 늘어나는 비용은 녹화뿐이다. 변경 후만 영상으로 찍고 변경 전은 사진으로 두는 방식은 영상과 사진을 비교하게 되어 차이가 흐려지므로 택하지 않았다.
- **정적 변경은 사진이 더 낫다.** 문구, 색, 간격, 정적 레이아웃은 픽셀을 나란히 놓고 보는 편이 영상보다 잘 비교된다.
- **`pr`과 `merge`는 같은 문장으로 함께 바뀐다.** 두 스킬의 PR 본문 규칙은 같은 텍스트이며, 각 스킬은 독립적으로 설치되므로 자기 사본을 가진다. 한쪽만 바꾸지 않는다.
- **민감 정보 기준은 사진과 같다.** 영상은 모든 프레임에서 가려야 하므로, 처음부터 안전한 테스트 데이터로 찍는 것을 우선한다.
- 2026-10-03 설치된 `gh` 2.100.0의 `gh pr create --help`는 `--attach`가 영상도 올리고 본문에서 플레이어로 보여 준다고 설명한다. 영상에는 대체 텍스트를 달 수 없다.
- [GitHub 첨부 문서](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/attaching-files)는 영상 형식으로 .mp4, .mov, .webm을 지원하고, 영상 한도를 무료 플랜 10MB, 유료 플랜 100MB로 둔다. 호환성을 위해 H.264를 권한다.

## 가정 (수정 가능)

- 영상은 판단할 동작만 담도록 짧게 자른다.
- 전후 영상은 위아래로 배치한다. 표 셀 안에서 영상 플레이어가 보이는지는 문서로 확인하지 못했다.
- 영상에는 대체 텍스트가 없으므로, 각 영상 바로 위에 무엇을 찍었는지(변경 전·후, 흐름, 조건)를 한 줄로 적는다.
- 웹 화면은 브라우저 자동화 도구의 녹화로, Expo 앱은 `agent-device`의 `record`로 찍을 수 있다. 실행 환경마다 실제 가능 여부를 확인한다.

## 범위 밖

- `triage-issues`가 이슈 코멘트에 붙이는 증거. 요청은 PR 본문에 관한 것이며, 이슈 코멘트의 매체 기준은 별도로 정한다.
- `expo-dev-loop`, `expo-smoke-test`, `implement`의 검증 증거 기준. 검증에 필요한 증거와 PR 리뷰어에게 보여 줄 증거는 목적이 다르다.
- 리뷰용 영상을 저장소에 커밋하거나 별도 호스팅을 쓰는 일. 기존 결정대로 GitHub 첨부만 쓴다.

## 보류한 점

- 없음.

## 남은 위험

- 표 셀 안에서 영상이 플레이어로 보이지 않으면 전후 영상을 나란히 볼 수 없다. 위아래 배치는 세밀한 차이를 비교하기 어렵게 하므로, 섞인 변경에서는 사진을 함께 쓰는 규칙에 기댄다.
- 무료 플랜의 10MB 한도에서는 긴 흐름이 사진으로 내려가는 경우가 잦을 수 있다.
- 실행 환경에 녹화 수단이 없으면 규칙이 바뀌어도 실제로는 사진만 올라간다. 이때 이유가 본문에 적히는지가 이 변경의 최소 효과다.
- 영상이 늘면 base 실행과 녹화 때문에 PR 생성 시간이 길어진다.
- `pr`의 기존 평가 사례 중 하나는 상호작용 변경에 "전후 이미지와 상호작용 영상"을 기대한다. 새 기준에 맞게 기대 결과를 갱신하지 않으면 평가가 이전 규칙을 계속 요구한다.
