# 설명 형태를 내용 종류로 정하기

[explain-visually](../../decisions/explain-visually.md)는 이 작업의 기준이다.
내용 종류별 형태, 출력 스타일과 스킬의 역할 분담, 첫 화면 규칙, 한 문장
브레이크, 기각된 대안이 모두 거기 있다.
[skill-design](../../decisions/skill-design.md)은 description에 발동 조건을
두는 규칙과 스킬 사이 의존 규칙을 정한다.
[testing](../../decisions/testing.md)은 아래 LLM 품질 수락 기준을 eval로
증명하는 방법(train과 held-out 분리, 졸업)을 정한다.

## 문제

사용자가 지금의 문제나 설명을 빠르고 쉽게 이해하게 돕는 것이 목적이다.
그런데 지금은 두 가지가 막고 있다.

- `explain-visually`는 사용자가 설명을 요청할 때만 발동한다. 이해를 도와야
  하는 설명의 대부분은 에이전트가 먼저 하는 결과 보고, 문제 원인 설명,
  선택지 비교인데, 이런 응답은 글로만 나온다.
- 발동하더라도 형태를 고르는 기준이 정해져 있지 않다. 그래서 과정은 한
  장짜리 그림으로, 메커니즘은 설명만 붙은 위젯으로 나올 수 있다.
- 렌더러가 연결돼 있으면 한 문장으로 끝날 질문에도 위젯을 그린다. 이전
  eval 기준선에서 "Comprehension gap 뜻"은 2회 중 2회, ".claude/skills
  심링크를 왜 커밋했나"는 2회 중 1회 렌더링했다. 렌더링이 늘어나면 이
  문제도 함께 커진다.

## 사용자에게 보이는 결과

- 플러그인 사용자는 `/output-style`에서 `at-a-glance`를 고를 수
  있다. 켜면 사용자가 설명을 요청했든 에이전트가 먼저 설명하든 내용의
  종류에 따라 형태가 정해진다.

  | 내용 종류 | 형태 |
  |---|---|
  | 사실이나 정의 | 글 한두 문장. 표나 그림을 덧붙이지 않는다 |
  | 구조나 관계 | 정지 다이어그램. 설명 글은 그림 안이나 바로 옆에 붙인다. 응답 안에 담을 수 있으면 표나 `A → B → C` 흐름으로 응답 안에 쓴다 |
  | 여러 단계 과정 | 스테퍼. 전체 단계 이름은 처음부터 보이고, 다음 단계로 넘기는 건 사용자가 한다. 자동 재생하지 않는다 |
  | 값에 따라 결과가 바뀌는 메커니즘 | 조작형. 조작하기 전에 결과를 예측하게 하고, 예측한 뒤에 결과와 조작 수단을 보여 준다 |

- 응답 안에 담을 수 없는 구조, 과정, 메커니즘은 `explain-visually`가 세션의
  렌더러로 그린다. 사용자가 따로 부르지 않아도 된다.
- 응답 첫 줄에는 답이나 결론이 오고, 추상어 대신 실제 파일 경로, 값, 예시를
  쓴다. 장식용 그림이나 아이콘은 넣지 않는다.
- 스타일을 켜도 작업 방식, 도구 사용, 코드 작성은 그대로다. 응답 언어는
  사용자 언어를 따른다.
- 스타일을 켜지 않은 사용자(skills.sh 사용자 포함)에게는 지금처럼 사용자가
  설명을 요청할 때만 `explain-visually`가 발동한다. 다만 요청을 받았을 때 고르는
  형태는 위 표를 따른다.
- 한 문장으로 끝나는 질문에는 렌더러가 연결돼 있어도 그리지 않는다.
- 렌더러가 없는 환경에서는 응답 안 텍스트로 대신한다. 스테퍼는 번호 매긴
  단계로, 조작형은 예측 질문과 값별 결과를 담은 표로 바뀐다.

## 범위

- 새 출력 스타일 `at-a-glance`. 플러그인으로 배포되고, 이 저장소에서도
  골라 쓸 수 있으며, README의 출력 스타일 목록에 들어간다.
- `explain-visually`의 형태 선택과 발동 범위를 위 결과에 맞춘다.
- 한 문장 브레이크 누수를 고친다. `docs/follow-ups/`에 있던 같은 항목을 이
  spec이 넘겨받는다.
- 설치한 플러그인 사용자가 업데이트를 받도록 플러그인 버전을 올린다.

## 수락 기준

LLM 출력에 대한 기준은 eval로 증명하며, 각 기준의 목표는 held-out 케이스로만
판정한다. 케이스는 이 저장소의 실제 주제(스킬, 결정 문서, 배포 경로, 워크플로)
에서 새로 만들고, 이전 eval의 control 케이스 3개는 train에만 둔다. 각 기준은
Sonnet 5.5에서 측정한다. Opus 5.5는 더 상위 모델이라 Sonnet이 넘는 기준은
넘는다고 보고 따로 측정하지 않는다(구현 중 사용자 결정, 2026-11-19).

1. **형태 라우팅**: 스타일을 켜고 렌더러를 연결한 상태에서, 내용 종류 정답이
   붙은 held-out 설명 상황 20개(사용자가 요청한 것 10개, 에이전트가 먼저
   설명하는 작업 상황 10개, 네 종류가 고르게 섞임)를 2회씩 돌린다. 고른
   형태가 정답과 일치하는 시행이 40회 중 36회 이상이어야 한다.
2. **한 문장 브레이크**: 렌더러를 연결한 상태에서, 한 문장이면 답이 끝나는
   held-out 질문 10개를 2회씩 돌린다. 렌더러 호출이나 다이어그램(ASCII와 표
   포함)이 나온 시행이 20회 중 1회 이하여야 한다. 스타일을 켠 경우와 끈 경우
   모두 이 기준을 넘어야 한다.
3. **스테퍼**: 과정으로 분류돼 렌더링된 held-out 응답 10개를 2회씩 돌린다.
   아무 조작 전 첫 화면에 모든 단계 이름이 보이고 자동으로 넘어가지 않는
   시행이 20회 중 19회 이상이어야 한다.
4. **예측 먼저**: 메커니즘으로 분류돼 렌더링된 held-out 응답 10개를 2회씩
   돌린다. 결과를 보여 주기 전에 예측을 묻는 시행이 20회 중 18회 이상이어야
   한다.
5. **기존 첫 화면 기준 유지**: `skill-evals/explain-visually/`의
   `explain-visually-first-view` held-out 점수가 지금 기준선(20/20) 아래로
   떨어지지 않는다.
6. **스타일 없이 요청 시 발동 유지**: 스타일을 끈 상태에서
   `skill-evals/explain-visually/evals.json`의 기존 기대가 지금처럼 통과한다.

결정적으로 확인하는 기준:

7. 스타일을 켜도 Claude Code의 기본 코딩 지시가 시스템 프롬프트에 남는다.
8. 플러그인을 설치하면 `/output-style` 목록에 `at-a-glance`가 보이고,
   이 저장소에서 작업할 때도 고를 수 있다.
9. `claude plugin validate . --strict`가 통과하고, 플러그인 버전이 올라가 있다.

## 정해진 제약과 이유

- 형태는 사용자가 요청했느냐가 아니라 내용의 종류로 정한다. 교육 연구에서
  효과를 가르는 기준이 내용의 종류였다. 그림과 글을 함께 주고 글을 그림 옆에
  붙일 때(Mayer의 근접성·신호·분절 원칙), 학습자가 속도를 정할 때, 시뮬레이션
  전에 예측하게 할 때(PhET) 효과가 컸다. 애니메이션 자체의 이점은 작았다.
- 새 스타일은 `natural-korean`과 따로 둔다. 어느 언어로든 쓸 수 있게 하기
  위해서다. Claude Code는 출력 스타일을 하나만 켤 수 있으므로, 사용자는 둘 중
  하나를 고른다.
- 스타일 이름은 `at-a-glance`다. 이 스타일의 목적인 "한눈에 이해"를 그대로 말하고,
  글로 답하는 경우까지 포함해 네 형태 모두와 맞는다. `visual-explanations`와
  `illustrated`는 늘 그린다는 뜻으로 읽혀서, `explanatory`와 `learning`은 Claude
  Code 기본 출력 스타일과 겹쳐서 쓰지 않았다.
- 사용자가 혼란스러워 보인다는 짐작으로는 발동하지 않는다. 발동 계기는
  에이전트가 무언가를 설명한다는 사실이다.
- 첫 화면만으로 전체 구조와 진행 방향이 보여야 한다는 기존 규칙은 모든 형태에
  그대로 적용된다.

## 가정 (바꿀 수 있음)

- 스타일 본문은 영어로 쓴다.
- 응답 안에서 쓰는 구조는 표와 화살표 흐름으로 한정한다. mermaid는 터미널에서
  그려지지 않아서 쓰지 않는다.
- "응답 안에 담을 수 있느냐"는 고정된 숫자 없이 모델이 판단한다.

## 건드리지 않는 것

- 사용자의 숙련도에 따라 형태를 바꾸는 것. 사용자가 이번 범위에서 빼기로
  했다.
- `natural-korean`. 기본 코딩 지시가 빠질 수 있다는 문제는
  `docs/follow-ups/natural-korean-drops-coding-instructions.md`에서 따로
  다룬다.
- skills.sh로 출력 스타일을 배포하는 것. skills.sh는 `SKILL.md`만 복사하므로
  불가능하다.

## 남은 위험

- 과정이나 메커니즘을 설명할 때마다 렌더링하므로 응답이 느려지고 토큰 비용이
  는다. 라우팅이 틀리면 짧게 끝날 응답까지 무거워진다.
- 렌더러는 호스트마다 다르다. 스테퍼나 조작형을 그릴 수 없는 환경에서는 텍스트
  대체만 나간다.
- 한국어 사용자가 이 스타일을 고르면 `natural-korean`의 문체 규칙을 받지
  못한다.
- 수락 기준 1–4는 합성한 상황으로 측정한다. 실제 대화에서 다르게 나올 수 있다.
