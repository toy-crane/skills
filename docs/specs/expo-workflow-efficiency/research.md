# Flyn Codex 세션의 워크플로우 지연 분석

상태: 조사 결과와 개선 후보. 구현의 승인 범위는 [spec.md](spec.md)에 있다.
분석일: 2026-09-15.

## 공개 자료의 범위

이 문서는 로컬 세션 조사에서 얻은 집계와 기술적 관찰을 요약한다. 원문
프롬프트, 세션·부모 ID, 개별 세션의 시각과 로컬 파일 경로는 공개하지 않는다.
원본 기록과 세션별 색인은 비공개 로컬 조사 자료로만 보관한다. 따라서 아래
수치는 조사 결과의 보고이며, 이 저장소만으로 원본을 독립 재집계할 수 있다는
뜻은 아니다. 동작 순서 모의 평가의 근거와 한계는 [verification.md](verification.md)에 있다.

## 조사 범위와 방법

- Codex의 활성·보관 JSONL에서 Flyn 작업 디렉터리나 저장소 메타데이터가
  일치하는 기록과 연결된 부모·자식 기록을 포함했다. 다른 프로젝트와 Claude
  세션은 제외했다.
- 원본 파일 277개, 고유 세션 273개, 중복 제거 후 구조화 레코드 212,336개를
  처리했다. JSON 파싱 실패는 0개다. 원본 약 1.5GB에는 이미지·첨부와 반복
  컨텍스트도 포함된다.
- 턴·호출 식별자로 이어받은 기록의 중복을 제거했다. 완료 이벤트의 시간을
  우선하고, 없으면 시작·종료 차이를 썼다. 미완료 구간을 추정해 채우지 않았다.
- 사용자 대화의 시작 주제와 장시간 턴을 점검하고, 반복 징후와 핵심 사례는
  원문 호출·결과를 대조했다. 전체 내용을 줄마다 정독했다는 뜻은 아니다.
- 턴 사이 유휴시간은 제외했다. 턴 안의 기기·CI·리뷰·사용자 응답 대기는
  완전히 분리하지 못하므로 순수 코딩 시간으로 해석하지 않는다. 보조 작업의
  시간을 부모 시간에 합산하지 않았다.

| 세션 분류 | 고유 세션 수 |
| --- | ---: |
| 사용자 대화 | 89 |
| review | 22 |
| worker | 51 |
| exec | 34 |
| guardian | 77 |
| 합계 | 273 |

사용자 대화의 중복 제거 완료 턴은 1,096개다. 이 중 30분 이상은 35개,
60분 이상은 15개다. 보조 기록 184개를 사용자 요청 184건으로 세지 않았다.
오류 문자열의 단순 출현 횟수도 실제 실패 횟수로 간주하지 않았다.

## 관찰과 개선 후보

| 경계 | 직접 확인한 기술적 관찰 | 해석과 개선 후보 |
| --- | --- | --- |
| PR 리뷰와 수정 | 한 병합 턴이 131.4분 이어졌고 리뷰 재요청 명령 19회와 base 통합 명령 3회가 있었다. 문자열 교정의 구두점·공백·경계 처리 지적이 이어졌다. | 19회는 명령 시도 수이며 완료 리뷰 수가 아니다. 실제 결함도 있어 전체 시간을 낭비로 볼 수 없다. 같은 계열의 일반 규칙, 정상 반례, 경계 사례를 함께 검증한다. |
| 실행 환경 준비 | 최소 9개 사용자 세션에서 로컬 설정 누락으로 앱 또는 실제 모델 호출이 막혔다. | 환경 파일 목록의 존재와 실제 작업 환경의 준비는 다르다. 작업에 필요한 설정·실행 경로를 초기에 확인하는 후보이며 이번 구현 범위에서는 제외했다. |
| 리뷰 실행 호환성 | 5개 사용자 세션에서 6회의 리뷰 시작 실패 보고를 확인했다. 같은 세션에서도 미지원 모델 문제가 반복됐다. | 하네스 리뷰와 별도 CLI를 구분하고 성공한 실행 경로를 재사용할 수 있다. 절감 시간은 측정하지 않았다. |
| 완료 판정과 승인 자료 | 159.5분 구현 턴의 완료 보고 뒤 접근성 누락이 드러났다. 다른 사례에서는 완료 항목의 누락 6개를 모아 보완했고 후속 구현은 131.3분이었다. | 후속 구현에는 실제 네이티브 결함 조사와 도구 복구도 있어 전부 앞선 누락 비용으로 계산할 수 없다. 기존 승인 자료 로딩·플랫폼별 실제 화면 대조 규칙이 실행되는지 확인한다. |
| 검증 도구 상태 | CLI·daemon 버전 충돌, 목록에 없는 기기 소유권, 준비 기록과 실제 앱 설치 상태 불일치가 보고됐다. | 제품 결함과 도구 상태 실패를 구분해야 한다. 다른 작업의 기기 소유권을 우회하지 않는 준비·복구가 필요하다. |
| 검증 데이터 | 실제 사용 후 남은 데이터가 표 전체 개수 테스트를 실패시켰다. 초기 실행만 실패하는 검사도 있었다. | 테스트가 만든 데이터 범위를 검증하고 기존 격리 경로를 사용한다. 공유 개발 DB 초기화를 일반 해법으로 삼지 않는다. |

이 관찰은 일회성 예외에 모두 규칙을 추가해야 한다는 근거가 아니다. 당시에는
실행 준비와 PR 수정 반복을 큰 후보로 봤지만, 사용자는 worktree와 개별 예외
개선을 이번 범위에서 제외하고 최종 검증 순서 변경을 선택했다.

## 이번에 선택한 순서

구현 중 실제 관찰과 승인 자료 대조를 유지하면서 전체 자동 검사 → 로컬 전체
리뷰 → 필요한 수정·영향 검증 → 최종 변경 흐름·핵심 흐름 검증으로 배치한다.
리뷰어에게는 이미 얻은 집중 검증 근거를 제공한다. 최종 검증이나 PR 리뷰에서
실행 동작이 바뀌면 해당 근거를 다시 확보해야 하므로 항상 검증 한 번으로
끝난다고 약속하지 않는다. 필수 PR 리뷰와 플랫폼별 완료 기준도 유지한다.

## 아직 입증하지 않은 주장

- 이 순서 변경이 실제 세션을 몇 분 줄이는지.
- 집중 검증 근거만 받은 리뷰가 중요한 결함을 더 늦게 발견하는지.
- 컨텍스트 축소, 병렬 작업, 로그인 준비 재사용 각각의 순효과.
- 매 파일 저장마다 기기 검증을 반복하는 일이 주된 지연 원인인지.

후속 측정은 실제 작업의 시작 조건·검증 범위·수정 횟수를 함께 기록해야 한다.
전체 세션 시간이나 단일 모의 실행의 호출 횟수만으로 개선율을 산출하지 않는다.
